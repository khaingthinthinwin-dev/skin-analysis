## 1. 機能概要

### 1.1 目的と範囲

本画面は、Cosmetics Finderプラットフォームにおけるユーザー認証のエントリーポイントとして機能します。サインアップおよびログインサブシステムは、新規ユーザーがアカウントを作成し、既存ユーザーが認証して安全なセッションを確立するために必要なすべての機能を提供します。

本サブシステムは、すべてのプラットフォーム機能へのゲートウェイです。適切に検証され、認証されたユーザーのみが保護機能にアクセスできるようにしつつ、JWTトークン管理、パスワードハッシュ化、セッション追跡によってセキュリティを維持します。

### 1.2 機能責任

本画面は以下のコア機能領域を担当します：

1. **ユーザー登録** — 新規ユーザーがメールアドレス、パスワード、名前、ロール選択（購入者または出品者）でアカウントを作成できるようにする。
2. **出品者ライセンスアップロード** — 出品者として登録する場合、ユーザーは事業許可書PDFファイル（license.pdf、最大10MB）をアップロードする必要がある。
3. **ユーザー認証** — ユーザー資格情報を検証し、JWTアクセストークン（有効期限15分）とリフレッシュトークン（有効期限7日）を発行する。
4. **セッション管理** — トークンの更新、ローテーション、無効化をファミリー追跡付きで管理する。
5. **トークンブラックリスト化** — Redisベースのトークンブラックリスト化による安全なログアウトを実装する。
6. **パスワードセキュリティ** — Argon2idアルゴリズム（64MBメモリ、3反復、4スレッド）でパスワードをハッシュ化する。
7. **レート制限** — 認証エンドポイントをブルートフォース攻撃から保護する。
8. **アカウント検証** — 保護ルートアクセスのためのトークン有クン有効性を検証する。

### 1.3 対象ユーザー

| 属性 | 値 |
|------|-----|
| **プライマリアクター** | 未認証ビジター（登録）、認証済みユーザー（ログイン/セッション） |
| **必要認証** | なし（登録）、JWT Bearerトークン（セッション操作） |
| **データスコープ** | 新規ユーザー作成（登録）、自身のセッション管理（ログイン/ログアウト）、事業許可書PDFアップロード（出品者のみ） |

### 1.5 入力／出力

| 入力情報 | データカテゴリ | ソース／説明 |
|---------|---------------|-------------|
| `email` | ユーザー入力 | 登録またはログイン用のメールアドレス |
| `password` | ユーザー入力 | 登録またはログイン用のパスワード |
| `name` | ユーザー入力 | 登録用のフルネーム |
| `role` | ユーザー入力 | 登録用のロール選択（buyer/merchant） |
| `license` | ファイルアップロード | 事業許可書PDF（出品者のみ、最大10MB） |
| `refreshToken` | HTTPクッキー | セッション操作用のリフレッシュトークン |

| 出力情報 | データカテゴリ | 宛先／説明 |
|---------|---------------|-----------|
| `accessToken` | JWTトークン | API認証用にレスポンスボディで返却 |

| `licenseUrl` | URL | アップロードされたライセンスファイルのパス（出品者のみ） |
| `blacklist` | Redisキー | ログアウト用のトークン無効化レコード |

## 3. 状態遷移仕様

### 3.1 ユーザーアカウント状態

| 状態 | 説明 | ログイン可能 | 登録可能 |
|------|------|:-----------:|:--------:|
| `NEW` | ユーザーが登録直後、まだログインしていない | ✓ | ✗ |
| `ACTIVE` | ユーザーアカウントがアクティブで認証可能 | ✓ | ✗ |
| `INACTIVE` | 管理者によってアカウントが無効化 | ✗ | ✗ |
| `EMAIL_UNVERIFIED` | メールアドレスが未検証 | ✓（制限付き） | ✗ |

### 3.2 セッション状態

| 状態 | 説明 | APIアクセス可能 | リフレッシュ可能 |
|------|------|:--------------:|:---------------:|
| `NO_SESSION` | トークン未発行 | ✗ | ✗ |
| `ACCESS_VALID` | アクセストークン有効（≤15分） | ✓ | ✓ |
| `ACCESS_EXPIRED` | アクセストークン期限切れ、リフレッシュ有効 | ✗ | ✓ |
| `REFRESH_EXPIRED` | 両トークン期限切れ | ✗ | ✗ |
| `BLACKLISTED` | トークン無効化（ログアウト） | ✗ | ✗ |

### 3.3 トークンライフサイクル遷移

| 遷移ID | 遷移元状態 | 遷移先状態 | トリガーアクション | ガード条件 |
|--------|-----------|-----------|-------------------|-----------|
| TR-AUTH-01 | `NO_SESSION` | `ACCESS_VALID` | ログイン成功 | 有効な資格情報、レート制限未超過 |
| TR-AUTH-02 | `ACCESS_VALID` | `ACCESS_VALID` | トークン更新 | 有効なリフレッシュトークン、ブラックリスト化なし |
| TR-AUTH-03 | `ACCESS_EXPIRED` | `ACCESS_VALID` | トークン更新 | 有効なリフレッシュトークン、期限切れでない |
| TR-AUTH-04 | `ACCESS_VALID` | `BLACKLISTED` | ログアウト | ユーザーがログアウトを開始 |
| TR-AUTH-05 | `BLACKLISTED` | `NO_SESSION` | トークン期限切れ | RedisのTTLが期限切れ |

## 4. ビジネスルール

### 4.1 登録ルール

| ルールID | ルール名 | 説明 | 実行レイヤー |
|---------|---------|------|-------------|
| BR-AUTH-001 | メールアドレス一意性 | メールアドレスはすべてのユーザーで一意であること。 | バックエンド（DB制約＋サービスチェック） |
| BR-AUTH-002 | パスワード強度 | 最小8文字、大文字、小文字、数字、特殊文字を含むこと。 | バックエンド（DTOバリデーション）＋フロントエンド（Zodスキーマ） |
| BR-AUTH-003 | ロール制限 | 登録時に許可されるロールは「buyer」または「merchant」のみ。 | バックエンド（DTOバリデーション） |
| BR-AUTH-004 | デフォルトロール | ロールが指定されない場合、デフォルトは「buyer」。 | バックエンド（サービスロジック） |
| BR-AUTH-005 | メール検証 | 新規ユーザーは`emailVerified = false`。 | バックエンド（ユーザー作成） |
| BR-AUTH-020 | 出品者ライセンス必須 | ロール=「merchant」の場合、ライセンスファイルアップロード必須。 | バックエンド（DTOバリデーション）＋フロントエンド（条件付きバリデーション） |
| BR-AUTH-021 | ライセンスファイルタイプ | ライセンスファイルはPDF形式のみ。 | バックエンド（ファイルバリデーション）＋フロントエンド（accept属性） |
| BR-AUTH-022 | ライセンスファイル名 | ライセンスファイルは「license.pdf」命名（大文字小文字不問）。 | バックエンド（ファイルバリデーション）＋フロントエンド（ファイル名チェック） |
| BR-AUTH-023 | ライセンスファイルサイズ | ライセンスファイルは10MBを超えてはならない。 | バックエンド（ファイルバリデーション）＋フロントエンド（サイズチェック） |

### 4.2 ログインルール

| ルールID | ルール名 | 説明 | 実行レイヤー |
|---------|---------|------|-------------|
| BR-AUTH-006 | 資格情報検証 | メールアドレスが存在し、パスワードがArgon2ハッシュと一致すること。 | バックエンド（認証サービス） |
| BR-AUTH-007 | アカウントアクティブチェック | ログインするには`isActive = true`であること。 | バックエンド（認証サービス） |
| BR-AUTH-008 | レート制限 | IPあたり300秒間に最大5回のログイン試行。 | バックエンド（Redisレートリミッター） |
| BR-AUTH-009 | 汎用エラーメッセージ | メールアドレスが存在するかどうか、パスワードが間違っているかどうかを決して明かさない。 | バックエンド（エラーハンドリング） |

### 4.3 トークンルール

| ルールID | ルール名 | 説明 | 実行レイヤー |
|---------|---------|------|-------------|
| BR-AUTH-010 | アクセストークン有効期限 | アクセストークンは15分で期限切れ。 | バックエンド（JWT設定） |
| BR-AUTH-011 | リフレッシュトークン有効期限 | リフレッシュトークンは7日で期限切れ。 | バックエンド（JWT設定） |
| BR-AUTH-012 | 絶対セッション制限 | ローテーションに関わらず、最大セッション期間は90日。 | バックエンド（リフレッシュトークンレコード） |
| BR-AUTH-013 | トークンローテーション | リフレッシュリクエストのたびに新しいリフレッシュトークンを発行。 | バックエンド（認証サービス） |
| BR-AUTH-014 | ファミリー追跡 | 各ログインセッションにユニークなファミリーIDを持ち、違反検知に使用。 | バックエンド（リフレッシュトークンレコード） |
| BR-AUTH-015 | リユース検知 | 無効化されたトークンが使用された場合、そのユーザーのすべてのトークンを無効化。 | バックエンド（認証サービス） |

## 6. 機能操作仕様

### 6.1 操作：ユーザー登録

| 属性 | 仕様 |
|------|------|
| **トリガー** | 登録フォームの「アカウント作成」ボタンクリック |
| **APIエンドポイント** | `POST /api/v1/auth/register` |
| **リクエストContent-Type** | `multipart/form-data`（ライセンスファイル添付時）または`application/json` |
| **送信前バリデーション** | フィールド全体のバリデーション（Zodスキーマ）。ロール=出品者の場合、ライセンスファイルバリデーション。 |
| **処理ステップ** | 1. メールアドレスの形式と一意性を検証。2. パスワード強度を検証。3. ロール=出品者の場合、ライセンスファイル（PDF、license.pdf命名、≤10MB）を検証。4. Argon2でパスワードをハッシュ化。5. ライセンスファイルをストレージにアップロード。6. license_url付きユーザーレコードを作成。7. ユーザーDTOを返却（パスワードを除く）。8. USER_REGISTEREDイベントをログ。 |
| **成功レスポンス** | 201 Created（ユーザーデータ、出品者のlicenseUrl含む） |
| **後アクション** | ログインページにリダイレクト |

### 6.2 操作：ユーザーログイン

| 属性 | 仕様 |
|------|------|
| **トリガー** | ログインフォームの「ログイン」ボタンクリック |
| **APIエンドポイント** | `POST /api/v1/auth/login` |
| **リクエストContent-Type** | `application/json` |
| **送信前バリデーション** | メールアドレス形式、パスワード非空 |
| **処理ステップ** | 1. メールアドレスでユーザーを検索。2. isActiveを確認。3. Argon2でパスワードを検証。4. レート制限を確認。5. アクセストークンを生成（15分）。6. リフレッシュトークンを生成（7日）。7. リフレッシュトークンをハッシュ化して保存。8. httpOnlyクッキーを設定。9. アクセストークン＋ユーザーDTOを返却。10. USER_LOGIN_SUCCESSイベントをログ。 |
| **成功レスポンス** | 200 OK（accessTokenおよびuser付き） |
| **後アクション** | ホームページにリダイレクト |

### 6.3 操作：トークン更新

| 属性 | 仕様 |
|------|------|
| **トリガー** | アクセストークン期限切れ時、または手動リフレッシュ |
| **APIエンドポイント** | `POST /api/v1/auth/refresh` |
| **リクエストContent-Type** | なし（クッキーから読み取り） |
| **送信前バリデーション** | クッキーにリフレッシュトークンが存在する |
| **処理ステップ** | 1. クッキーからリフレッシュトークンを読み取り。2. JWT署名を検証。3. ハッシュでトークンレコードを検索。4. 無効化されていない、期限切れでない、絶対制限内であることを検証。5. トークンファミリーを確認（リユース検知）。6. 古いトークンを無効化。7. 新しいアクセストークンを生成。8. 新しいリフレッシュトークンを生成（同じファミリー）。9. 新しいトークンをハッシュ化して保存。10. 新しいhttpOnlyクッキーを設定。11. 新しいアクセストークンを返却。12. TOKEN_REFRESHEDイベントをログ。 |
| **成功レスポンス** | 200 OK（新しいaccessToken付き） |
| **エラーレスポンス** | 401 Unauthorized（さまざまな理由） |

### 6.4 操作：ユーザーログアウト

| 属性 | 仕様 |
|------|------|
| **トリガー** | UIからの「ログアウト」アクション |
| **APIエンドポイント** | `POST /api/v1/auth/logout` |
| **リクエストヘッダー** | `Authorization: Bearer <accessToken>` |
| **送信前バリデーション** | 有効なアクセストークン |
| **処理ステップ** | 1. アクセストークンを検証。2. ペイロードからjtiを抽出。3. 残りTTLでRedisブラックリストにjtiを追加。4. リフレッシュトークンを無効化。5. 204 No Contentを返却。6. USER_LOGOUTイベントをログ。 |
| **成功レスポンス** | 204 No Content |
| **後アクション** | クライアント側トークンをクリアし、ログインページにリダイレクト |

### 6.5 操作：トークン検証

| 属性 | 仕様 |
|------|------|
| **トリガー** | アプリ読み込み、または保護ルートへのアクセス |

## 10. 権限とアクセス制御

### 10.1 認証要件

- JSON Web Token（JWT）Bearerトークンが保護エンドポイントの`Authorization`ヘッダーで渡される。
- リフレッシュトークンはセッション管理用にhttpOnlyクッキーに保存される。

### 10.2 公開 vs 保護エンドポイント

| エンドポイント | アクセスレベル | 説明 |
|--------------|--------------|------|
| `POST /auth/register` | 公開 | 認証不要（出品者の場合、ライセンスファイルアップロード含む） |
| `POST /auth/login` | 公開 | 認証不要 |
| `POST /auth/refresh` | Cookieベース | クッキーに有効なリフレッシュトークンが必要 |
| `POST /auth/logout` | 保護 | 有効なアクセストークンが必要 |
| `GET /auth/verify` | 保護 | 有効なアクセストークンが必要 |

### 10.3 ロールベースアクセス

| ロール | 登録可能 | ログイン可能 | 登録時の追加要件 | デフォルトダッシュボード |
|--------|:--------:|:-----------:|----------------|------------------------|
| `buyer` | ✓ | ✓ | なし | ホームページ |
| `merchant` | ✓ | ✓ | 事業許可書PDFアップロード必須 | 出品者ダッシュボード |
| `admin` | ✗（シード済み） | ✓ | — | 管理者ダッシュボード |

### 10.4 セキュリティ監査ログ

| イベント | ログデータ | 保持期間 |
|---------|-----------|---------|
| `USER_REGISTERED` | userId、email、ip、timestamp、role | 90日 |
| `LICENSE_UPLOADED` | userId、filename、fileSize、ip、timestamp | 90日 |
| `LICENSE_VALIDATION_FAILED` | filename、error、ip、timestamp | 30日 |
| `USER_LOGIN_SUCCESS` | userId、email、ip、timestamp | 90日 |
| `USER_LOGIN_FAILED` | email、ip、timestamp、reason | 30日 |
| `USER_LOGOUT` | userId、timestamp | 90日 |
| `TOKEN_REFRESHED` | userId、timestamp | 90日 |
| `SECURITY_VIOLATION` | userId、ip、timestamp、details | 1年 |

## 11. リアルタイム通知動作

### 11.1 現在の実装

サインアップ/ログイン画面は未認証状態で動作するため、WebSocket接続は不要。

### 11.2 ログイン後のWebSocket接続

ログイン成功後、フロントエンドはWebSocket接続を確立：

| イベント | トリガー | アクション |
|---------|---------|-----------|
| `connect` | ログイン成功 | ユーザー固有のルームに参加 |
| `statusUpdate` | 注文/ステータス変更 | トースト通知を表示 |
| `disconnect` | 接続切断 | バックオフ付き自動再接続 |

## 13. 非機能要件

### 13.1 パフォーマンス要件

| 指標 | ターゲット |
|------|-----------|
| ページロード（初期表示） | ≤ 2秒 |
| ログインAPIレスポンス | ≤ 500ミリ秒 |
| 登録APIレスポンス | ≤ 1秒 |
| ライセンスファイルアップロード | ≤ 3秒（10MB PDF） |
| トークン更新レスポンス | ≤ 200ミリ秒 |
| パスワードハッシュ化（Argon2） | ≤ 1秒 |

### 13.2 セキュリティ考慮事項

| 懸念事項 | 対策 |
|---------|------|
| ブルートフォース攻撃 | レート制限（IPあたり300秒間に5回） |
| パスワード盗難 | Argon2idハッシュ化（メモリーハード、GPU耐性） |
| トークン盗難 | httpOnlyクッキー、Secureフラグ、SameSite=Strict |
| セッションハイジャック | トークンローテーション、ファミリー追跡、リユース検知 |
| CSRF | SameSiteクッキー、CORS制限 |
| 悪意のあるファイルアップロード | PDFのみバリデーション、ファイルサイズ制限（10MB）、ファイル名バリデーション（license.pdf） |

### 13.3 レスポンシブデザイン要件

| ブレークポイント | レイアウト |
|----------------|-----------|
| デスクトップ（≥ 1024px） | セントリックカード、最大幅400px |
| タブレット（768px – 1023px） | セントリックカード、パディング付きフル幅 |
| モバイル（< 768px） | フル幅カード、スタックレイアウト |

## 14. 設定項目（外部定義）

`.env`設定で定義：

| 定義キー | デフォルト値 | 説明 |
|---------|-------------|------|
| `JWT_ACCESS_SECRET` | （必須） | アクセストークン署名用シークレット |

| `JWT_ACCESS_EXPIRY` | `15m` | アクセストークン有効期限 |
| `JWT_REFRESH_EXPIRY` | `7d` | リフレッシュトークン有効期限 |
| `JWT_ABSOLUTE_LIMIT_DAYS` | `90` | 最大セッション期間（日） |
| `ARGON2_MEMORY_COST` | `65536` | Argon2メモリコスト（KB、64MB） |
| `ARGON2_TIME_COST` | `3` | Argon2反復回数 |
| `ARGON2_PARALLELISM` | `4` | Argon2並列スレッド数 |
| `RATE_LIMIT_LOGIN` | `5` | ウィンドウあたりの最大ログイン試行回数 |
| `RATE_LIMIT_WINDOW` | `300` | レート制限ウィンドウ（秒） |
| `LICENSE_MAX_SIZE` | `10485760` | ライセンスファイル最大サイズ（バイト、10MB） |
| `LICENSE_ALLOWED_TYPES` | `['application/pdf']` | ライセンスアップロード許可MIMEタイプ |
| `LICENSE_ALLOWED_FILENAME` | `license.pdf` | ライセンスアップロード必須ファイル名 |
| `LICENSE_STORAGE_PATH` | `./uploads/licenses` | アップロードされたライセンスファイル保存ディレクトリ |
