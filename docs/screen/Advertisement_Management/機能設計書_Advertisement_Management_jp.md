## 1. 機能概要

### 1.1 目的と範囲

本サブシステムは、Cosmetics Finder マーケットプレイス内のショップ広告のライフサイクル全体を管理します。広告プロセスは6つのステップ構成です：**1・パッケージ選択 → 2・コンテンツアップロード（画像＋テキスト）→ 3・料金支払い → 4・管理者審査 → 5・承認 → 6・掲載**。マーチャントは管理者が作成した広告パッケージを閲覧し、パッケージを選択して下書き広告を作成し、広告コンテンツ（タイトル、内容、画像、告知メッセージ）をアップロードし、広告料金を支払い、管理者の審査のために広告を提出します。管理者は理由付きで広告を承認・却下し（却却時には自動返金）、支払済・承認済・スケジュール内の広告のみがストアフロントにプラットフォーム全体で表示されます（バナー/画像＋告知メッセージ）。却却された広告は、マーチャントが編集して再提出できます。

広告管理サブシステムは、管理者が管理するパッケージモデルを通じて、マーチャントの販促意図と購入者の視認性を結び付けます。広告パッケージは管理者によって `ad_fee_settings` に定義され、各パッケージは掲載場所、料金プラン、日額、表示期間（`duration_days`）を定義します。料金は `日額 × 表示日数` で算出されます。マーチャントがパッケージを選択すると、下書き広告レコードが `approval_status = pending` かつ `payment_status = pending` で作成されます。マーチャントは広告コンテンツ（画像＋テキスト）をアップロードし、支払いが完了すると広告は管理者審査の `PENDING_APPROVAL` に入ります。アクティブでスケジュール内の承認済み広告は、キャッシュ可能なエンドポイントを通じて公開ストアフロントに配信され、一貫したバナー描画が保証されます。プラットフォーム全体で週あたり最大5件のアクティブ広告が強制されます。ストアフロントスライダーは、1回転あたり最大5件の広告を表示し、料金プランの優先順序（Premium > Standard > Basic）順に並べ、同一プラン内ではラウンドロビンで回転し、5秒ごとに自動回転します。

### 1.2 機能の責務

このサブは、以下のコア機能領域を担います：

1. **パッケージ管理（管理者専用）** ― 管理者は `ad_fee_settings` 内の広告パッケージ（掲載場所 × 料金プラン）を作成、更新、無効化します。マーチャントはパッケージの作成・編集・無効化ができません。
2. **パッケージ選択（マーチャント）** ― マーチャントは管理者が作成したパッケージカタログ（`GET /ads/packages`）を閲覧し、パッケージを選択します。選択により、マーチャントのショップにリンクされた下書き広告レコードが作成されます。この段階では支払いは行われません。
3. **広告コンテンツアップロード（マーチャント）** ― パッケージ選択後、マーチャントは広告コンテンツとして `title`、`content`（テキスト説明）、`image_url`（バナー画像）、`link_url`（クリックスルーリンク）、`announcement_message` をアップロードします。これにより広告は `DRAFT` から `CONTENT_UPLOADED` に遷移します。
4. **広告料金支払い（マーチャント）** ― 広告料金はコンテンツアップロード後の別ステップで請求されます。料金 = パッケージの `日額 × 表示日数`。支払いにより広告は `PENDING_APPROVAL` に遷移します。支払い取引は金額、ステータス、参照の情報とともに `ad_payments` に記録されます。
5. **広告管理（マーチャント）** ― マーチャントは自社の広告を閲覧、コンテンツ編集、掲載/非掲載切り替え、論理削除（無効化）することができます。また、却下された広告は編集後に再提出できます。
6. **管理者承認ワークフロー** ― 支払い後、広告は `PENDING_APPROVAL` に入ります。管理者は理由付きで承認または却下します。却下された広告は自動返金が発生し、マーチャントは編集して再提出できます。
7. **週間広告上限** ― プラットフォーム全体で週あたり最大5件（月曜 00:00 から 日曜 23:59 UTC）のアクティブ広告が強制され、広告の掲載承認前に検証されます。
8. **パッケージ定義の表示期間** ― 表示期間は選択したパッケージの `duration_days` で固定されます（カタログは掲載場所をまたいで7〜30日）。レート解決時に検証されます。
9. **広告料金設定管理** ― 管理者は `ad_fee_settings` でパッケージカタログ全体を管理します：新規パッケージ作成、日額更新、パッケージ無効化。すべてのレート変更は `ad_fee_history` に記録され、変更後に選択されるパッケージにのみ適用されます。
10. **ステータス制御** ― マーチャントから見えるライフサイクル（掲載中/期限切れ）は `is_active`、`approval_status`、`payment_status`、スケジュールから導出されます。マーチャントは `is_active` を直接切り替えられます。
11. **ソフト保持（Soft Retention）** ― 広告レコードは履歴のために保持されます。マーチャントの削除は `is_active = false` を設定します。管理者はパッケージを無効化してカタログに表示されないようにできます。
12. **プラットフォーム表示** ― 支払済・承認済・アクティブ・スケジュール内の広告は、ストアフロントのバナー・告知メッセージ描画用の公開エンドポイントを通じて公開されます。ストアフロントスライダーは1回転あたり最大5件を表示し、Premium > Standard > Basic の順で並べ、同一プラン内ではラウンドロビンで回転し、5秒ごとに自動回転します。期限切れ・却下広告は自動的に除外されます。
13. **キャッシュ管理** ― アクティブ広告はRedisに5分のTTLでキャッシュされます。キャッシュはあらゆる変更（コンテンツアップロード、支払い、管理者承認/却下、マーント編集/切り替え/削除、管理者パッケージ変更）で無効化されます。
14. **監査ログ** ― パッケージ変更、選択/支払い、コンテンツアップロード、承認アクションはすべて監査のために記録されます（マーチャント側イベント：90日間保持。管理者の承認/却下/料金変更イベント：開発ルール §6.4 に基づき2年間保持）。

### 1.3 対象ユーザー

| 属性 | 値 |
|-----------|-------|
| **主要アクター（マーチャント）** | 認証済みマーチャント。管理者作成パッケージの閲覧、パッケージ選択、広告コンテンツのアップロード、料金支払い、自社広告の管理、却下広告の再提出を行う |
| **主要アクター（管理者）** | 広告パッケージの作成・管理、購入済み広告の承認/却下を行う管理者 |
| **主要アクター（購入者）** | プラットフォームバナーを閲覧する認証済みまたは未認証の訪問者 |
| **必要な認証** | マーチャント・管理者操作には JWT ベアラートークン。アクティブ広告表示は公開 |
| **データ範囲** | マーチャント：自社ショップの広告のみ。購入者：全アクティブ広告（公開）。管理者：全広告。 |

## 2. ユースケースと業務ワークフロー

### 2.1 ユースケースカタログ

| UC-ID | ユースケース名 | 事前条件 | 事後条件 | トリガー主体 |

## 3. 状態遷移仕様

### 3.1 広告の表示状態

> **注記：** DATABASE_SPEC v2.5 は `approval_status` を `pending/approved/rejected` に制約しています。アプリケーションはコンテンツアップロード状態をコンテンツフィールド（title, announcement_message）で、支払い状態を `payment_status` で追跡します。

| 状態 | 説明 | 購入者に表示 | 編集可 | 削除可 |
|-------|------|:---:|:---:|:---:|
| `PENDING`（コンテンツなし） | パッケージ選択済み。コンテンツ未アップロード。`payment_status = pending` | ✗ | ✓ | ✓ |
| `PENDING`（コンテンツアップロード済み） | コンテンツアップロード済み。`payment_status = pending` | ✗ | ✓ | ✓ |
| `PENDING`（支払済み） | コンテンツアップロード済み。`payment_status = completed`。管理者審査待ち | ✗ | ✗ | ✗ |
| `APPROVED` | `approval_status = approved`、`payment_status = completed` | スケジュールと `is_active` に依存 | ✗ | ✗ |
| `REJECTED` | `approval_status = rejected`（返金処理済み） | ✗ | ✓（再提出） | ✓ |
| `SCHEDULED` | 承認済み、`is_active = true` かつ `starts_at > now` | ✗ | ✓（切替可） | ✓ |
| `ACTIVE` | 承認済み、`is_active = true`、`starts_at <= now <= expires_at` | ✓ | ✓（切替可） | ✓ |
| `INACTIVE` | `is_active = false`（マーチャント管理の非表示状態） | ✗ | ✓（切替可） | ✓ |
| `EXPIRED` | `expires_at < now` | ✗ | ✗ | ✗ |

> **広告状態フロー（M-AD-010、DATABASE_SPEC v2.5 に合わせて修正）：** `pending(コンテンツなし) → pending(コンテンツアップロード済み) → pending(支払済み) → approved → active → expired`
> 承認段階で却下された広告 → 料金を自動返金 → マーチャントが編集して再提出 → `pending` に戻る

### 3.2 承認状態（`approval_status`）

> **注記：** DATABASE_SPEC v2.5 は `approval_status` を `pending/approved/rejected` のみに制約しています。`draft` と `content_uploaded` 状態はアプリケーションレベルの概念であり、`payment_status` とコンテンツフィールドで管理されます。

| 状態 | DB値 | 説明 | 遷移可能先 |
|-------|----------|-------------|-------------------|
| `PENDING` | `'pending'` | 広告作成済み（パッケージ選択）。コンテンツアップロード、支払い、管理者審査を待つ | → `approved`, `rejected` |
| `APPROVED` | `'approved'` | 管理者が承認。支払済・アクティブ・スケジュール内なら表示可能 | → （承認後の却下は不可） |
| `REJECTED` | `'rejected'` | 管理者が理由付きで却下。返金は自動処理。マーチャントは再提出可 | → `pending`（編集後の再提出時） |

### 3.3 支払い状態（`payment_status`）

> **注記：** DATABASE_SPEC v2.5 は `payment_status` を `pending/completed/refunded` のみに制約しています。

| 状態 | DB値 | 説明 | 遷移可能 |
|-------|------|-------------|-------------------|
| `PENDING` | `'pending'` | 広告料金が未払い | → `completed` |
| `COMPLETED` | `'completed'` | 料金支払済・検証済み。管理者承認の前に必要 | → `refunded` |
| `REFUNDED` | `'refunded'` | 却下時に自動返金済み | → `pending`（再提出時） |

### 3.4 広告ライフサイクルの遷移

> **注記：** DATABASE_SPEC v2.5 は `approval_status` を `pending/approved/rejected` に制約しています。アプリケーションはコンテンツアップロード状態をコンテンツフィールドで、支払い状態を `payment_status` で追跡します。

| 遷移ID | 遷移元 | 遷移先 | トリガーアクション | ガード条件 |
| --- | --- | --- | --- | --- |
| TR-AD-01 | — | `PENDING`（コンテンツなし） | マーチャントが管理者作成パッケージを選択 | 有効なパッケージ（`ad_fee_settings` アクティブ）、ショップ承認済み。`approval_status = pending`、`payment_status = pending`、`starts_at = NULL`、`expires_at = NULL` |
| TR-AD-02 | `PENDING`（コンテンツなし） | `PENDING`（コンテンツアップロード済み） | マーチャントがコンテンツをアップロード（title, content, image, announcement） | コンテンツフィールドを検証。`starts_at` はマーチャントが設定、`expires_at` は導出 |
| TR-AD-03 | `PENDING`（コンテンツアップロード済み） | `PENDING`（支払済み） | マーチャントが料金を支払う | 有効なスケジュール（`expires_at = starts_at + duration_days`）、支払い成功。`payment_status = completed`、`week_number` 導出 |
| TR-AD-04 | `PENDING`（支払済み） | `APPROVED` | 管理者が承認 | 対象週の週間上限 ≤ 5（マーチャント単位） |
| TR-AD-05 | `PENDING`（支払済み） | `REJECTED` | 管理者が理由付きで却下 | 理由必須。返金を自動処理 |
| TR-AD-06 | `REJECTED` | `PENDING` | マーチャントが編集して再提出（新たな料金を支払う） | コンテンツを更新。支払い成功 |
| TR-AD-07 | `APPROVED` | `SCHEDULED` | 開始時刻が未到達 | システム時刻チェック |
| TR-AD-08 | `SCHEDULED` | `ACTIVE` | 開始時刻に到達 | システム時刻チェック |
| TR-AD-09 | `ACTIVE` | `EXPIRED` | 終了時刻を経過 | システム時刻チェック |
| TR-AD-10 | `ACTIVE` / `SCHEDULED` | `INACTIVE` | マーチャントが掲載をOFFに切り替え | マーチャントが広告を所有 |
| TR-AD-11 | `INACTIVE` | `ACTIVE` / `SCHEDULED` | マーチャントが掲載をONに切り替え | マーチャントが広告を所有、スケジュール内 |
| TR-AD-12 | `PENDING` / `INACTIVE` | （削除） | マーチャントが広告を論理削除 | `is_active = false`。レコードを保持 |
| TR-AD-13 | `EXPIRED` | — | — | 終端。再実行するには新しいパッケージを選択 |

### 3.5 キャッシュ状態（Redis `cache:ads:active`）

| 状態 | 説明 | TTL | 動作 |
|-------|------|:---:|------|
| `CACHE_COLD` | アクティブ広告一覧がキャッシュされていない | — | DB へクエリ（approved, paid, active, in-schedule）、キャッシュをシード（5分TTL） |
| `CACHE_WARM` | キャッシュされたアクティブ広告一覧が利用可能 | 5分 | キャッシュレスポンスを返す |
| `CACHE_INVALIDATED` | 変更が発生（作成/更新/削除/コンテンツアップロード/支払い/承認/却下） | — | `DEL cache:ads:active`、次回リクエストで再クエリ |

> **設計注記 ― 掲載場所/料金プランの永続化ギャップ：** DATABASE_SPEC v2.5 の `advertisements` テーブルは `placement` や `tier`（購入したパッケージ）を永続化しません。掲載場所と料金プランは選択時に選択したパッケージから取得され、料金解決（`日額 × 表示日数`）と `payment_amount` スナップショットに使用されますが、表示の順序付けや掲載場所ごとの容量チェック（`max_ads`）にはクエリできません。**推奨フォローアップ：** 購入したパッケージを永続化するスキーマ移行（例：`advertisements` に `placement`/`tier` 列を追加、または `ad_fee_setting_id` 外部キー）を行い、BR-AD-055 の順序付けと BR-AD-053 の容量強制をサーバー側で実装できるようにします。それまでの間、`GET /ads/active` は `created_at DESC` 順に広告を返し、料金プランに基づく優先順位付けはパッケージコンテキストが利用可能な場合にのみクライアント側で適用されます。

## 6. 機能操作仕様

> **v2.5 運用モデル：** マーチャントは6ステップの広告フローを実行します：パッケージ選択 → コンテンツアップロード → 料金支払い → 管理者審査 → 承認 → 掲載。パッケージ選択により下書き広告が作成され、コンテンツアップロードは別ステップ、支払いは広告を `PENDING_APPROVAL` にする別ステップです。マーチャントはコンテンツの編集、掲載/非掲載の切り替え、論理削除、却下広告の再提出もできます。
>
> **実装状況（2026-08-25時点）：** 管理者側操作は `backend/src/modules/admin/advertisement-management/` に実装済み。マーチャント側操作（`backend/src/modules/merchant/advertisements/`）は本仕様に従って実装される予定。

### 6.1 操作：広告パッケージの選択

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | パッケージカードの「選択」ボタンのクリック（§5.3） |
| **APIエンドポイント** | `POST /api/v1/ads/packages/:feeSettingId/select` |
| **リクエストContent-Type** | `application/json`（空ボディまたは任意の `paymentReference`） |
| **送信前検証** | JWTマーチャントロール。アクティブな料金設定が存在。ショップ承認済み |
| **処理ステップ** | 1. `:feeSettingId` をUUID形式として検証。2. JWTトークンとマーチャントロールを検証。3. マーチャントのショップを解決（GET /shops/merchant）。4. ショップが存在し `is_approved = true` であることを確認。**ショップが未承認の場合は `403 SHOP_NOT_APPROVED` を返す。** 5. `ad_fee_settings` でIDによりアクティブパッケージを検索。見つからないか非アクティブの場合は `404 NOT_FOUND` / `400 AD_PACKAGE_INVALID` を返す。6. トランザクション内で：ショップにリンクされた広告レコードを `approval_status = pending`、`payment_status = pending`、`is_active = true`、コンテンツなし、スケジュールなし、パッケージ料金 `日額 × 表示日数` を参照として保存して作成。7. パッケージカタログキャッシュを無効化。8. `AD_SELECTED` 監査イベントを記録。9. 作成した広告DTOを返す（`201 Created`）。 |
| **成功レスポンス** | 201 Created、広告データ付き（下書き状態） |
| **事後アクション** | 新しく作成した下書き広告用にコンテンツアップロードダイアログ（§5.2）を開く |

### 6.2 操作：広告コンテンツのアップロード

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | コンテンツアップロードダイアログでの「保存して次へ」ボタンのクリック（§5.2）または編集ダイアログの「保存」（§5.5） |
| **APIエンドポイント** | `PATCH /api/v1/ads/:id/content` |
| **リクエストContent-Type** | `multipart/form-data`（画像アップロード用）または `application/json` |
| **送信前検証** | JWTマーチャントロール。広告がマーチャントのショップに属する。広告が `DRAFT` または `CONTENT_UPLOADED` または `REJECTED` 状態 |
| **処理ステップ** | 1. `:id` をUUID形式として検証。2. JWTトークンとマーチャントロールを検証。3. 広告を検索。所有権を確認（`shop_id` がマーチャントのショップと一致）。4. 広告状態がコンテンツアップロードを許可していることを確認（`DRAFT`、`CONTENT_UPLOADED`、または `REJECTED`）。5. コンテンツフィールドを検証：`title`（必須、1〜200文字）、`announcementMessage`（必須、最大500文字）、`content`（任意）、`linkUrl`（任意、有効なURL）。6. ファイルアップロードで `imageUrl` が提供された場合：MIMEタイプ（JPG/PNG/WebP）を検証、サイズ（≤ 5MB）を検証、UUIDファイル名を生成、webroot外に保存、`image_url` を設定。7. リクエストから `starts_at` を設定。8. `expires_at = starts_at + パッケージ duration_days`（選択時の広告パッケージから解決）を導出。9. `expires_at > starts_at` を検証。10. 広告を更新：`title`、`content`、`image_url`、`link_url`、`announcement_message`、`starts_at`、`expires_at` を設定。`approval_status` は `'pending'` のまま（変更なし）。11. `AD_CONTENT_UPLOADED` 監査イベントを記録。12. 更新した広告DTOを返す。 |
| **成功レスポンス** | 200 OK、更新された広告データ付き |
| **事後アクション** | ダイアログが閉じ、広告カードで料金支払いボタンが利用可能になる |

### 6.3 操作：広告料金の支払い

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | 支払い確認ダイアログでの「支払い＆送信」ボタンのクリック（§5.4） |
| **APIエンドポイント** | `POST /api/v1/ads/:id/pay` |
| **リクエストContent-Type** | `application/json`（`paymentReference` 任意） |
| **送信前検証** | JWTマーチャントロール。広告がマーチャントのショップに属する。広告が `CONTENT_UPLOADED` 状態。コンテンツとスケジュールが検証済み |
| **処理ステップ** | 1. `:id` をUUID形式として検証。2. JWTトークンとマーチャントロールを検証。3. 広告を検索。所有権と、広告がコンテンツをアップロード済み（`content IS NOT NULL AND image_url IS NOT NULL`）であること、かつ `payment_status = 'pending'` であることを確認。4. パッケージから料金 = `日額 × 表示日数` を解決。5. 単一トランザクション内で：支払いを処理（スタブ）。取引を `ad_payments` に記録（`payment_status = completed`、`amount`、`payment_method`、`transaction_id`、`paid_at`）。広告を更新：`payment_status = completed`。`approval_status` は `'pending'` のまま（変更なし）。`payment_amount`、`payment_reference` を設定し、`starts_at` から `week_number` を導出。6. アクティブ広告キャッシュを無効化（`DEL cache:ads:active`）。7. `AD_PAID` 監査イベントを記録。8. 承認待ちを管理者に通知。9. 更新した広告DTOを返す。 |
| **成功レスポンス** | 200 OK、更新された広告データ付き（PENDING_APPROVAL状態） |
| **事後アクション** | 広告がマーチャント一覧に PENDING_APPROVAL として表示。料金支払いボタンは非表示 |

## 7. 入出力定義

### 7.1 入力定義 ― パッケージ選択（マーチャント）

| フィールド | 表示名（EN） | 表示名（JA） | データ型と長さ | 必須 | 入力制御 | 検証 |
|-------|-------------------|-------------------|-------------------|:--------:|---------------|------------|
| `feeSettingId` | Package | 広告パッケージ | UUID（パスパラメータ） | はい | 選択ボタン | `@IsUUID()`。アクティブな `ad_fee_settings` レコードに解決されなければならない |

### 7.2 入力定義 ― 広告コンテンツのアップロード（マーチャント）

| フィールド | 表示名（EN） | 表示名（JA） | データ型と長さ | 必須 | 入力制御 | 検証 |
|-------|-------------------|-------------------|-------------------|:--------:|---------------|------------|
| `title` | Title | タイトル | VARCHAR(200) | はい | 入力（テキスト） | `@IsString()`、`@IsNotEmpty()`、`@MaxLength(200)` |
| `content` | Content | 内容 | TEXT | いいえ | テキストエリア | `@IsString()`、`@IsOptional()` |
| `image` | Image | 画像 | ファイル（バイナリ） | いいえ | ファイルアップロード | MIME: `image/jpeg`、`image/png`、`image/webp`。最大5MB |
| `linkUrl` | Link URL | リンクURL | VARCHAR(2048) | いいえ | 入力（url） | `@IsUrl()`、`@IsOptional()`、`@MaxLength(2048)` |
| `announcementMessage` | Announcement Message | 告知メッセージ | VARCHAR(500) | はい | テキストエリア | `@IsString()`、`@IsNotEmpty()`、`@MaxLength(500)` |
| `startsAt` | Start Date | 開始日 | DATE | はい | 日付ピッカー | `@IsDateString()`。今日以上でなければならない |

> `expiresAt` は選択したパッケージの `starts_at + duration_days` としてサーバー側で導出され、マーチャント入力ではありません。`approval_status`、`payment_status`、`payment_amount`、`payment_reference`、`week_number`、`approved_by`、`approved_at`、`rejection_reason` はシステム管理です。

### 7.3 入力定義 ― 料金の支払い（マーチャント）

| フィールド | 表示名（EN） | 表示名（JA） | データ型と長さ | 必須 | 入力制御 | 検証 |
|-------|-------------------|-------------------|-------------------|:--------:|---------------|------------|
| `paymentReference` | Payment Reference | 支払い参照 | VARCHAR(100) | いいえ | （非表示、ゲートウェイスタブ） | `@IsString()`、`@IsOptional()`、`@MaxLength(100)` |

### 7.4 入力定義 ― 一覧クエリ

| フィールド | 表示名（EN） | データ型 | 必須 | 入力制御 | 検証 |
|-------|-------------------|-----------|:--------:|---------------|------------|
| `page` | Page | 数値 | いいえ | ページネーション | `@IsInt()`、`@Min(1)`、デフォルト1 |
| `limit` | Limit | 数値 | いいえ | ページネーション | `@IsInt()`、`@Min(1)`、`@Max(100)`、デフォルト20 |
| `status` | Status | 文字列 | いいえ | セレクト | `@IsIn(['active', 'inactive', 'expired'])`、`@IsOptional()` |
| `approvalStatus` | Approval Status | 文字列 | いいえ | セレクト | `@IsIn(['pending', 'approved', 'rejected'])`、`@IsOptional()` |

### 7.5 入力定義 ― 管理者アクション

| エンドポイント | フィールド | データ型 | 必須 | 検証 |
|----------|-------|-----------|:--------:|------------|
| `PATCH /admin/ads/:id/reject` | `reason` | 文字列 | はい | `@IsString()`、`@IsNotEmpty()`、`@MaxLength(2000)` |

### 8.5 検証の適用層

1. **フロントエンド（クライアント）**：React Hook Form + Zodスキーマ検証を全フォーム（パッケージ選択、コンテンツアップロード、支払い、編集）に適用。
2. **バックエンド（サーバー）**：全エンドポイントで NestJS ValidationPipe + class-validator DTO。パッケージ解決、ショップ承認、コンテンツ検証、支払い、承認/週間上限ルール、サーバー側の `expires_at` 導出のためのサービスレベルのチェック。
3. **データベース（PostgreSQL）**：最終ガードとしての CHECK 制約 `chk_advertisements_dates`、`chk_advertisements_approval_status`、`chk_advertisements_payment_status`。

### 9.1 エラーレスポンス構造


### 9.2 エラー分類表 ― 広告操作

| HTTPステータス | エラーコード | シナリオ | ユーザー向け動作 |
|-------------|------------|----------|---------------------|
| `400` | `BAD_REQUEST` | 検証失敗（`title`、`announcementMessage` の欠落、不正な画像など） | フィールドレベルのインラインエラー＋上部バナー |
| `401` | `UNAUTHORIZED` | JWTの欠落または無効 | ログインへリダイレクト |
| `403` | `FORBIDDEN` | マーチャント/管理者でない、広告所有者でない | "You don't have permission to manage this ad" |
| `403` | `SHOP_NOT_APPROVED` | 保留中マーチャントがパッケージ選択を試行 | "Your shop is pending approval. You cannot select an advertising package until your shop is approved." |
| `404` | `NOT_FOUND` | 広告が見つからない。選択したパッケージが見つからない | 更新オプション付きで "Advertisement not found" |
| `409` | `CONFLICT` | `expires_at <= starts_at`（DBガード） | "Invalid schedule dates" |
| `409` | `WEEKLY_LIMIT_REACHED` | 承認時の週間広告上限（5件/週）到達 | "Weekly advertisement limit reached (max 5)" |
| `400` | `AD_PACKAGE_INVALID` | 選択した `feeSettingId` がアクティブな `ad_fee_settings` レコードに解決されない | "Selected advertising package is unavailable" |
| `400` | `AD_SCHEDULE_INVALID` | 導出されたスケジュールが無効（`expires_at` をパッケージ期間から導出できない） | "Advertisement schedule is invalid" |
| `413` | `PAYLOAD_TOO_LARGE` | 広告画像ファイル > 5MB | "Image file must not exceed 5MB" |
| `415` | `UNSUPPORTED_MEDIA_TYPE` | 不正な画像形式（JPG/PNG/WebP以外） | "Image must be JPG, PNG, or WebP format" |
| `422` | `UNPROCESSABLE_ENTITY` | 非保留広告の承認。支払い検証失敗 | "Payment failed. Please try again." |
| `429` | `TOO_MANY_REQUESTS` | レート制限超過 | "Too many requests. Please wait {seconds} seconds" |
| `500` | `INTERNAL_SERVER_ERROR` | サーバーエラー（支払い検証失敗を含む） | "Something went wrong. Please try again" |

### 9.3 フロントエンドのエラー表示動作

- **フィールドレベルの検証**：無効な入力の下に赤い枠とインラインテキスト。
- **フォームレベルのサマリー**：フォーム上部に全エラーを列挙した警告バナー。
- **トースト通知**：APIエラーと成功アクションに使用。
- **ローディング状態**：API呼び出し中の送信ボタンにスピナー。
- **空状態**：現在のフィルタ/検索に一致する広告がない場合に説明付きメッセージ。
- **確認ダイアログ**：パッケージ選択と削除には確認ダイアログが必要。

### 10.4 所有権の強制

```typescript
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles('merchant', 'admin')
@Controller('ads')
export class AdvertisementsController {
  // GET /packages        — 読み取り専用の管理者作成カタログ（merchant/admin）
  // POST /packages/:feeSettingId/select — merchant select（下書き広告を作成）
  // PATCH /:id/content   — merchant コンテンツのアップロード
  // POST /:id/pay        — merchant 料金の支払い
  // GET /                — 自社広告（merchant）、全広告（admin）
  // PATCH /:id           — merchant コンテンツの編集
  // DELETE /:id          — merchant 論理削除
  // PATCH /:id/toggle    — merchant 掲載/非掲載の切り替え

  @Public()
  @Get('active')
  findActive() { ... }
}

@UseGuards(JwtAuthGuard, RolesGuard)
@Roles('admin')
@Controller('admin')
export class AdminAdvertisementsController {
  // GET /ads, PATCH /ads/:id/approve, PATCH /ads/:id/reject,
  // GET /ad-fee-settings, POST /ad-fee-settings,
  // PATCH /ad-fee-settings/:id, DELETE /ad-fee-settings/:id  (admin only)
}
```

マーチャントは `shop_id` が自社のショップと一致する広告のみ管理できます。別のマーチャントの広告にアクセスしようとした場合、MUST で `403 Forbidden` を返します。管理者はパッケージカタログのライフサイクルを所有します。承認/却下エンドポイントは `admin` ロールのみが要求する MUST があります。

**保留中マーチャント制限：** `license_status` が `'pending'` または `'reject'` のマーチャントはパッケージカタログの閲覧と自社の購入一覧の閲覧（読み取り専用）はできますが、パッケージ選択では MUST で `shop.is_approved = true` を検証し、ショップが未承認の場合は `403 SHOP_NOT_APPROVED` を返します。フロントエンドは保留中マーチャントの選択アクションを無効化します。

## 11. リアルタイム通知動作

### 11.1 現在の実装

広告管理画面は WebSocket 接続を必要としません。広告ステータス（draft/content_uploaded/pending/approved/rejected、active/inactive/expired）はスケジュールデータから導出され、変更後の標準クエリ無効化（TanStack Query）により更新されます。

### 11.2 通知イベント

| イベント | トリガー | 受信者 | アクション |
|-------|---------|-----------|--------|
| `AD_SUBMITTED` | 支払い後、広告が `PENDING_APPROVAL` に入る | 管理者 | 承認待ちバッジ / 管理者ダッシュボードの通知 |
| `AD_APPROVED` | 管理者が広告を承認 | マーチャント | 通知＋広告が表示可能になる（キャッシュ更新 ≤ 5分） |
| `AD_REJECTED` | 管理者が広告を却下 | マーチャント | `rejection_reason` 付きの通知。返金処理。マーチャントは編集・再提出可能 |
| `AD_ACTIVATED` | 開始時刻に到達 | — | `cache:ads:active` の更新後にストアフロントに表示（最大5分） |
| `AD_EXPIRED` | `expires_at` を経過 | — | キャッシュ更新後にストアフロントから消える |
| `AD_MUTATED` | コンテンツアップロード / 支払い / マーチャント編集 / 切り替え / 削除 / 管理者パッケージ変更 | — | キャッシュは即時無効化。次の `GET /ads/active` でDBを再クエリ |

## 13. 非機能要件

### 13.1 パフォーマンス要件

| 指標 | 目標値 |
|--------|--------|
| 広告一覧ページの読込 | ≤ 2秒 |
| パッケージカタログの読込 | ≤ 2秒 |
| コンテンツアップロードAPI | ≤ 2秒（画像アップロード時間を除く） |
| 料金支払いAPI | ≤ 2秒 |
| 広告の承認/却下API | ≤ 1秒 |
| アクティブ広告API（キャッシュヒット） | ≤ 100ミリ秒 |
| アクティブ広告API（キャッシュミス） | ≤ 500ミリ秒 |

### 13.2 キャッシュ戦略

| キャッシュキー | TTL | 無効化トリガー |
|-----------|-----|---------------------|
| `cache:ads:active` | 5分 | コンテンツアップロード、支払い、承認/却下、マーチャント編集/切り替え/削除、管理者パッケージ変更 |
| `cache:ads:packages` | 10分 | 管理者パッケージの作成/更新/無効化（レート変更） |

### 13.3 画像最適化

| 要件 | 説明 |
|-------------|-------------|
| 形式 | サポートされる場合は WebP を配信、フォールバックとして JPEG |
| バナー寸法 | 標準バナーアスペクト比（例 4:1）とレスポンシブバリアント |
| CDN対応 | 画像URLは本番用にCDN互換であるべき |
| 圧縮 | 最適化・サイズ調整されたバリアントを配信してバナー読込重量を最小化 |

### 13.4 レスポンシブデザイン要件

| ブレークポイント | レイアウト |
|------------|--------|
| デスクトップ（≥ 1024px） | サイドバー、サムネイル付きカード一覧を持つ完全なダッシュボードレイアウト |
| タブレット（768px – 1023px） | サイドバーが折りたたまれ、広告カードが縦に積み重なる |
| モバイル（< 768px） | 単一列の広告カード、ダイアログはフルスクリーンシートに |

### 13.5 アクセシビリティ要件

| 要件 | 実装 |
|-------------|---------------|
| WCAG 2.1 AA | セマンティックHTML、全インタラクティブ要素にARIAラベル |
| キーボード操作 | 広告カード、ツールバー、ダイアログフィールドを通るタブ順 |
| スクリーンリーダー | 広告画像の代替テキスト、編集/削除/切り替えアクションのARIAラベル |
| 色のコントラスト | テキストは最小4.5:1、UIコンポーネント（ステータスバッジ）は3:1 |
| フォーカスインジケーター | 全インタラクティブ要素に可視フォーカスリング。ダイアログ内のフォーカストラップ |
