## 1. 機能概要

### 1.1 目的と適用範囲

本サブシステムは、Cosmetics Finder マーケットプレイス内のショップ広告のライフサイクル全体を管理する。マーチャントは、承認済みの自店舗に紐づくプロモーションバナー広告の作成、スケジュール設定、掲載料の支払い、管理者承認への提出、有効/無効化、管理を行うことができる。管理者は提出された広告を理由付きで承認または却下し、支払済みかつ承認済みかつ期間内の広告のみがストアフロント（バナー/画像＋告知メッセージ）でプラットフォーム全体に表示される。

広告管理サブシステムは、マーチャントのプロモーション意図と購入者の認知を結びつける。有効かつ期間内かつ承認済みの広告は、キャッシュ可能な公開エンドポイントを通じて一般ストアフロントに配信され、マーチャント側の管理操作を公開することなく、一貫したバナーレンダリングを実現する。プラットフォーム全体で週間の有効広告上限は5件に制限される。

### 1.2 機能責任（機能一覧）

本サブシステムは、以下の主要機能領域を担う。

1. **広告作成** — マーチャントは、タイトル、内容、告知メッセージ、任意の画像、任意のクリックスルーリンク、スケジュールを指定して広告を作成できる。
2. **広告スケジュール設定** — マーチャントは開始/終了日時を設定でき、広告はスケジュール期間内のみ表示される。
3. **広告画像アップロード** — マーチャントは広告画像（JPG、PNG、WebP、最大5MB）をアップロードでき、UUIDベースの命名で保存される。
4. **広告管理** — マーチャントは自社の広告を一覧・検索・絞り込み・編集・削除できる。
5. **広告掲載料の支払い** — マーチャントは承認提出前に広告掲載料を支払う必要がある。支払い取引は金額、ステータス、参照番号とともに記録される。
6. **管理者承認ワークフロー** — 支払い確認後、広告は `PENDING_APPROVAL` 状態となり、管理者が理由付きで承認または却下する。却下された広告は編集・再提出が可能。
7. **週間広告件数上限** — プラットフォーム全体で週間の有効広告は最大5件（月曜00:00〜日曜23:59 UTC）。表示承認前に検証される。
8. **ステータス管理** — マーチャント表示用のライフサイクル（予定/有効/無効/期限切れ）は、`is_active`、`approval_status`、`payment_status`、スケジュールから導出される。
9. **ソフト削除** — 広告を削除すると `is_active = false` に設定され、履歴のためにレコードは保持される。
10. **プラットフォーム表示** — 支払済み・承認済み・有効・期間内の広告は、ストアフロントでのバナーおよび告知メッセージ表示用に公開エンドポイントから配信される。
11. **キャッシュ管理** — 有効広告は Redis に5分間のTTLでキャッシュされ、いかなる変更時にもキャッシュが無効化される。
12. **監査ログ** — 広告のすべての変更および承認/支払いアクションは監査のため記録される（90日間保持）。

### 1.3 対象ユーザー

| 属性 | 値 |
|-----------|-------|
| **主要アクター（マーチャント）** | 認証済みマーチャント。自店舗の広告を作成・支払い・管理する |
| **主要アクター（管理者）** | 広告の承認/却下およびプラットフォーム全体の広告を管理する管理者 |
| **主要アクター（購入者）** | プラットフォームのバナーを閲覧する認証済みまたは未認証の訪問者 |
| **必要な認証** | マーチャント・管理者操作には JWT Bearer Token。有効広告表示は公開 |
| **データスコープ** | マーチャント：自店舗の広告のみ。購入者：すべての有効広告（公開）。管理者：すべての広告 |

### 1.5 入出力

| 入力情報 | データ区分 | 出典 / 説明 |
|-------------------|---------------|----------------------|
| `title` | ユーザー入力 | 広告タイトル（必須、最大200文字） |
| `content` | ユーザー入力 | 広告内容/説明（任意、最大5000文字） |
| `announcementMessage` | ユーザー入力 | バナー告知メッセージ（必須、最大500文字） |
| `imageUrl` | ファイルアップロード | 広告画像URL（JPG、PNG、WebP、最大5MB） |
| `linkUrl` | ユーザー入力 | クリックスルーリンクURL（任意） |
| `isActive` | ユーザー入力 | 広告の有効フラグ |
| `startsAt` | ユーザー入力 | スケジュール開始日時 |
| `expiresAt` | ユーザー入力 | スケジュール終了日時 |
| `paymentReference` | システム / ユーザー入力 | 広告掲載料の支払い取引参照番号 |
| `page` / `limit` / `status` / `approvalStatus` | クエリパラメータ | 一覧表示用のページネーションとステータス絞り込み |
| `id` | パスパラメータ | 更新/削除対象の広告ID（UUID） |

| 出力情報 | データ区分 | 送信先 / 説明 |
|--------------------|---------------|---------------------------|
| `advertisement` | Advertisement DTO | 広告の全データ（承認/支払いフィールドを含む） |
| `advertisements` | Advertisement[] DTO | ページネーション付き広告一覧 |
| `meta` | Pagination Meta | ページ、件数、総件数、総ページ数 |
| `activeAds` | Advertisement[] DTO | プラットフォーム表示用の有効・期間内・承認済み広告 |
| `pendingApprovalAds` | Advertisement[] DTO | 管理者の承認/却下待ち広告 |

## 2. ユースケースと業務ワークフロー

### 2.1 ユースケース一覧

| UC-ID | ユースケース名 | 事前条件 | 事後条件 | 起動アクター |
|-------|---------------|--------------|---------------|------------------|
| UC-AD-001 | 広告を作成する | マーチャントが認証済みであり、承認済みの店舗を持つ | `approval_status = pending`、`payment_status = pending` として、マーチャントの店舗に紐づく新しい広告レコードが `advertisements` テーブルに作成される | マーチャント |
| UC-AD-002 | 広告のスケジュールを設定する | マーチャントが認証済み。店舗が承認済み | 広告に有効な `starts_at` / `expires_at` スケジュールと導出された `week_number` が設定される | マーチャント |
| UC-AD-003 | 広告画像をアップロードする | マーチャントが認証済み。店舗が承認済み | 画像がUUID命名でアップロード・保存され、`image_url` が設定される | マーチャント |
| UC-AD-004 | 自社広告を一覧表示する | マーチャントが認証済み | 自社広告のページネーション付き一覧（ステータス/承認状態での絞り込み付き）が表示される | マーチャント |
| UC-AD-005 | 広告を更新する | マーチャントが認証済み。広告がマーチャントの店舗に属する | 広告レコードが更新される。却下済み広告の場合は `pending`（承認待ち）に戻る | マーチャント |
| UC-AD-006 | 広告を削除する（ソフト削除） | マーチャントが認証済み。広告がマーチャントの店舗に属する | 広告の `is_active` が false に設定される。有効広告キャッシュが無効化される | マーチャント |
| UC-AD-007 | 広告の有効/無効を切り替える | マーチャントが認証済み。広告がマーチャントの店舗に属する | 広告の表示可否が切り替わる | マーチャント |
| UC-AD-008 | 有効広告を表示する | なし（公開） | 支払済み・承認済み・有効・期間内の広告がストアフロント表示用に返される | 購入者/訪問者 |
| UC-AD-009 | 広告掲載料を支払う | マーチャントが認証済み。広告が作成済み（下書き） | 支払いが `payment_amount` / `payment_reference` とともに記録され、`payment_status` が `paid` に設定される | マーチャント / 支払いシステム |
| UC-AD-010 | 広告を承認申請に提出する | マーチャントが認証済み。広告の `payment_status = paid` | 広告が管理者レビュー用に `approval_status = pending` となる | マーチャント |
| UC-AD-011 | 広告を承認する | 管理者が認証済み。広告が承認待ちかつ支払済み | 週間上限が検証され、広告の `approval_status = approved`、`approved_by` / `approved_at` が設定され、キャッシュが無効化される | 管理者 |
| UC-AD-012 | 広告を却下する | 管理者が認証済み。広告が承認待ち | 広告の `approval_status = rejected`、`rejection_reason` が保存され、自動的に払い戻しが処理される | 管理者 |
| UC-AD-013 | 却下された広告を再提出する | マーチャントが認証済み。広告が却下済み | 却下済み広告が編集・再提出され、`approval_status` が `pending` に戻る | マーチャント |

## 3. 状態遷移仕様

### 3.1 広告の表示状態

| 状態 | 説明 | 購入者に表示 | 編集可能 | 削除可能 |
|-------|-------------|:-----------------:|:--------:|:----------:|
| `DRAFT` | `approval_status = pending`、`payment_status = pending` | ✗ | ✓ | ✓ |
| `PENDING_APPROVAL` | `payment_status = paid`、`approval_status = pending` | ✗ | ✗（却下済みの場合を除く） | ✓ |
| `APPROVED` | `approval_status = approved`、`payment_status = paid` | スケジュールと `is_active` に依存 | ✓ | ✓ |
| `REJECTED` | `approval_status = rejected`（払い戻し処理済み） | ✗ | ✓（再提出用） | ✓ |
| `SCHEDULED` | 承認済み、`is_active = true` かつ `starts_at > now` | ✗ | ✓ | ✓ |
| `ACTIVE` | 承認済み、`is_active = true`、`starts_at <= now <= expires_at` | ✓ | ✓ | ✓ |
| `INACTIVE` | `is_active = false`（非表示またはソフト削除） | ✗ | ✓ | ✓ |
| `EXPIRED` | `expires_at < now` | ✗ | ✓ | ✓ |

### 3.2 承認状態（`approval_status`）

| 状態 | DB値 | 説明 | 遷移許可 |
|-------|----------|-------------|-------------------|
| `PENDING` | `'pending'` | 管理者レビュー待ち（下書き、または支払済み/提出済み） | → `approved`、`rejected` |
| `APPROVED` | `'approved'` | 管理者が承認済み。支払済み・有効・期間内であれば表示可能 | →（承認後は却下不可） |
| `REJECTED` | `'rejected'` | 管理者が理由付きで却下。払い戻しは自動処理 | → `pending`（編集＋再提出） |

### 3.3 支払い状態（`payment_status`）

| 状態 | DB値 | 説明 | 遷移許可 |
|-------|----------|-------------|-------------------|
| `PENDING` | `'pending'` | 広告掲載料が未払い | → `paid`、`failed` |
| `PAID` | `'paid'` | 料金支払い済み・検証済み。承認提出の前提条件 | → `refunded` |
| `FAILED` | `'failed'` | 支払い試行が失敗 | → `pending`、`paid` |
| `REFUNDED` | `'refunded'` | 却下時に自動払い戻し済み | 終端状態 |

### 3.4 広告ライフサイクル遷移

| 遷移ID | 遷移元状態 | 遷移先状態 | トリガーアクション | ガード条件 |
|---------------|--------------|--------------|----------------|------------------|
| TR-AD-01 | — | `DRAFT` | 広告を作成（下書き） | データが有効、店舗が承認済み、告知メッセージ必須 |
| TR-AD-02 | `DRAFT` | `PENDING_APPROVAL` | 料金支払い＋承認申請に提出 | `payment_status = paid`。週間上限は承認時にチェック |
| TR-AD-03 | `PENDING_APPROVAL` | `APPROVED` | 管理者が承認 | 対象週の週間上限 ≤ 5件 |
| TR-AD-04 | `PENDING_APPROVAL` | `REJECTED` | 管理者が理由付きで却下 | 理由必須。払い戻しは自動処理 |
| TR-AD-05 | `REJECTED` | `PENDING_APPROVAL` | 編集＋再提出 | 広告がマーチャントに属する。新内容が有効 |
| TR-AD-06 | `APPROVED` | `SCHEDULED` | 開始時刻に未到達 | システム時刻チェック |
| TR-AD-07 | `SCHEDULED` | `ACTIVE` | 開始時刻に到達 | システム時刻チェック |
| TR-AD-08 | `ACTIVE` | `EXPIRED` | 終了時刻を経過 | システム時刻チェック |
| TR-AD-09 | `ACTIVE` | `INACTIVE` | 有効をオフに切り替え | 広告がマーチャントに属する |
| TR-AD-10 | `INACTIVE` | `ACTIVE` | 有効をオンに切り替え（期間内） | 広告がマーチャントに属する、広告が承認済み |
| TR-AD-11 | `ACTIVE` | `INACTIVE` | ソフト削除 | 広告がマーチャントに属する |
| TR-AD-12 | `EXPIRED` | `ACTIVE` | `expires_at` を延長 / 再スケジュール | 新しい日付範囲が有効 |

### 3.5 キャッシュ状態（Redis `cache:ads:active`）

| 状態 | 説明 | TTL | 挙動 |
|-------|-------------|:---:|----------|
| `CACHE_COLD` | 有効広告一覧のキャッシュなし | — | DBをクエリ（承認済み、支払済み、有効、期間内）、キャッシュを投入（TTL 5分） |
| `CACHE_WARM` | 有効広告一覧のキャッシュあり | 5分 | キャッシュ済みレスポンスを配信 |
| `CACHE_INVALIDATED` | 変更を実行（作成/更新/削除/承認/却下） | — | `DEL cache:ads:active`、次のリクエストで再クエリ |

### 4.2 広告スケジュールルール

| ルールID | ルール名 | 説明 | 適用レイヤー |
|---------|-----------|-------------|-------------------|
| BR-AD-008 | スケジュール必須 | `startsAt` と `expiresAt` の両方が必須 | バックエンド（DTOバリデーション） |

| BR-AD-025 | 週番号 | `week_number`（ISO週）は `starts_at` から導出され、週間上限追跡用に保存される | バックエンド（サービスロジック） |

## 6. 機能操作仕様

### 6.1 操作：広告を作成する（下書き）

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | 広告作成ダイアログの「Save Ad」ボタンクリック |
| **APIエンドポイント** | `POST /api/v1/ads` |
| **リクエストContent-Type** | `multipart/form-data`（画像添付時）または `application/json` |
| **提出前バリデーション** | 完全なDTOバリデーション（class-validator）＋ Zodスキーマ |
| **処理ステップ** | 1. JWTトークンとマーチャントロールを検証。2. マーチャントの店舗を特定（GET /shops/merchant）。3. 店舗の存在と `is_approved = true` を検証。4. すべてのフィールドを検証（タイトル、告知メッセージ、スケジュール、画像）。5. 画像をアップロード（指定された場合）。6. `starts_at` から `week_number` を導出。7. `shop_id`、`approval_status = pending`、`payment_status = pending` で広告レコードを作成。8. 有効広告キャッシュを無効化（`DEL cache:ads:active`）。9. `AD_CREATED` 監査イベントを記録。10. 作成された広告DTOを返す。 |
| **成功レスポンス** | 201 Created、広告データ付き |
| **後続アクション** | ダイアログを閉じ、広告一覧を更新し、成功トーストを表示。広告は「支払い＆提出」アクション付きの下書きとして表示 |

### 6.2 操作：広告掲載料を支払う

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | 下書き広告の「Pay Fee」ボタンクリック |
| **APIエンドポイント** | `POST /api/v1/ads/:id/pay` |
| **リクエストContent-Type** | `application/json`（支払い情報。支払いゲートウェイはスタブ実装） |
| **提出前バリデーション** | 広告の所有権チェック。広告が `payment_status = pending` であること |
| **処理ステップ** | 1. `:id` をUUID形式として検証。2. JWTトークンとマーチャントロールを検証。3. 広告を検索し、所有権を確認。4. 広告が未支払いであることを確認。5. `payment_amount`（設定可能な料金）で支払いを処理（スタブ）。6. `payment_status = paid`、`payment_amount`、`payment_reference` を記録。7. `AD_PAID` 監査イベントを記録。8. 更新された広告DTOを返す。 |
| **成功レスポンス** | 200 OK、更新された広告データ付き |
| **後続アクション** | 「承認申請に提出」ボタンを有効化。成功トーストを表示 |

### 6.3 操作：広告を承認申請に提出する

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | 「Submit for Approval」ボタンクリック（`payment_status = paid` が必要） |
| **APIエンドポイント** | `POST /api/v1/ads/:id/submit` |
| **リクエストContent-Type** | なし |
| **提出前バリデーション** | 広告の所有権チェック。`payment_status = paid` 必須 |
| **処理ステップ** | 1. `:id` をUUID形式として検証。2. JWTトークンとマーチャントロールを検証。3. 広告を検索し、所有権を確認。4. `payment_status = paid` を検証。5. `approval_status = pending` に設定（提出）。6. 有効広告キャッシュを無効化。7. 管理者に承認待ちを通知。8. `AD_SUBMITTED` 監査イベントを記録。9. 更新された広告DTOを返す。 |
| **成功レスポンス** | 200 OK、更新された広告データ付き |
| **後続アクション** | 管理者の判断まで広告はマーチャントにとって読み取り専用になる |

### 6.4 操作：管理者が広告を承認する

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | 管理者モデレーション画面の「Approve」ボタンクリック |
| **APIエンドポイント** | `POST /api/v1/admin/ads/:id/approve` |

| **提出前バリデーション** | 管理者ロール。広告が `approval_status = pending` |
| **処理ステップ** | 1. `:id` をUUID形式として検証。2. JWTトークンと管理者ロールを検証。3. 広告を検索し、`approval_status = pending` を確認。4. 週間上限を検証：同じ `week_number` の承認済み有効広告をカウント。5件以上なら 409 Conflict を返す。5. `approval_status = approved`、`approved_by`（管理者ID）、`approved_at`（現在時刻）を設定。6. 有効広告キャッシュを無効化。7. `AD_APPROVED` 監査イベントを記録。8. 更新された広告DTOを返す。 |

| **後続アクション** | 広告はスケジュール期間内にストアフロント表示の対象になる |

### 6.5 操作：管理者が広告を却下する

| **処理ステップ** | 1. `:id` をUUID形式として検証。2. JWTトークンと管理者ロールを検証。3. 広告を検索し、`approval_status = pending` を確認。4. `rejection_reason` を検証（必須）。5. `approval_status = rejected`、`approved_by`、`approved_at`、`rejection_reason` を設定。6. 自動払い戻しを実行 → `payment_status = refunded`。7. 有効広告キャッシュを無効化。8. `AD_REJECTED` 監査イベントを記録。9. マーチャントに却下と理由を通知。10. 更新された広告DTOを返す。 |
| **成功レスポンス** | 200 OK、更新された広告データ付き |

## 7. 入出力仕様

### 7.1 入力仕様 — 広告作成（入力定義）

| フィールド | 表示名（EN） | 表示名（JA） | データ型・長さ | 必須 | 入力コントロール | バリデーション |
|-------|-------------------|-------------------|-------------------|:--------:|---------------|------------|
| `title` | Title | タイトル | VARCHAR(200) | はい | 入力（テキスト） | `@IsString()`、`@IsNotEmpty()`、`@MaxLength(200)` |
| `content` | Content | 内容 | TEXT | いいえ | テキストエリア | `@IsString()`、`@IsOptional()`、`@MaxLength(5000)` |
| `announcementMessage` | Announcement Message | 告知メッセージ | VARCHAR(500) | はい | テキストエリア | `@IsString()`、`@IsNotEmpty()`、`@MaxLength(500)` |
| `imageUrl` | Image | 画像 | VARCHAR(500) | いいえ | ファイルアップロード | `@IsUrl()`、`@IsOptional()`、`@MaxLength(500)`、JPG/PNG/WebP、最大5MB |
| `linkUrl` | Link URL | リンクURL | VARCHAR(500) | いいえ | 入力（URL） | `@IsUrl()`、`@IsOptional()`、`@MaxLength(500)` |
| `isActive` | Active | 有効フラグ | BOOLEAN | いいえ | スイッチ | `@IsBoolean()`、`@IsOptional()`、デフォルト true |
| `startsAt` | Start Date | 開始日時 | TIMESTAMPTZ | はい | 入力（日時） | `@IsDateString()` |
| `expiresAt` | End Date | 終了日時 | TIMESTAMPTZ | はい | 入力（日時） | `@IsDateString()`、`startsAt` より後であること |

> 注：`approval_status`、`payment_status`、`payment_amount`、`payment_reference`、`week_number`、`approved_by`、`approved_at`、`rejection_reason` はシステム管理項目であり、マーチャント入力からは一切受け付けない。

## 9. エラーハンドリング仕様

### 9.1 エラーレスポンス構造

```json
{
  "statusCode": 403,
  "message": ["Forbidden"],
  "error": "Forbidden",
  "timestamp": "2026-08-05T12:00:00.000Z",
  "path": "/api/v1/ads/a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

### 9.2 エラー分類表 — 広告操作

| HTTPステータス | エラーコード | シナリオ | ユーザー向け挙動 |
|-------------|------------|----------|---------------------|
| `400` | `BAD_REQUEST` | バリデーション失敗（`rejectionReason` 欠落、`announcementMessage` 欠落を含む） | フィールド単位のインラインエラー＋上部バナー |
| `401` | `UNAUTHORIZED` | JWT欠落または無効 | ログイン画面へリダイレクト |
| `403` | `FORBIDDEN` | マーチャント/管理者でない、広告の所有者でない、または店舗が未承認 | "Shop is not approved" / "You don't have permission to manage this ad" |
| `404` | `NOT_FOUND` | 広告が存在しない | "Advertisement not found"（更新オプション付き） |
| `409` | `CONFLICT` | `expires_at <= starts_at` | "Invalid schedule dates"（日付のインラインエラー付き） |
| `409` | `WEEKLY_LIMIT_REACHED` | 承認時に週間広告上限（5件/週）に到達 | "Weekly advertisement limit reached (max 5)" |
| `422` | `UNPROCESSABLE_ENTITY` | 支払いなしで提出 / 承認待ちでない広告を承認 | "Advertising fee must be paid before submission" |
| `413` | `PAYLOAD_TOO_LARGE` | 広告画像ファイル > 5MB | "Image file must not exceed 5MB" |
| `415` | `UNSUPPORTED_MEDIA_TYPE` | 無効な画像形式 | "Only JPG, PNG, and WebP images are supported" |
| `429` | `TOO_MANY_REQUESTS` | レート制限超過 | "Too many requests. Please wait {seconds} seconds" |
| `500` | `INTERNAL_SERVER_ERROR` | サーバーエラー（支払い検証失敗を含む） | "Something went wrong. Please try again" |

### 9.3 フロントエンドのエラー表示挙動

- **フィールド単位のバリデーション**：無効な入力に赤い枠とインラインテキストを表示。
- **フォーム全体のサマリー**：フォーム上部にすべてのエラーを一覧表示するアラートバナー。
- **トースト通知**：APIエラーと成功アクションに使用。
- **ローディング状態**：API呼び出し中は送信ボタンにスピナーを表示。
- **空状態**：現在の絞り込み/検索に一致する広告がない場合にイラスト付きメッセージを表示。
- **確認ダイアログ**：ソフト削除API呼び出し前に削除の確認が必要。

## 10. 権限とアクセス制御

### 10.1 認証要件

- マーチャント操作には JSON Web Token（JWT）Bearer Token を `Authorization` ヘッダーで送信。
- 公開エンドポイント（有効広告表示）には認証は不要。

### 10.2 公開 vs 保護エンドポイント

| エンドポイント | アクセスレベル | 説明 |
|----------|-------------|-------------|
| `POST /ads` | 保護（マーチャント/管理者） | 広告を作成（下書き） |
| `GET /ads` | 保護（マーチャント/管理者） | 自社広告を一覧表示 |
| `PATCH /ads/:id` | 保護（マーチャント/管理者） | 広告を更新 |
| `DELETE /ads/:id` | 保護（マーチャント/管理者） | 広告を削除（ソフト削除） |
| `POST /ads/:id/pay` | 保護（マーチャント/管理者） | 広告掲載料を支払う |
| `POST /ads/:id/submit` | 保護（マーチャント/管理者） | 広告を承認申請に提出 |
| `GET /admin/ads` | 保護（管理者） | 全広告/承認待ちキューを一覧表示 |
| `POST /admin/ads/:id/approve` | 保護（管理者） | 広告を承認 |
| `POST /admin/ads/:id/reject` | 保護（管理者） | 広告を却下（理由付き＋払い戻し） |
| `GET /ads/active` | 公開 | プラットフォーム表示用の有効承認済み広告を一覧表示 |

| ロール | 自社広告の閲覧 | 広告作成 | 広告編集 | 広告削除 | 支払い/提出 | 承認/却下 | 有効広告の閲覧（公開） |

| `merchant` | ✓（自店舗） | ✓（自店舗） | ✓（自店舗） | ✓（自店舗） | ✓（自店舗） | ✗ | ✓ |
| `admin` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

### 10.4 所有権の強制

```typescript
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles('merchant', 'admin')
@Controller('ads')
export class AdvertisementsController {
  // POST /, GET /, PATCH /:id, DELETE /:id, POST /:id/pay, POST /:id/submit
  //   上記ロールでガード + 所有権チェック

  @Public()
  @Get('active')
  findActive() { ... }
}

@UseGuards(JwtAuthGuard, RolesGuard)
@Roles('admin')
@Controller('admin/ads')
export class AdminAdvertisementsController {
  // GET /, POST /:id/approve, POST /:id/reject（管理者のみ）
```

## 11. リアルタイム通知の挙動

### 11.1 現在の実装

広告管理画面では WebSocket 接続は不要である。広告ステータス（承認待ち/承認済み/却下済み、有効/無効/期限切れ）はスケジュールデータから導出され、変更後は標準的なクエリ無効化（TanStack Query）で更新される。

### 11.2 通知イベント

| イベント | トリガー | 受信者 | アクション |
|-------|---------|-----------|--------|
| `AD_SUBMITTED` | マーチャントが広告を承認申請に提出 | 管理者 | 管理者ダッシュボードの承認待ちバッジ/通知 |
| `AD_APPROVED` | 管理者が広告を承認 | マーチャント | 通知＋広告が表示可能になる（キャッシュ更新 ≤ 5分） |
| `AD_REJECTED` | 管理者が広告を却下 | マーチャント | `rejection_reason` 付きの通知。払い戻し処理 |
| `AD_ACTIVATED` | 広告の開始時刻到達 / 有効への切り替え | — | `cache:ads:active` 更新後にストアフロントに表示（最大5分） |
| `AD_EXPIRED` | `expires_at` 経過 | — | キャッシュ更新後にストアフロントから消える |
| `AD_MUTATED` | 作成/更新/削除 | — | キャッシュは即時に無効化。次の `GET /ads/active` で DB を再クエリ |
