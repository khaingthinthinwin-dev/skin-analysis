## 1. 機能概要

### 1.1 目的と範囲

本画面サブシステムは、Cosmetics Finder プラットフォーム内の広告ライフサイクルを、プラットフォーム管理者が完全に管理できるようにする。ショップが提出した広告のレビューと承認・却下（個別または一括）、広告パッケージ価格と料金設定の管理、料金変更履歴の追跡、配置場所と料金ティア別のプラットフォーム全体の広告収益内訳の分析、広告パフォーマンスおよび料金履歴レポートの出力という、管理者側の責務全体を対象とする。

広告システムは主要な収益化チャネルである。ショップは配置場所と価格ティアに基づく日額料金を支払う。すべての広告は表示前に管理者の承認を必要とする。本書では、管理者が本サブシステムを管理するための全画面、操作、業務ルール、APIエンドポイントを定義する。

### 1.2 機能責務

1. **広告レビュー・承認** — 保留中のショップ広告をレビューし、理由を付けて個別に承認または却下し、承認メタデータ（approved_by、approved_at）を追跡する。
2. **一括承認・却下** — チェックボックスで複数の保留中広告を選択し、単一の一括操作で承認または却下する。一括却下には共通の却下理由を使用し、自動で一括返金する。
3. **広告表示管理** — 承認済み、アクティブ、かつ有効期限内の広告だけが表示されることを保証する。ティアに基づく優先度ローテーション（Premium > Standard > Basic）、ティア内のラウンドロビン、スライダーあたり最大5件、5秒ごとの自動ローテーションを行う。
4. **パッケージ・料金管理** — 配置場所とティアごとの料金設定を作成、編集、有効化・無効化する。すべての変更を、タイムスタンプ、変更前後の値、理由とともに料金履歴へ記録する。
5. **料金履歴追跡** — すべての価格変更を完全な監査証跡とともに記録する。
6. **収益内訳分析** — カスタム日付範囲における配置場所および価格ティア別の広告収益内訳について、財務チャート、グラフ、集計指標を提供する。
7. **レポート出力** — 広告パフォーマンス、ショップ広告提出履歴、料金履歴の各レポートを CSV 形式で出力する。
8. **監査ログ** — 重要な管理者操作（承認、却下、一括承認、一括却下、料金作成、料金更新、料金無効化）をすべて監査証跡へ記録する。

## 3. 状態遷移仕様

### 3.1 広告承認状態

| 状態 | 説明 | 表示対象 | 管理者の操作 |
|-------|-------------|:------------:|:-------------:|
| `pending` | ショップが提出し、管理者レビュー待ち | いいえ | 承認、却下、一括承認、一括却下 |

## 4. 業務ルール

### 4.1 広告レビュー・承認ルール

| ルールID | ルール名 | 説明 | 適用層 |
|---------|-----------|-------------|-------------------|
| BR-ADM-001 | 管理者承認必須 | 広告を承認または却下できるのは管理者のみ。 | Backend（RBAC: admin ロール） |
| BR-ADM-002 | 却下理由必須 | 広告を却下する場合（単体・一括）、管理者は理由を入力しなければならない。 | Backend（DTO validation） |
| BR-ADM-003 | 承認メタデータ | 承認ごとに `approved_by`（管理者ユーザーID）と `approved_at`（タイムスタンプ）を記録する。 | Backend（service logic） |
| BR-ADM-004 | 却下時返金 | 管理者が広告を却下したとき、対応する支払いの返金を開始する。 | Backend（ad_payments refund） |
| BR-ADM-005 | pending 状態ガード | `approval_status='pending'` の広告だけを承認・却下できる。 | Backend（state check） |

### 4.2 一括操作ルール

| ルールID | ルール名 | 説明 | 適用層 |
|---------|-----------|-------------|-------------------|
| BR-ADM-010 | 一括選択上限 | 1回の一括操作で選択できる広告は最大50件。 | Frontend（checkbox cap） + Backend（validation） |
| BR-ADM-011 | 一括承認の原子性 | 選択した広告を単一のデータベーストランザクションで承認する。いずれかの広告がバリデーションに失敗した場合、バッチ全体をロールバックする。 | Backend（transaction） |
| BR-ADM-012 | 一括却下の共通理由 | 一括却下操作では、すべての広告に単一の却下理由を適用する。 | Backend（DTO） |
| BR-ADM-013 | 一括返金処理 | 一括却下では、広告ごとに返金を順次処理する。返金失敗は記録するが、他の返金を妨げない。 | Backend（batch processing） |
| BR-ADM-014 | 一括通知 | 一括操作では、各ショップ所有者に広告ごとの個別通知を送る（集約通知1件ではない）。 | Backend（notification loop） |
| BR-ADM-015 | 一括監査ログ | トレーサビリティのため、一括操作の各広告に固有の監査ログエントリを生成する。 | Backend（audit loop） |
| BR-ADM-016 | 状態混在時の却下 | 選択した広告に pending 以外の状態が1件でもある場合、pending でない広告を特定する説明的なエラーを返して一括操作を失敗させる。 | Backend（pre-flight check） |

### 4.3 広告表示ルール

## 6. 機能操作仕様

### 6.1 操作: 広告一覧

| 属性 | 仕様 |
|-----------|---------------|
| **起動** | `/admin/advertisements` へ移動 |
| **APIエンドポイント** | `GET /api/v1/admin/ads` |
| **クエリパラメーター** | `status`（任意）、`placement`（任意）、`tier`（任意）、`shop`（任意検索）、`dateFrom`（任意）、`dateTo`（任意）、`page`、`limit` |
| **処理手順** | 1. JWT token と管理者ロールを検証する。2. `shops` と `ad_payments` を関連付けて `advertisements` を検索し、料金情報は広告の保存済みスナップショット値を使用する。3. フィルター（status、placement、tier、ショップ検索、日付範囲）を適用する。4. 結果をページングする。5. ショップ情報、料金スナップショット、支払状態付きのページング済み広告一覧を返す。 |
| **成功レスポンス** | ページング済み広告一覧を含む 200 OK |

### 6.2 操作: 広告の単体承認

| 属性 | 仕様 |
|-----------|---------------|
| **起動** | 広告レビューモーダルで「承認」をクリック |
| **APIエンドポイント** | `POST /api/v1/admin/ads/:id/approve` |
| **処理手順** | 1. JWT token と管理者ロールを検証する。2. IDで広告を検索する。3. 広告の `approval_status='pending'` を確認する。4. `approval_status='approved'` を設定する。5. `approved_by=currentAdmin.id` を設定する。6. `approved_at=currentTimestamp` を設定する。7. ショップ所有者に通知する: 「広告『{title}』が承認されました」。8. AD_APPROVED イベントを audit_logs に記録する（entity_type='Advertisement', entity_id=adId）。9. 更新済み広告 DTO を返す。 |
| **成功レスポンス** | 更新済み広告を含む 200 OK |

### 6.3 操作: 広告の単体却下

| 属性 | 仕様 |
|-----------|---------------|
| **起動** | 広告レビューモーダルで却下理由を入力して「却下」をクリック |
| **APIエンドポイント** | `POST /api/v1/admin/ads/:id/reject` |
| **リクエストボディ** | `{ rejection_reason: string }` |
| **処理手順** | 1. JWT token と管理者ロールを検証する。2. IDで広告を検索する。3. 広告の `approval_status='pending'` を確認する。4. `rejection_reason` が指定され空でないことを検証する。5. `approval_status='rejected'` を設定する。6. `rejection_reason` を設定する。7. `approved_by=currentAdmin.id` を設定する。8. `approved_at=currentTimestamp` を設定する。9. `ad_id = id` かつ `payment_status='completed'` の対応する `ad_payments` レコードを検索する。10. `ad_payments` を更新し、`payment_status='refunded'`、`refund_amount=payment_amount`、`refund_reason=rejection_reason`、`refunded_at=currentTimestamp` を設定する。11. ショップ所有者に通知する: 「広告『{title}』が却下されました。理由: {reason}」。12. AD_REJECTED イベントを audit_logs に記録する。13. 更新済み広告 DTO を返す。 |
| **成功レスポンス** | 更新済み広告を含む 200 OK |

### 6.4 操作: 広告の一括承認

| 属性 | 仕様 |
|-----------|---------------|
| **起動** | 広告を選択して「一括承認」をクリック |
| **APIエンドポイント** | `POST /api/v1/admin/ads/bulk/approve` |
| **リクエストボディ** | `{ ad_ids: string[] }` |
| **処理手順** | 1. JWT token と管理者ロールを検証する。2. `ad_ids` 配列が空でなく、≤ 50 であることを検証する。3. IDで全広告を検索する。4. **事前チェック:** 選択した全広告の `approval_status='pending'` を確認する。pending でない広告があれば、pending でない広告ID一覧を含む 400 を返す。5. データベーストランザクションを開始する。6. バッチ内の各広告について、a. `approval_status='approved'` を設定する。b. `approved_by=currentAdmin.id` を設定する。c. `approved_at=currentTimestamp` を設定する。7. トランザクションをコミットする。8. 各広告について、a. ショップ所有者へ個別通知する: 「広告『{title}』が承認されました」。b. AD_APPROVED イベントを audit_logs に記録する。9. 一括結果 DTO `{ approved: number, total: number, ad_ids: string[] }` を返す。 |
| **成功レスポンス** | 一括結果 DTO を含む 200 OK |

### 6.5 操作: 広告の一括却下

| 属性 | 仕様 |
|-----------|---------------|
| **起動** | 広告を選択し、共通理由を指定して「一括却下」をクリック |
| **APIエンドポイント** | `POST /api/v1/admin/ads/bulk/reject` |
| **リクエストボディ** | `{ ad_ids: string[], rejection_reason: string }` |
| **処理手順** | 1. JWT token と管理者ロールを検証する。2. `ad_ids` 配列が空でなく、≤ 50 であることを検証する。3. `rejection_reason` が指定され空でないことを検証する。4. IDで全広告を検索する。5. **事前チェック:** 選択した全広告の `approval_status='pending'` を確認する。pending でない広告があれば、該当ID一覧を含む 400 を返す。6. データベーストランザクションを開始する。7. バッチ内の各広告について、a. `approval_status='rejected'`、b. `rejection_reason=commonReason`、c. `approved_by=currentAdmin.id`、d. `approved_at=currentTimestamp` を設定する。8. トランザクションをコミットする。9. 各広告について（トランザクション外で順次）、a. `ad_id = ad.id` かつ `payment_status='completed'` の `ad_payments` を検索する。b. `payment_status='refunded'`、`refund_amount=payment_amount`、`refund_reason=rejection_reason`、`refunded_at=currentTimestamp` を設定して更新する。c. 返金に失敗した場合、エラーを記録して次の広告へ進む。10. 各広告について、a. ショップ所有者へ個別通知する: 「広告『{title}』が却下されました。理由: {reason}」。b. AD_REJECTED イベントを audit_logs に記録する。11. 一括結果 DTO `{ rejected: number, total: number, refundsProcessed: number, refundsFailed: number, ad_ids: string[] }` を返す。 |

### 6.7 操作: 広告料金設定の管理

| 属性 | 仕様 |
|-----------|---------------|
| **起動** | `/admin/advertisements/packages` へ移動 |
| **APIエンドポイント** | `GET /api/v1/admin/ad-fees`（一覧）、`POST /api/v1/admin/ad-fees`（作成）、`PUT /api/v1/admin/ad-fees/:id`（更新）、`PATCH /api/v1/admin/ad-fees/:id/deactivate`（無効化） |
| **処理手順 (GET)** | 1. 管理者ロールを検証する。2. 全 `ad_fee_settings` を検索する。3. 料金設定一覧を返す。 |
| **処理手順 (POST)** | 1. 管理者ロールを検証する。2. daily_rate > 0、duration_days > 0、max_ads > 0 を検証する。3. 一意性を確認する: 指定された配置場所・ティアに有効な設定が存在しないこと。競合時は 409 を返す。4. `is_active=true` で `ad_fee_settings` レコードを作成する。5. `ad_fee_history` レコードを作成する: `ad_fee_setting_id=<new_id>`、`old_daily_rate=null`、`new_daily_rate=daily_rate`、`old_duration_days=null`、`new_duration_days=duration_days`、`old_max_ads=null`、`new_max_ads=max_ads`、`changed_by=currentAdmin.id`、`change_reason`、`effective_from`。6. FEE_CREATED イベントを audit_logs に記録する。7. 作成済み料金設定を返す。 |

| `dateFrom` | 必須 | "Start date is required" | "開始日は必須です" |
| `dateTo` | 必須、>= dateFrom | "End date is required" / "End date must be after start date" | "終了日は必須です" / "終了日は開始日より後である必要があります" |

### 8.8 バリデーション適用層

1. **Frontend (Client)**: React Hook Form + Zod schema によるリアルタイムフィードバック付きバリデーション。
2. **Backend (Server)**: すべてのエンドポイントに NestJS ValidationPipe + class-validator DTO。
3. **Database (Constraint)**: 最終的な安全網として DB check constraints。

## 9. エラー処理仕様

### 9.1 エラーレスポンス構造

```json
{
  "statusCode": 400,
  "message": ["ad_ids must contain between 1 and 50 items"],
  "error": "Bad Request",
  "timestamp": "2026-08-24T12:00:00.000Z",
  "path": "/api/v1/admin/ads/bulk/approve"
}
```

### 9.2 エラー分類表 — 広告レビュー（単体・一括）

| HTTP Status | Error Code | Scenario | User-Facing Behavior |
|-------------|------------|----------|---------------------|
| `400` | `BAD_REQUEST` | 却下理由がない | "Rejection reason is required" |
| `400` | `BAD_REQUEST` | 広告が pending 状態でない | "This advertisement is no longer pending review" |
| `400` | `BAD_REQUEST` | 一括: 選択中に pending でない広告がある | "The following ads are no longer pending: {list}. Please refresh and try again." |
| `400` | `BAD_REQUEST` | 一括: ad_ids 配列が空 | "At least one ad must be selected" |
| `400` | `BAD_REQUEST` | 一括: 50件上限超過 | "Maximum 50 ads per bulk operation" |
| `400` | `BAD_REQUEST` | 一括: UUID 形式不正 | "Invalid ad ID format" |
| `403` | `FORBIDDEN` | 管理者以外が操作を試行 | "Access denied" |
| `404` | `NOT_FOUND` | 広告が見つからない | "Advertisement not found" |
| `409` | `CONFLICT` | 一括: 処理中に一部広告の状態が変わった | "{n} ads were processed by another admin. Please refresh." |
| `500` | `INTERNAL_SERVER_ERROR` | サーバーエラー | "Something went wrong. Please try again" |

### 9.3 エラー分類表 — 料金管理

| HTTP Status | Error Code | Scenario | User-Facing Behavior |
|-------------|------------|----------|---------------------|
| `400` | `BAD_REQUEST` | 日額料金不正（<=0） | "Daily rate must be greater than 0" |
| `400` | `BAD_REQUEST` | 期間不正（<=0） | "Duration must be at least 1 day" |
| `400` | `BAD_REQUEST` | max_ads 不正（<=0） | "Max ads must be at least 1" |
| `409` | `CONFLICT` | 配置場所・ティアの重複 | "A fee setting already exists for this placement and tier" |
| `404` | `NOT_FOUND` | 料金設定が見つからない | "Fee setting not found" |
| `400` | `BAD_REQUEST` | 無効化: 料金設定が既に無効 | "Fee setting is already inactive" |
| `400` | `BAD_REQUEST` | 作成・無効化の変更理由がない | "Change reason is required" |
| `500` | `INTERNAL_SERVER_ERROR` | サーバーエラー | "Something went wrong. Please try again" |

### 9.4 エラー分類表 — 収益分析

| HTTP Status | Error Code | Scenario | User-Facing Behavior |
|-------------|------------|----------|---------------------|
| `400` | `BAD_REQUEST` | dateFrom または dateTo がない | "Start date and end date are required" |
| `400` | `BAD_REQUEST` | dateTo が dateFrom より前 | "End date must be after start date" |
| `400` | `BAD_REQUEST` | 日付範囲が365日超過 | "Date range cannot exceed 365 days" |
| `500` | `INTERNAL_SERVER_ERROR` | サーバーエラー | "Something went wrong. Please try again" |

### 9.5 エラー分類表 — 出力

| HTTP Status | Error Code | Scenario | User-Facing Behavior |
|-------------|------------|----------|---------------------|
| `400` | `BAD_REQUEST` | レポート種別不正 | "Invalid report type" |
| `400` | `BAD_REQUEST` | 形式不正 | "Invalid export format. Use CSV." |
| `400` | `BAD_REQUEST` | 日付範囲がない | "Date range is required" |
| `500` | `INTERNAL_SERVER_ERROR` | 出力生成失敗 | "Report generation failed. Please try again." |

### 9.6 フロントエンドのエラー表示動作

- **フィールド単位バリデーション**: 不正な入力の赤枠と、その下のインラインテキスト。
- **フォーム単位サマリー**: すべてのエラーを列挙するフォーム上部の警告バナー。
- **Toast 通知**: APIエラーと操作成功に使用する。
- **ローディング状態**: API呼び出し中は送信ボタンにスピナーを表示する。
- **一括操作の進捗**: 処理済み件数付きの進捗バー。

## 13. 非機能要件

### 13.1 パフォーマンス要件

| 指標 | 目標 |
|--------|--------|
| 広告一覧ページ読み込み | ≤ 2秒 |
| 単体承認・却下 API | ≤ 500ミリ秒 |
| 一括承認・却下（50広告） | ≤ 5秒 |
| 料金設定更新 | ≤ 500ミリ秒 |
| 収益分析クエリ | ≤ 2秒 |
| 出力生成（≤1000行） | ≤ 3秒 |

### 13.2 セキュリティ考慮事項

| 懸念 | 対策 |
|---------|------------|
| 管理者バイパス | 全エンドポイントで JwtAuthGuard + RolesGuard により RBAC を適用 |
| 一括操作の悪用 | バッチあたり最大50広告、一括エンドポイントのレート制限 |
| 料金改ざん | 管理者ID、理由、変更前後の値付きで料金変更を記録 |
| 出力データ漏えい | 機密フィールド（パスワードハッシュ、トークン）を除外し、監査ログに記録 |
| SQL Injection | Prisma ORM によるパラメーター化クエリ |
| 並行一括編集 | バッチコミット前の楽観的ロックまたは事前状態チェック |

### 13.3 レスポンシブデザイン要件

| ブレークポイント | レイアウト |
|------------|--------|
| デスクトップ (≥ 1024px) | 完全なテーブルレイアウト、サイドバーフィルター、横並びチャート |
| タブレット (768px – 1023px) | フィルター縦積み、レスポンシブテーブル、チャート縦積み |
| モバイル (< 768px) | カード型広告一覧、全幅モーダル、1列チャート |

### 13.4 アクセシビリティ要件

| 要件 | 実装 |
|-------------|----------------|
| キーボードナビゲーション | すべての操作要素を Tab でフォーカス可能にし、一括チェックボックスをキーボード操作可能にする |
| スクリーンリーダー | ボタン、ステータスバッジ、モーダル、チャートに ARIA ラベルを付与 |
| 色コントラスト | ステータスバッジとチャート色を WCAG 2.1 AA に準拠させる |
| フォーカス管理 | モーダルのフォーカストラップと、閉じた際のフォーカス復帰 |
| チャートアクセシビリティ | 代替としてテキストベースのデータテーブルをチャートに含める |
