## 1. Functional Overview

### 1.1 Purpose and Scope

This subsystem manages the complete lifecycle of promotional discount codes (coupons) within the Cosmetics Finder marketplace. It provides merchants with full CRUD capabilities for promotions and enables buyers to validate and apply coupon codes during checkout.

The Promotion Management subsystem is central to the marketplace's sales strategy, enabling merchants to create targeted discount campaigns to attract buyers and increase conversion rates.

### 1.2 Functional Responsibilities

This subsystem is responsible for the following core functional areas:

1. **Promotion Creation** — Merchants can create new promotions with code, description, discount type (percentage/fixed), discount value, minimum order amount, maximum uses, and validity period.
2. **Promotion Editing** — Merchants can update existing promotion details, discount settings, and active status. **Note: Promotions that have been used (used_count > 0) cannot be edited.**
3. **Promotion Deletion** — Merchants can delete promotions (hard delete), permanently removing them from the database. **Note: Promotions that have been used (used_count > 0) cannot be deleted.**
4. **Dedicated Status Toggle** — Fast toggle of active/inactive status via dedicated `PATCH /api/v1/promotions/:id/toggle-active` endpoint.
5. **Coupon Code Validation** — Validate coupon codes at checkout, checking expiration, usage limits, minimum order amount, and active status.
6. **Usage Statistics** — Merchants can view promotion usage counts and expiry information. Usage is dynamically aggregated from completed orders (`usedCount`).
7. **License Status & Deactivation Guard** — Merchants with `pending`, `rejected`, or `deactivated` status cannot create, edit, delete, or activate/deactivate promotions. The promotion list page loads in restricted read-only mode with appropriate warning banners; direct mutation requests remain blocked by the backend (`RequireApprovedMerchantGuard`).
8. **Automated Expired Promotion Cleanup** — Daily scheduled cron job (`@Cron('0 2 * * *')`) automatically cleans up expired promotions older than 7 days.

### 1.3 Target Users

| Attribute | Value |
|-----------|-------|
| **Primary Actor (Merchant)** | Authenticated merchant managing their promotions (license status must be `approved`, account active) |
| **Primary Actor (Buyer)** | Authenticated buyer validating and applying coupons at checkout |
| **Primary Actor (Admin)** | Admin with full promotion management access |
| **Restricted Actor (Pending/Rejected/Deactivated Merchant)** | Authenticated merchant with `pending` or `rejected` license status or deactivated account — promotion mutations are restricted |
| **Required Authentication** | JWT Bearer Token for merchant/buyer operations |
| **Data Scope** | Merchant: own promotions only. Buyer: validate coupons for checkout. Admin: all promotions. Pending/rejected merchant: read-only list, no mutations. |

## 3. State Transition Specification

### 3.1 Promotion States

| State | Description | Can Edit | Can Delete | Can Validate |
|-------|-------------|:--------:|:----------:|:------------:|
| `ACTIVE` | `isActive = true` and current time is within the validity period | ✓ (if usedCount = 0) | ✓ (if usedCount = 0) | ✓ |
| `INACTIVE` | `isActive = false` | ✓ | ✓ (if usedCount = 0) | ✗ |
| `EXPIRED` | Current time is at or after `expiresAt` | ✓ | ✓ (if usedCount = 0) | ✗ |
| `MAX_USES_REACHED` | `maxUses` is set and `usedCount >= maxUses` | ✗ | ✗ | ✗ |

### 3.2 Promotion Lifecycle Transitions

| Transition ID | Origin State | Target State | Trigger Action | Guard Conditions |
|---------------|--------------|--------------|----------------|------------------|
| TR-PROMO-01 | — | `ACTIVE` | Create promotion (default) | Valid promotion data, merchant authenticated, license approved |
| TR-PROMO-02 | `ACTIVE` | `INACTIVE` | Merchant toggles is_active to false | Promotion belongs to merchant |
| TR-PROMO-03 | `INACTIVE` | `ACTIVE` | Merchant toggles is_active to true | Promotion belongs to merchant |
| TR-PROMO-04 | `ACTIVE` | `EXPIRED` | Time passes expires_at | Automatic system check |
| TR-PROMO-05 | `ACTIVE` | `MAX_USES_REACHED` | used_count reaches max_uses | Automatic on order completion |

### 3.3 Coupon Validation States

| Validation State | Description | Can Apply |
|-----------------|-------------|:---------:|
| `VALID` | All checks passed | ✓ |
| `EXPIRED` | Current time > expires_at | ✗ |
| `INACTIVE` | is_active = false | ✗ |
| `MAX_USES_REACHED` | used_count >= max_uses | ✗ |
| `MIN_ORDER_NOT_MET` | Order amount < min_order_amount | ✗ |
| `NOT_FOUND` | Code does not exist | ✗ |

## 4. Business Rules

### 4.1 Promotion Creation Rules

| Rule ID | Rule Name | Description | Enforcement Layer |
|---------|-----------|-------------|-------------------|
| BR-PROMO-001 | Required & Optional Fields | Promotion requires: code (max 50, uppercase), discountTypeCode ('percentage' or 'fixed'), discountValue (> 0), startsAt (ISO date), expiresAt (ISO date). Optional: description (max 500), minOrderAmount (>= 0), maxUses (>= 1), isActive (default true). | Backend (DTO validation) + Frontend form validation |
| BR-PROMO-002 | Code Uniqueness | Code must be globally unique across all merchants. Per DATABASE_SPEC, `code` has a global UNIQUE constraint (`uq_promotions_code`). If already taken, returns 409 Conflict with message "A promotion with this code already exists". | Backend (DB query & constraint `uq_promotions_code`, 409 Conflict) |
| BR-PROMO-003 | Discount Positive | discount_value must be > 0 (DECIMAL(10,2), min 0.01). | Backend (DB constraint `chk_promotions_discount_value` + class-validator `@Min(0.01)`) |
| BR-PROMO-004 | Percentage Range | When discountTypeCode = 'percentage', discountValue must be between 1 and 99. Value > 99 throws 400 Bad Request ("Percentage discount must not exceed 99"). | Backend (Service check + DTO) + Frontend validation |
| BR-PROMO-005 | Fixed Discount Limit | When discountTypeCode = 'fixed' and minOrderAmount is specified, discountValue cannot be equal to or greater than minOrderAmount. Throws 400 Bad Request ("Fixed discount cannot be equal to or greater than minimum order amount"). | Backend (Service validation) + Frontend validation |
| BR-PROMO-006 | Date Range Valid | expiresAt must be after startsAt (`expiresAt > startsAt`). Throws 400 Bad Request ("Expiry date must be after start date"). Frontend additionally validates that startsAt is not in the past for new promotions. | Backend (Service check + DB constraint `chk_promotions_dates`) + Frontend validation |
| BR-PROMO-007 | Default Status | New promotions default to `isActive = true`. | Backend (DB default) + Frontend form default |
| BR-PROMO-008 | Default Usage Count | New promotions start with `used_count = 0`. | Backend (DB default) |

### 4.2 Promotion Edit Rules

| Rule ID | Rule Name | Description | Enforcement Layer |
|---------|-----------|-------------|-------------------|
| BR-PROMO-009 | Usage Restriction | Promotions that have already been used (`usedCount > 0`, verified via order records) cannot be edited. Returns 409 Conflict ("Cannot edit a promotion that has already been used"). In UI, edit controls are disabled and warning alert is displayed. | Backend (service check via Order groupBy count) + Frontend UI disable |
| BR-PROMO-010 | Ownership Required | Merchants can only edit their own promotions (`promotion.merchantId === user.merchantId`). | Backend (service check) |
| BR-PROMO-011 | Code Immutable | The promotion `code` cannot be changed after creation. In edit mode, `code` is read-only / disabled. | Frontend UI (disabled field) + Backend DTO (omitted from UpdatePromotionDto) |

### 4.3 Promotion Deletion Rules

| Rule ID | Rule Name | Description | Enforcement Layer |
|---------|-----------|-------------|-------------------|
| BR-PROMO-012 | Hard Delete | Delete permanently removes the promotion record from the database. Returns 200 OK with `{ deleted: true }`. | Backend (Prisma delete) |
| BR-PROMO-013 | Ownership Required | Merchants can only delete their own promotions. | Backend (service check) |
| BR-PROMO-014 | Usage Restriction | Promotions that have been used (`usedCount > 0`, verified via orders) cannot be deleted. Returns 409 Conflict ("Cannot delete a promotion that has already been used"). | Backend (service check) + Frontend UI disable |

### 4.4 Coupon Validation Rules

| Rule ID | Rule Name | Description | Enforcement Layer |
|---------|-----------|-------------|-------------------|
| BR-PROMO-015 | Expiration Check | Current time must be within `startsAt` and `expiresAt` (`startsAt <= now <= expiresAt`). Throws 400 Bad Request ("Coupon has expired or is not yet valid"). | Backend (Service logic) |
| BR-PROMO-016 | Usage Limit Check | When `maxUses` is set, `usedCount` (from order history) must be less than `maxUses`. Throws 400 Bad Request ("Coupon has reached maximum usage"). | Backend (Service logic) |
| BR-PROMO-017 | Minimum Order Check | Cart subtotal must be >= `minOrderAmount` (if set). Throws 400 Bad Request ("Minimum order amount is {amount} MMK"). | Backend (Service logic) |
| BR-PROMO-018 | Active Check | `isActive` must be true. Throws 400 Bad Request ("Coupon is no longer active"). | Backend (Service logic) |
| BR-PROMO-021 | One Coupon Per Order | Only one coupon can be applied per order during checkout. | Backend (Checkout service) |

### 4.5 Merchant License Status & Account Status Rules

| Rule ID | Rule Name | Description | Enforcement Layer |
|---------|-----------|-------------|-------------------|
| BR-PROMO-019 | Restricted License Status | Merchants with license status `pending` or `rejected` may view their promotion list in read-only mode, but cannot create, update, delete, or toggle promotions. Direct mutation endpoints return `403 Forbidden` (`RequireApprovedMerchantGuard`). | Backend guard + frontend conditional rendering |
| BR-PROMO-020 | Deactivated Account Guard | Merchants with deactivated accounts (`isActive === false` or `status === 'deactivated'/'inactive'`) see `AccountDeactivatedBanner` and cannot perform any mutations. Create and Edit pages redirect to `/merchant/promotions`. | Frontend guard (`useMerchantProductsGuard`, `useAuth`) + Backend guard |

### 10.4 License Status Enforcement

Merchants with `pending` license status are restricted from all promotion management operations. The following enforcement applies:

**Backend (API Guard):**
```typescript
// Backend license status check — applied to all promotion CRUD endpoints
const merchant = await this.prisma.merchant.findUnique({ where: { userId: user.id } });
if (!merchant) throw new ForbiddenException('Merchant profile not found');
if (merchant.licenseStatus === 'pending') {
  throw new ForbiddenException({
    statusCode: 403,
    error: 'MERCHANT_NOT_APPROVED',
    message: 'Your account is pending approval. Promotion management is not available at this time.'
```

**Frontend (Route Guard):**
```typescript
// Frontend route guard — applied to /merchant/promotions/* routes
const merchantProfile = await fetchMerchantProfile(user.id);

}
```

## 13. Non-Functional Considerations

### 13.1 Performance Requirements

| Metric | Target |
|--------|--------|
| Promotion List API | ≤ 200 milliseconds |
| Coupon Validation API | ≤ 100 milliseconds |
| Promotion Create API | ≤ 500 milliseconds |

### 13.2 Caching Strategy

**Redis Cache Keys:**

- **`promo:detail:{code}`** — Promotion detail cache
  - TTL: Set to the exact remaining time until `expiresAt` using `EXPIRE`
  - Invalidation: On promotion update/delete, or after committed usage reaches `maxUses`

- **`promo:list:{merchantId}`** — Merchant promotion list cache
  - TTL: 2 minutes (120 seconds)
  - Invalidation: On any promotion CRUD operation for that merchant

- **`promo:quota:{code}`** — Optional reservation counter for limited-use promotions
  - TTL: Set to the exact remaining time until `expiresAt`
  - This counter is not authoritative; `promotions.used_count` is the source of truth
  - Never increment usage during coupon validation; commit usage atomically with order creation

**Cache Invalidation Triggers:**

- Promotion created → invalidate merchant list cache
- Promotion updated → invalidate detail cache + list cache
- Promotion deleted → invalidate detail cache + list cache + quota key
- Coupon validated → optional short-lived read cache only; do not mutate usage
- Coupon applied in a committed order → increment `used_count` atomically and invalidate detail/list caches
- Quota exhausted → invalidate detail cache; do not rewrite database status because no status column exists

## 16. Redis Cache Invalidation Strategy

> **Note** — No new PostgreSQL database tables are added. This section covers Redis Cache Layer only.

### 16.1 Time-Based Expiry (TTL)

**Redis `EXPIRE` command** is used to set TTL with **exact promo expiration timestamps**.

**TTL Calculation Logic:**

- **Step 1: Get expiration time** — Retrieve `promo.expires_at` from database as UTC timestamp.
- **Step 2: Calculate remaining TTL** — `ttlSeconds = Math.max(0, Math.floor((promo.expires_at - Date.now()) / 1000))`. If `ttlSeconds = 0`, delete key immediately.
- **Step 3: Set Redis key with TTL** — `SET promo:detail:{code} {json_data} EX {ttlSeconds}`

**TTL Application Examples:**

- Promotion created at 10:00, expires at 18:00 (8 hours) → TTL = 28800 seconds
- Promotion created at 10:00, expires at 10:30 (30 minutes) → TTL = 1800 seconds
- Promotion already expired → TTL = 0 → Key deleted immediately

**Backend Implementation:**

```typescript
// Backend — TTL-based cache setting
async setPromotionCache(promo: Promotion): Promise<void> {
  const now = new Date();
  const expiresAt = new Date(promo.expires_at);
  const ttlSeconds = Math.max(0, Math.floor((expiresAt.getTime() - now.getTime()) / 1000));

  if (ttlSeconds === 0) {
    await this.redis.del(`promo:detail:${promo.code}`);
    return;
  }

  const cacheData = JSON.stringify(promo);
  await this.redis.set(`promo:detail:${promo.code}`, cacheData, 'EX', ttlSeconds);
}
```

### 16.2 Atomic Counters for Quotas

**Redis Atomic Commands** may reserve capacity for **limited-use promotions** without race conditions. The database `used_count` remains authoritative, and reservation logic is separate from coupon validation.

**Quota Key Structure:**

- **Key Pattern:** `promo:quota:{code}`
- **Initial Value:** `max_uses` (integer)
- **TTL:** Same as promotion expiration time

**Atomic Decrement Strategy:**

- **Step 1: Check quota availability** — `GET promo:quota:{code}` → returns remaining count. If `null` or `0` → quota exhausted, reject coupon.
- **Step 2: Atomic decrement** — Use **Lua script** for atomic check-and-decrement.

**Lua Script for Optional Reservation:**

```lua
-- Redis Lua Script — Atomic coupon use with quota check
local key = KEYS[1]  -- promo:quota:{code}
local max_uses = tonumber(ARGV[1])

-- Get current quota
local current = tonumber(redis.call('GET', key))

-- If key doesn't exist, initialize with max_uses
if current == nil then
  redis.call('SET', key, max_uses)
  current = max_uses
end

-- Check if quota available
if current <= 0 then
  return -1  -- Quota exhausted
end

-- Atomic decrement
local new_value = redis.call('DECR', key)

-- If went below 0, restore and reject
if new_value < 0 then
  redis.call('INCR', key)
  return -1  -- Quota exhausted
end

return new_value  -- Returns remaining count
```

**Backend Integration:**

```typescript
// Backend — Atomic quota check
async useCouponQuota(code: string, maxUses: number): Promise<boolean> {
  const luaScript = `
    local key = KEYS[1]
    local max_uses = tonumber(ARGV[1])
    local current = tonumber(redis.call('GET', key))
    if current == nil then
      redis.call('SET', key, max_uses)
      current = max_uses
    end
    if current <= 0 then return -1 end
    local new_value = redis.call('DECR', key)
    if new_value < 0 then
      redis.call('INCR', key)
      return -1
    end
    return new_value
  `;

  const result = await this.redis.eval(
    luaScript,
    1,  // number of keys
    `promo:quota:${code}`,
    maxUses.toString()
  );

  return result !== -1;
}
```

**Quota Exhaustion Behavior:**

- Quota hits zero → Redis key `promo:quota:{code}` value = `0`
- Next coupon attempt → Lua script returns `-1` → Reject
- Auto-invalidation → Detail cache `promo:detail:{code}` also invalidated
- Status update → Promotion status set to `MAX_USES_REACHED` in cache

### 16.3 Event-Driven Invalidation

**Event-Driven Invalidation** — When promotion changes occur, **immediately** invalidate cache.

**Event-Driven Invalidation Triggers:**

- **Merchant deletes promotion**
  - Event: `PROMOTION_DELETED`
  - Action: `DEL promo:detail:{code}` + `DEL promo:quota:{code}`
  - Service: `PromotionsService.deletePromotion()`

- **Merchant updates promotion**
  - Event: `PROMOTION_UPDATED`
  - Action: `DEL promo:detail:{code}` (re-fetch on next read)
  - Service: `PromotionsService.updatePromotion()`

- **Quota exhausted**
  - Event: `QUOTA_EXHAUSTED`
  - Action: `DEL promo:detail:{code}` + status update
  - Service: `PromotionQuotaService.decrementQuota()`

### 16.4 Cache Invalidation Flow

**Complete Cache Lifecycle:**

- **Create Promotion**
  - DB: INSERT promotion
  - Redis: `SET promo:detail:{code} {data} EX {ttl}`
  - Redis: `SET promo:quota:{code} {max_uses} EX {ttl}`

- **Update Promotion**
  - DB: UPDATE promotion
  - Redis: `DEL promo:detail:{code}` (invalidate cache)
  - Next read: Re-fetch from DB, repopulate cache

- **Delete Promotion (Hard Delete)**
  - DB: DELETE promotion
  - Redis: `DEL promo:detail:{code}` + `DEL promo:quota:{code}`
  - Next read: Returns null (not found)

- **Use Coupon (Quota Decrement)**
  - Redis Lua: `DECR promo:quota:{code}`
  - If quota = 0: `DEL promo:detail:{code}` + `DEL promo:quota:{code}`
  - Next read: Returns null or status `MAX_USES_REACHED`

- **Promotion Expires (TTL Auto-Delete)**
  - Redis: Key auto-deleted when TTL reaches 0
  - No application code needed — Redis handles automatically

### 16.5 Redis Cache Patterns Summary

- **`promo:detail:{code}`** — Single promotion detail cache
  - Set with exact TTL (expires_at - now)
  - Invalidated on: update, delete, quota exhaustion

- **`promo:list:{merchantId}`** — Merchant promotion list cache
  - TTL: 120 seconds (short-lived)
  - Invalidated on: any CRUD operation

- **`promo:quota:{code}`** — Atomic quota counter
  - Set with exact TTL (expires_at - now)
  - Used with Lua script for atomic decrement
  - Auto-invalidated when counter reaches zero

**Redis Performance Targets:**

- **Cache Hit Rate** — >= 95%
- **Cache Read Latency** — <= 1ms (Redis is in-memory)
- **Cache Write Latency** — <= 2ms
- **Lua Script Execution** — <= 5ms
