## 2. Screen Overview & Purpose (画面概要・目的)

### 2.1 Purpose (目的)
The Promotion Management screens enable merchants to manage their promotional discount codes (coupons) through full CRUD operations. Merchants can create, edit, delete promotions, toggle active status, and view usage statistics. Buyers can validate and apply coupon codes at checkout. Admin users have full access to all promotions.

### 2.2 Target Users & Roles (対象ユーザーと権限)

| Attribute | Value |
| :--- | :--- |
| **Primary Actors** | Authenticated merchant (own promotions), Admin (all promotions) |
| **Secondary Actor** | Authenticated buyer (coupon validation at checkout) |
| **Restricted Actor** | Pending/rejected merchant (read-only list, no mutations) |
| **Required Authentication** | JWT Bearer Token |
| **Data Scope** | Merchant: own promotions only. Buyer: validate coupons. Admin: all promotions. |
| **Access Control** | Protected routes — JwtAuthGuard + RolesGuard (merchant/admin/buyer) |

### 2.3 Core Functions & Basic Design Principles (主要機能・基本設計方針)
1. **Promotion Listing** — View and manage merchant's promotions with search/filter.
2. **Promotion Creation** — Create new promotions with code, discount type, value, and validity period.
3. **Promotion Editing** — Update existing promotion details (restricted when used_count > 0).
4. **Promotion Deletion** — Hard delete promotions (restricted when used_count > 0).
5. **Status Toggle** — Toggle promotion active/inactive status.
6. **Usage Statistics** — View usage counts and expiry information.
7. **Coupon Validation** — Buyers validate coupon codes at checkout.
8. **Internationalization** — Full i18n support for EN, JA, MY.
9. **Responsive Design** — Mobile-first adaptive layout.

## 5. Item Behaviors & Event Specifications (各項目における挙動・イベント仕様)

### 5.1 Search Promotions (`txtSearch` onChange)
- **Trigger:** User types in search input.
- **Processing Logic:**
  1. **Client-Side Pre-Check:** Search string trimmed.
  2. **Backend Dispatch:** `GET /api/v1/promotions?search={encodedQuery}&status={status}&sortBy={sortBy}&page=1&limit={limit}`.
  3. **Backend Execution:** Filter promotions where code contains search query (case-insensitive via Prisma `mode: 'insensitive'`).
  4. **Post-Execution UI:** Update promotion list with matching items. Reset pagination to page 1.
- **Exception Handling:**
  - Network / Server error: Display error alert banner / toast with message from `getPromotionErrorInfo(error)`.

### 5.2 Filter by Status (`selStatusFilter` onChange)
- **Trigger:** User selects status filter option (`all`, `active`, `inactive`, `expired`).
- **Processing Logic:**
  1. **Backend Dispatch:** `GET /api/v1/promotions?status={status}&sortBy={sortBy}&page=1&limit={limit}` (omitted if `all`).
  2. **Backend Execution:** Filter promotions by active flag and expiration timestamp compared to `NOW()`.
  3. **Post-Execution UI:** Update promotion list. Reset pagination to page 1.
- **Exception Handling:** Handled via TanStack Query error state.

### 5.2a Sort By (`selSortBy` onChange)
- **Trigger:** User selects sort order option (`newest`, `oldest`, `code`).
- **Processing Logic:**
  1. **Backend Dispatch:** `GET /api/v1/promotions?sortBy={sortBy}&status={status}&search={search}&page=1&limit={limit}`.
  2. **Backend Execution:** Sort promotions by `createdAt desc` (newest), `createdAt asc` (oldest), or `code asc` (code).
  3. **Post-Execution UI:** Refresh promotion list with re-ordered records.
- **Exception Handling:** Handled via TanStack Query error state.

### 5.2b Copy Promotion Code (`btnCopyCode` onClick)
- **Trigger:** User clicks copy icon button next to promotion code.
- **Processing Logic:**
  1. Call `navigator.clipboard.writeText(promo.code)`.
  2. Set local state `copiedCode = promo.code`.
  3. Change icon from `Copy` to `Check` (green color) for 2,000ms.
  4. Reset `copiedCode` to `null` after timeout.
- **Exception Handling:** Silent catch if clipboard API is disallowed.

### 5.3 Add New Promotion (`btnAddPromotion` onClick)
- **Trigger:** User clicks "Add New Promotion" button.
- **Processing Logic:**
  1. Navigate to `/merchant/promotions/new`.
  2. Initialize form with default startsAt (now) and expiresAt (+1 month).
- **Exception Handling:** Restricted if merchant is pending/rejected or deactivated.

### 5.4 Edit Promotion (`btnEdit` onClick)
- **Trigger:** User clicks edit pencil button on promotion row.
- **Processing Logic:**
  1. Navigate to `/merchant/promotions/:id/edit`.
  2. Fetch promotion detail via `GET /api/v1/promotions/:id`.
  3. Populate form fields.
  4. If `usedCount > 0`: Edit button is disabled on list with tooltip `既に使用されたプロモーションは編集/削除できません`. If navigated directly, form displays `alertUsedRestriction` and all inputs/buttons are disabled.
- **Exception Handling:**
  - `404`: Display "Promotion not found" toast and redirect to list.

### 5.5 Delete Promotion (`btnDelete` onClick → `dlgDeleteConfirm` → `dlgDeleteConfirmBtn` onClick)
- **Trigger:** User clicks delete trash icon on promotion row.
- **Processing Logic:**
  1. **Restriction Check:** If `usedCount > 0`, button is disabled with tooltip `既に使用されたプロモーションは編集/削除できません`.
  2. **Confirmation Dialog:** Open `AlertDialog` asking "Are you sure you want to delete this promotion? This action cannot be undone.".
  3. **On Confirm:** Dispatch `DELETE /api/v1/promotions/:id`.
  4. **Backend Execution:** Permanently delete promotion record (hard delete). Invalidate Redis cache keys (`promo:list:${merchantId}`, `promo:detail:${code}`, `promo:quota:${code}`).
  5. **Post-Execution UI:** Close dialog, invalidate query `['merchant', 'promotions']`, show success toast `Promotion deleted successfully`.
- **Exception Handling:**
  - `403`: Display permission error.
  - `404`: Display "Promotion not found".
  - `409`: Display "Cannot delete a promotion that has already been used".

### 5.6 Toggle Active Status (`swtActive` onChange)
- **Trigger:** User toggles active switch on promotion row or card.
- **Processing Logic:**
  1. **Backend Dispatch:** Dedicated endpoint `PATCH /api/v1/promotions/:id/toggle-active`.
  2. **Backend Execution:** Inverts `isActive` flag in database. Invalidates Redis cache.
  3. **Post-Execution UI:** Invalidate query `['merchant', 'promotions']`, toggle switch updates instantly.
- **Exception Handling:**
  - `403`: Permission denied (pending/rejected license). Switch reverts state.

### 5.7 Promotion Form Submit (`btnSave` onClick)
- **Trigger:** User clicks "Save Promotion" (Create) or "Update Promotion" (Edit).
- **Processing Logic:**
  1. **Client-Side Pre-Check (`validate()`):**
     - Code: Required, max 50 characters, auto-uppercased.
     - Discount Value: Required, > 0. If percentage: 1-99%. If fixed: must be < `minOrderAmount` (if set).
     - Starts At: Required, cannot be in the past for new promotions.
     - Expires At: Required, must be strictly after `startsAt`.
     - Max Uses: Optional, must be ≥ 1 if provided.
     - Min Order Amount: Optional, must be ≥ 0 if provided.
  2. **Backend Dispatch:**
     - Create: `POST /api/v1/promotions` with `CreatePromotionDto` (`discountTypeCode`, `discountValue`, etc.).
     - Update: `PATCH /api/v1/promotions/:id` with `UpdatePromotionDto` (`discountTypeCode`, `discountValue`, etc. Code is excluded/read-only).
  3. **Backend Execution:**
     - Validate dates, percentages, and minimum order relationships.
     - On Create: Check code uniqueness against database. Return 409 Conflict if duplicate.
     - On Update: Check dynamic `realUsedCount` from Orders table. Return 409 Conflict if `realUsedCount > 0`.
     - Persist changes, invalidate Redis cache.
  4. **Post-Execution UI:** Show success toast `Promotion saved successfully`, navigate back to `/merchant/promotions`.
- **Exception Handling:**
  - `400`: Display field validation errors or toast message.
  - `409 Conflict`: Display "A promotion with this code already exists" (Create) or "Cannot edit a promotion that has already been used" (Update).
  - `403 Forbidden`: Account not approved or deactivated.

### 5.8 Cancel Form (`btnCancel` onClick)
- **Trigger:** User clicks "Cancel" button.
- **Processing Logic:**
  1. Navigate back to `/merchant/promotions`.
- **Exception Handling:** None.

### 5.10 Theme Toggle (`btnThemeToggle` onClick)
- **Trigger:** User clicks theme toggle button.
- **Processing Logic:**
  1. Toggles Light / Dark mode classes on HTML root.
- **Exception Handling:** None.

### 5.11 Pagination & Limit Change (`PaginationControls`)
- **Trigger:** User clicks pagination page buttons / arrows, or changes per-page selector (`limit`).
- **Processing Logic:**
  1. Update `page` or `limit` query parameters.
  2. Dispatch `GET /api/v1/promotions?page={page}&limit={limit}`.
  3. Re-render table and update total page calculation (`Math.ceil(total / limit)`).
- **Exception Handling:** None.

### 5.12 Restricted Merchant Page Load Behavior
- **Trigger:** User navigates to promotion pages with pending, rejected, or deactivated account status.
- **Processing Logic:**
  1. **Promotions List Page (`/merchant/promotions`):**
     - If `isDeactivated`: Displays `AccountDeactivatedBanner`. CRUD actions hidden (`showCrudActions = false`), switches render as static Yes/No text.
     - If `status === 'pending'`: Displays warning alert banner (`bannerLicensePending`). "Add New Promotion" button hidden, row edit/delete/toggle controls hidden.
     - If `status === 'rejected'`: Displays destructive alert banner (`bannerLicenseRejected`) with link to `/merchant/profile`. CRUD controls hidden.
  2. **Create / Edit Pages (`/merchant/promotions/new`, `/merchant/promotions/:id/edit`):**
     - If deactivated, pending, or rejected: Component displays error toast and immediately redirects to `/merchant/promotions` with `replace: true`.
- **Exception Handling:** 401 redirects to login.

## 11. Special UI Notes & Styling Constraints (特記事項・UI仕様)

- **Design System:** Luxury Cosmetics Theme — Primary `#7C3AED` (Purple), Accent `#EC4899` (Pink), Secondary `#F3E8FF` (Lavender).
- **Responsive Viewport Design:** Full-width form on all breakpoints. Table scrolls horizontally on mobile.
- **Accessibility:** Every control must be keyboard navigable. ARIA labels required. Error messages must be announced via `role="alert"`.
- **Performance:** Promotion list uses skeleton loaders during initial load. Buttons display spinner during async operations.
- **Security:** All user input is sanitized to prevent XSS. Never trust client-side validation alone.
- **Design Tokens:** Status badges use standard color mapping — success: `bg-green-100 text-green-800`, error: `bg-red-100 text-red-800`, warning: `bg-amber-100 text-amber-800`, info: `bg-blue-100 text-blue-800`.
- **Discount Type Badges:** Percentage: `bg-blue-100 text-blue-800`. Fixed: `bg-green-100 text-green-800`.
- **Code Field Styling:** Monospace font (`font-mono`) for promotion codes to improve readability.
