## 1. 機能概要

### 1.1 目的と範囲

本画面は、Cosmetics Finderプラットフォームにおけるプラットフォームの整合性維持のための中心的な管理ハブとして機能します。レビュー・コンテンツ管理サブシステムは、管理者が製品レビューをモデレートし、違反コンテンツを削除し、出品者登録を承認し、プラットフォーム品質基準を適用するために必要な一式の機能を提供します。

本サブシステムは、マーケットプレイス全体の信頼と安全性を確保するために不可欠です。管理者に対して、レビューの承認、却下、削除、プラットフォームポリシーに違反するコンテンツの削除、ユーザーアカウントの管理と監査証跡の維持、プラットフォームポリシーへの準拠を提供するツールを提供することを担当します。

### 1.2 機能責任

本画面は以下のコア機能領域を担当します：

1. **レビューモデレーション** — 全レビューの閲覧、表示中または非表示レビューの承認/却下、不適切レビューの削除と監査ログ記録。レビューはデフォルトで承認済みであり、将来のプレモデレーションモードを明示的に追加しない限り、本画面は公開後モデレーションを対象とします。
2. **コンテンツモデレーション** — プラットフォームポリシーに違反するコンテンツの削除。
3. **出品者登録管理** — ライセンス確認とコンプライアンスチェックに基づく出品者ショップの承認/却下。
4. **ユーザーアカウントモデレーション** — ポリシー違反によるユーザーアカウントの有効化/無効化。

### 1.3 対象ユーザー

| 属性 | 値 |
|-----------|-------|
| **主アクター** | プラットフォーム管理者（管理者） |
| **必要認証** | `admin` ロールを含むJWT Bearer Token |
| **データ範囲** | 全レビュー、製品、出品者、ユーザーアカウント |

## 2. ユースケースとビジネスワークフロー

### 2.1 ユースケースカタログ

| UC-ID | ユースケース名 | 前提条件 | 結果条件 | トリガーアクター |
|-------|---------------|--------------|---------------|------------------|
| UC-MOD-001 | 全レビュー閲覧 | 管理者が `admin` ロールで認証済み。 | フィルタとページネーション付きの全レビュー一覧が表示される。 | 管理者 |
| UC-MOD-002 | レビューモデレート（承認/却下） | レビューが存在し、管理者が認証済み。 | レビューの `is_approved` ステータスが更新される。該当の場合、製品の `avg_rating` と `review_count` が再計算される。 | 管理者 |

| UC-MOD-004 | 違反コンテンツの削除 | コンテンツがプラットフォームポリシーに違反。 | コンテンツが削除または無効化される。監査ログが記録される。 | 管理者 |
| UC-MOD-005 | 出品者登録の承認/却下 | 出品者が `license_status = 'pending'` で存在し、関連ショップが存在する。 | 出品者の `license_status` を更新し、関連する `shops.is_approved` を同期する。 | 管理者 |
| UC-MOD-006 | ユーザーアカウントの有効化/無効化 | ユーザーアカウントが存在。 | ユーザーの `is_active` ステータスが切り替わる。無効化時、ユーザーセッションが終了。 | 管理者 |

## 3. 状態遷移仕様

### 3.1 レビューモデレーションステータス

| ステータス | 説明 | 購入者に表示 | 編集可能 |
|-------|-------------|:-----------------:|:-------------:|
| `APPROVED` | レビューが承認され、製品ページに表示 | ✓ | ✗ |
| `REJECTED` | レビューが却下され、製品ページから非表示 | ✗ | ✗ |
| `PENDING` | 現行DBスキーマでは未対応。将来のプレモデレーションモード用にのみ予約。 | N/A | ✗ |

### 3.2 出品者承認ステータス

| ステータス | 説明 | 製品出品可能 | ダッシュボードアクセス |
|-------|-------------|:-----------------:|:--------------------:|
| `PENDING` | 出品者が登録済み、ショップ作成済み、管理者承認待ち | ✗ | ✓（制限付き） |
| `APPROVED` | 管理者により承認済み、ショップがアクティブ | ✓ | ✓ |
| `REJECTED` | 管理者により却下済み、ショップが無効化 | ✗ | ✓（制限付き） |

### 3.3 製品モデレーションステータス

| ステータス | 説明 | 検索に表示 | 購入可能 |
|-------|-------------|:-----------------:|:----------------:|
| `ACTIVE` | 製品がアクティブで承認済み | ✓ | ✓ |
| `INACTIVE` | 製品が無効化（ソフト削除または管理者アクション） | ✗ | ✗ |

### 3.4 ユーザーアカウントモデレーションステータス

| ステータス | 説明 | ログイン可能 | アクション実行可能 |
|-------|-------------|:---------:|:-------------------:|
| `ACTIVE` | アカウントがアクティブ | ✓ | ✓ |
| `INACTIVE` | 管理者によりアカウント無効化 | ✗ | ✗ |

## 4. ビジネスルール

### 4.1 レビューモデレーションルール

| ルールID | ルール名 | 説明 | 適用層 |
|---------|-----------|-------------|-------------------|
| BR-MOD-001 | 管理者のみモデレート | `admin` ロールを持つユーザーのみがレビューをモデレート可能。 | バックエンド（JwtAuthGuard + RolesGuard） |
| BR-MOD-002 | レビュー承認デフォルト | 新規レビューはデフォルトで承認される（`is_approved = true`）。 | バックエンド（レビュー作成サービス） |
| BR-MOD-003 | 評価再計算 | レビューの承認ステータスが変更された場合、承認済みレビューのみから製品の `avg_rating` と `review_count` を再計算する必要がある。 | バックエンド（モデレーションサービス） |
| BR-MOD-004 | キャッシュ無効化 | レビューステータスが変更された場合、製品キャッシュ（`cache:product:{id}`）と製品リストキャッシュ（`cache:products:list:*`）を無効化する必要がある。 | バックエンド（モデレーションサービス） |
| BR-MOD-005 | 削除カスケード | レビューの削除はそれを完全に削除し、製品統計を再計算する。 | バックエンド（Prisma onDelete: Cascade） |
| BR-MOD-006 | 監査ログ記録 | 全モデレーションアクション（承認、却下、削除）を、管理者ID、ターゲットID、アクション、タイムスタンプとともに記録する必要がある。 | バックエンド（監査インターセプター） |

### 4.2 コンテンツモデレーションルール

| ルールID | ルール名 | 説明 | 適用層 |
|---------|-----------|-------------|-------------------|
| BR-MOD-010 | 製品の可視性 | 承認済み出品者のアクティブな製品（`is_active = true`）のみが購入者向け検索結果に表示される。 | バックエンド（製品クエリフィルター） |
| BR-MOD-011 | 違反コンテンツの削除 | 管理者はプラットフォームポリシーに違反する製品を `is_active = false` に設定して無効化可能。 | バックエンド（モデレーションサービス） |
| BR-MOD-012 | 製品オーナーシップ | 出品者は自分の製品のみを編集/削除可能。管理者は任意の製品をモデレート可能。 | バックエンド（サービス内のオーナーシップチェック） |
| BR-MOD-013 | ソフト削除パターン | 製品は注文履歴の整合性を保持するために、ハード削除ではなく `is_active = false` によるソフト削除が行われる。 | バックエンド（サービスロジック） |

### 4.3 出品者承認ルール

| ルールID | ルール名 | 説明 | 適用層 |
|---------|-----------|-------------|-------------------|
| BR-MOD-020 | 出品者承認必須 | 新規出品者は、出品者機能を利用する前に管理者承認が必要。`merchants.license_status = 'pending'` と `shops.is_approved = false` がデフォルト。 | バックエンド（出品者/ショップ作成） |
| BR-MOD-021 | 未承認出品者制限 | `license_status` が `approved` でない出品者、または未承認ショップの商品は、購入者向け検索結果に表示されない。 | バックエンド（製品クエリフィルター） |
| BR-MOD-022 | 理由付き却下 | 管理者は出品者を理由付きで却下でき、理由は `merchants.rejection_reason` に保存される。 | バックエンド（モデレーションDTO） |
| BR-MOD-023 | 再有効化時の再承認 | 承認済み出品者/ショップが無効化された場合、出品者機能と公開表示を戻す前に再承認が必要。 | バックエンド（ステータス遷移） |

### 4.4 ユーザーモデレーションルール

| ルールID | ルール名 | 説明 | 適用層 |
|---------|-----------|-------------|-------------------|
| BR-MOD-040 | 管理者のみユーザーモデレート | `admin` ロールを持つユーザーのみがユーザーアカウントを有効化/無効化可能。 | バックエンド（RolesGuard） |
| BR-MOD-041 | セッション終了 | ユーザーが無効化された場合、全アクティブセッション（リフレッシュトークン）を取消すべき。 | バックエンド（トークン取消） |
| BR-MOD-042 | 自己無効化防止 | 管理者は自分のアカウントを無効化できない。 | バックエンド（オーナーシップチェック） |

## 6. 機能操作仕様

### 6.1 操作：レビューの閲覧

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | 管理者が /admin/reviews に遷移、またはレビューステータスフィルタを変更 |
| **APIエンドポイント** | `GET /api/v1/admin/reviews` |
| **リクエストクエリパラメータ** | `page`（デフォルト：1）、`limit`（デフォルト：20）、`sort`（デフォルト：`createdAt`）、`order`（デフォルト：`desc`）、`status`（`approved`/`rejected`/未指定で全件） |
| **送信前バリデーション** | JWTアクセストークン検証。管理者ロール確認。 |
| **処理ステップ** | 1. JWTアクセストークンを検証。2. RolesGuardで管理者ロールを確認。3. フィルタ付きで `reviews` テーブルをクエリ。4. 表示データのために `users` と `products` を結合。5. ページネーション適用。6. メタデータ付きページネーション済みレビュー一覧を返却。 |
| **成功レスポンス** | 200 OK（ページネーション済みレビューデータ） |
| **後処理** | モデレーションアクション付きレビュー一覧を表示 |

### 6.2 操作：レビューモデレーション（承認/却下）

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | 管理者がレビューの「承認」または「却下」をクリック |
| **APIエンドポイント** | `POST /api/v1/admin/reviews/:id/moderate` |
| **リクエストContent-Type** | `application/json` |
| **リクエストボディ** | `{ action: 'approve' | 'reject', reason?: string }` |
| **送信前バリデーション** | JWTアクセストークン検証。管理者ロール確認。レビュー存在確認。却下時は理由必須。 |
| **処理ステップ** | 1. JWTと管理者ロールを検証。2. IDでレビューを検索。3. action = 'reject' の場合、理由の提供をバリデーション。4. アクションに基づいて `reviews.is_approved` を更新。5. 承認済みレビューのみから製品の `avg_rating` と `review_count` を再計算。6. Redisで製品キャッシュを無効化。7. Redisで製品リストキャッシュを無効化。8. 監査証跡にモデレーションアクションをログ記録。9. 更新されたレビューデータを返却。 |
| **成功レスポンス** | 200 OK（更新されたReview DTO） |
| **後処理** | トースト通知を表示。レビュー一覧をリフレッシュ。 |

### 6.3 操作：レビュー削除

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | 管理者がレビューの「削除」を確認ダイアログ付きでクリック |
| **APIエンドポイント** | `DELETE /api/v1/admin/reviews/:id` |
| **リクエストヘッダー** | `Authorization: Bearer <accessToken>` |
| **送信前バリデーション** | JWTアクセストークン検証。管理者ロール確認。レビュー存在確認。 |
| **処理ステップ** | 1. JWTと管理者ロールを検証。2. IDでレビューを検索。3. データベースからレビューをハード削除。4. 残りの承認済みレビューから製品の `avg_rating` と `review_count` を再計算。5. Redisで製品キャッシュを無効化。6. Redisで製品リストキャッシュを無効化。7. 監査証跡に削除アクションをログ記録。8. 204 No Content を返却。 |
| **成功レスポンス** | 204 No Content |
| **後処理** | トースト通知を表示。レビュー一覧をリフレッシュ。 |

## 9. エラー処理仕様

### 9.1 エラーレスポンス構造

```json
{
  "statusCode": 400,
  "message": ["action must be one of the following values: approve, reject"],
  "error": "Bad Request",
  "timestamp": "2026-08-07T12:00:00.000Z",
  "path": "/api/v1/admin/reviews/abc123/moderate"
}
```

### 9.2 エラー分類表 — レビューモデレーション

| HTTPステータス | エラーコード | シナリオ | ユーザー向け動作 |
|-------------|------------|----------|---------------------|
| `400` | `BAD_REQUEST` | バリデーション失敗（action、reasonの欠落） | フィールドレベルインラインエラー + トップバナー |
| `403` | `FORBIDDEN` | 非管理者ユーザーによるモデレート試行 | "このアクションを実行する権限がありません" |
| `404` | `NOT_FOUND` | レビューが見つからない | "レビューが見つかりません"（戻るリンク付き） |
| `409` | `CONFLICT` | レビューが既に対象ステータス | "レビューは既に承認済み/却下済みです" |
| `500` | `INTERNAL_SERVER_ERROR` | サーバーエラー | "問題が発生しました。再試行してください" |

### 9.3 エラー分類表 — 出品者管理

| HTTPステータス | エラーコード | シナリオ | ユーザー向け動作 |
|-------------|------------|----------|---------------------|
| `400` | `BAD_REQUEST` | バリデーション失敗 | フィールドレベルインラインエラー |
| `403` | `FORBIDDEN` | 非管理者ユーザー | "権限がありません" |
| `404` | `NOT_FOUND` | 出品者/ショップが見つからない | "出品者が見つかりません" |
| `409` | `CONFLICT` | 出品者が既に対象ステータス | "出品者は既に承認済み/却下済みです" |
| `500` | `INTERNAL_SERVER_ERROR` | サーバーエラー | "問題が発生しました。再試行してください" |

### 9.4 フロントエンドエラー表示動作

- **フィールドレベルバリデーション**：無効な入力の下に赤いボーダーとインラインテキスト。
- **フォームレベルサマリー**：フォーム上部に全エラーをリストするアラートバナー。
- **トースト通知**：APIエラーと成功アクションに使用。
- **読み込み状態**：API呼び出し中の送信ボタンにスピナー。
- **確認ダイアログ**：デストラクティブアクション（レビュー削除、出品者却下）に必須。

## 10. 権限・アクセス制御

### 10.1 認証要件

- 全管理者エンドポイントで `Authorization` ヘッダー経由のJSON Web Token（JWT）Bearer Token。
- トークンにはペイロードに `role: 'admin'` を含む必要がある。

### 10.2 管理者エンドポイントアクセス制御

| エンドポイント | アクセスレベル | 説明 |
|----------|-------------|-------------|
| `GET /admin/reviews` | 保護済み（管理者） | 全レビューの閲覧（承認済み/却下済みフィルタ任意） |
| `POST /admin/reviews/:id/moderate` | 保護済み（管理者） | レビューの承認/却下 |
| `DELETE /admin/reviews/:id` | 保護済み（管理者） | レビューの削除 |
| `GET /admin/users` | 保護済み（管理者） | 全ユーザーの閲覧 |
| `PATCH /admin/users/:id/status` | 保護済み（管理者） | ユーザーの有効化/無効化 |
| `GET /admin/merchants` | 保護済み（管理者） | 全出品者の閲覧 |
| `PATCH /admin/merchants/:id/status` | 保護済み（管理者） | 出品者の承認/却下 |

### 10.3 ロールベースアクセス

| ロール | レビュー閲覧 | レビューモデレート | 出品者管理 | ユーザー管理 |
|------|:----------------:|:--------------------:|:--------------------:|:----------------:|
| `buyer` | ✗ | ✗ | ✗ | ✗ |
| `merchant` | 自分の製品のみ | ✗ | ✗ | ✗ |
| `admin` | ✓ | ✓ | ✓ | ✓ |

### 10.4 セキュリティ監査ログ

| イベント | ログデータ | 保持期間 |
|-------|-------------|-----------|
| `REVIEW_APPROVED` | adminId, reviewId, productId, タイムスタンプ | 2年 |
| `REVIEW_REJECTED` | adminId, reviewId, productId, reason, タイムスタンプ | 2年 |
| `REVIEW_DELETED` | adminId, reviewId, productId, タイムスタンプ | 2年 |
| `MERCHANT_APPROVED` | adminId, shopId, merchantId, タイムスタンプ | 2年 |
| `MERCHANT_REJECTED` | adminId, shopId, merchantId, reason, タイムスタンプ | 2年 |
| `USER_DEACTIVATED` | adminId, userId, タイムスタンプ | 2年 |
| `USER_ACTIVATED` | adminId, userId, タイムスタンプ | 2年 |
| `RBAC_VIOLATION` | userId, endpoint, requiredRole, タイムスタンプ | 30日 |

## 11. リアルタイム通知動作

### 11.1 管理者ダッシュボード通知

管理者ダッシュボードは、保留中のモデレーションアイテムのリアルタイム更新を受信します：

| イベント | トリガー | アクション |
|-------|---------|--------|
| `NEW_MERCHANT_REGISTRATION` | 新規出品者登録 | 保留中出品者承認バッジのインクリメント |
| `REVIEW_CREATED` | 新規レビュー送信 | 合計レビューバッジをインクリメント。レビューはデフォルトで承認済み |

### 11.2 モデレーション後WebSocket更新

モデレーションアクション後、関係者に通知：

| イベント | トリガー | 受信者 | アクション |
|-------|---------|------------|--------|
| `REVIEW_STATUS_CHANGED` | 管理者がレビューを承認/却下 | レビュー投稿者、製品出品者 | トースト通知 |
| `MERCHANT_STATUS_CHANGED` | 管理者が出品者を承認/却下 | 出品者ユーザー | ウェブサイト通知 |
| `CONTENT_REMOVED` | 管理者が製品を無効化 | 製品出品者 | トースト通知 |
| `USER_STATUS_CHANGED` | 管理者がユーザーを有効化/無効化 | 対象ユーザー | 無効化時にセッション終了 |

## 13. 非機能的考慮事項

### 13.1 パフォーマンス要件

| 指標 | 目標 |
|--------|--------|
| 管理者ダッシュボード読み込み | ≤ 2秒 |
| レビュー一覧APIレスポンス | ≤ 500ミリ秒 |
| モデレーションアクションレスポンス | ≤ 300ミリ秒 |
| 検索/フィルタレスポンス | ≤ 3秒（10,000レビュー） |
| キャッシュ無効化 | ≤ 50ミリ秒（Redis DEL） |

### 13.2 セキュリティ考慮事項 | Concern | Mitigation |
|---------|------------|
| 不正アクセス | 全管理者エンドポイントでJwtAuthGuard + RolesGuard |
| RBACバイパス | バックエンドのみで強制。フロントエンドは決して信頼しない |
| 監査証跡改ざん | 管理者ID追跡付き追記専用監査ログ |
| 一括操作 | 管理者エンドポイントのレート制限（100リクエスト/分） |
| デストラクティブアクション | 削除/却下アクションに確認ダイアログ必須 |
| セッション取消 | ユーザー無効化時に全リフレッシュトークンを取消 |

### 13.3 レスポンシブデザイン要件

| ブレークポイント | レイアウト |
|------------|--------|
| デスクトップ（≥ 1024px） | フルサイドバ + モーダルオーバーレイ付きテーブルレイアウト |
| タブレット（768px – 1023px） | 折りたたみサイドバ + レスポンシブテーブル |
| モバイル（< 768px） | ボトムナビゲーション + スタックカード（管理者モバイルは主要ターゲット外） |
