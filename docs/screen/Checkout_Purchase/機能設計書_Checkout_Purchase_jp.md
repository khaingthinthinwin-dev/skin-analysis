## 1. 機能概要

### 1.1 目的と範囲

本画面は、Cosmetics Finderプラットフォームのチェックアウトと注文管理の完全な機能を提供する。チェックアウトサブシステムは、注文確認から決済方法選択、注文確定に至るまでの購入ワークフローを処理する。注文サブシステムは、認証されたバイヤー向けに注文履歴、注文詳細、注文追跡を管理する。

これらのサブシステムは、eコマースワークフローの最終段階であり、カート内容を確認済み注文に変換する。在庫確認、クーポン割引適用、合計計算、出品者履行およびバイヤー追跡のための注文記録永続化を行う。

### 1.2 機能責務

本画面は以下のコア機能領域を担当する：

1. **チェックアウトフロー** — 配送先住所入力、決済方法選択、クーポン適用、注文サマリー確認を経て、最終確定までユーザーを案内する。
2. **クーポン検証** — チェックアウト時に割引コード（パーセンテージまたは固定額）を検証・適用し、有効期限、最低注文額、1回限りの制約を適用する。
3. **注文計算** — カート商品と適用クーポンに基づき、小計、割引額、最終合計を計算する。
4. **注文登録** — ステータス`placed`で注文記録を作成し、在庫を原子的に減算し、カートをクリアし、注文確認を返す。
5. **スポンサー広告表示** — 出品者が購入した広告パッケージの承認済み・有効・掲載期間内の広告を、パッケージ掲載枠およびティア優先度ルールを適用してチェックアウト画面にスライドダウン広告パネルとして描画する。
6. **注文履歴** — 過去の全注文のページネーション付きリストを、ステータス、日付、合計、商品数とともに表示する。
7. **注文詳細** — 商品、配送先住所、決済ステータス、注文タイムラインを含む完全な注文情報を表示する。
8. **注文追跡** — タイムライン可視化と推定配送日のリアルタイム注文ステータス追跡を提供する。
9. **通知配信** — バイヤーおよび関連する出品者に注文確認およびステータス変更通知を送信する。

### 1.3 対象ユーザー

| 属性 | 値 |
|------|-----|
| **主要アクター** | 認証済みバイヤー (Authenticated Buyer) |
| **認証要件** | JWTベアラートークン |
| **データスコープ** | 自身の注文、自身の配送先住所、自身の決済記録 |
| **ゲストユーザーの動作** | チェックアウト不可。ゲストユーザーが`/checkout`にアクセスを試みた場合、アラートモーダルを表示：「購入を完了するにはログインしてください。」[ログイン]をクリックするとログインページ`/login`に遷移する。 |

## 3. 状態遷移仕様

### 3.1 注文ステータス状態

| `packed` | 注文梱包済み、出荷準備完了 | ✗ | ✓（→`shipped`） | ✓ |
| `shipped` | 注文が配送業者に発送済み | ✗ | ✓（→`out_for_delivery`） | ✓ |
| `out_for_delivery` | 注文がバイヤーへの配送中 | ✗ | ✗ | ✓ |
| `delivered` | バイヤーが注文を受領 | ✗ | ✗ | ✓ |

#### 6.4.1 チェックアウト永続化およびトランザクション設計

以下のすべての書き込みステップは1つのデータベーストランザクション内で実行される。サービスは選択された商品行に対して行レベルロック（または同等の条件付き更新）を使用し、在庫が最新のコミット済み値に対して再確認されるようにする。いずれかのステップで失敗した場合は、注文、注文商品、在庫変更、在庫履歴レコード、クーポン更新、カート変更がロールバックされ、バイヤーや出品者に部分的な注文が公開されることはない。

##### A. カート統合ロジック (`carts`, `cart_items` から `orders`, `order_items`)

1. `carts.user_id`が認証済みバイヤーIDと一致する単一のカートを、その`cart_items`および参照される`products`とともに読み込む。
2. カートが存在しないか商品が含まれていない場合は`400 BAD_REQUEST`でリクエストを拒否する。参照されている商品が無効、利用不可、無効な出品者に属している、または在庫が不足している場合は`409 CONFLICT`で拒否する。
3. カート商品を`products.merchant_id`でグループ化する。`orders`行は1つの`merchant_id`を持つため、出品者グループごとに1つの注文を作成する。すべてのグループが作成できる場合にのみリクエストは成功し、それ以外の場合は完全なトランザクションがロールバックされる。単一出品者のカートの場合、1つの注文が生成される。
4. 各グループについて、クライアント入力からではなく、ロックされた商品レコードから価格と合計を計算する。`buyer_id`、グループの`merchant_id`、配送/決済フィールド、計算された金額、および`status = 'placed'`を指定して`orders`に挿入する。
5. ソースの`cart_items`行ごとに1つの`order_items`行を挿入し、`product_id`、`merchant_id`、要求された`quantity`、現在の正式な商品価格を`unit_price`として、`quantity * unit_price`を`total_price`としてコピーする。`cart_items`は可変の買い物意図のままであり、`order_items`は不変の購入スナップショットとなる。
6. 注文商品に正常に変換された`cart_items`行のみを削除する。すべての行が消費された後、バイヤーの空の`carts`行をその後の使用のために保持する。チェックアウトが失敗した場合、カートは変更されないまま残る。

##### B. 在庫トランザクションロジック (`inventory_transactions`)

作成された各`order_items`行について、ロックされた`products.stock_quantity`を`before_quantity`として読み取り、`before_quantity >= order_items.quantity`を検証し、商品在庫を`after_quantity = before_quantity - order_items.quantity`に更新する。同一トランザクション内で以下を含む`inventory_transactions`行を挿入する：

| イベント | `transaction_type` | `quantity` | `before_quantity` / `after_quantity` | 参照・監査フィールド |
|-------|--------------------|------------|----------------------------------------|----------------------------|
| 注文確定 | `order_created` | `-order_items.quantity` | 減算直前/直後の在庫数 | `product_id`, `merchant_id`, `reference_type = 'order'`, `reference_id = orders.id`, `reason = 'Checkout order placed'`, `created_by = buyer_id` |

トランザクションログは追加専用（append-only）であり、通常の運用中に`order_created`行が編集または削除されることはない。

##### C. 注文ステータス履歴追跡 (`order_status_history`)

`orders.status`は現在の状態を保持し、`order_status_history`は正式な時系列監査証跡となる。名前付きステータスを`order_statuses`マスター行に解決し、`orders.status`が変更されるたびに同一データベーストランザクション内で正確に1つの履歴行を挿入する。

| 遷移 | `orders.status` 更新 | 履歴レコード |
|------------|------------------------|----------------|
| チェックアウト成功 | `placed`として作成 | `order_id`、`placed`ステータスID、`changed_by = buyer_id`、および備考`Order placed via checkout`を挿入。 |
| 出品者が確認 | `placed`から`confirmed` | `confirmed`ステータスID、`changed_by = merchant user ID`、およびオプションの運用備考を挿入。 |
| システム/配送業者の履行遷移 | 許可された次の状態へ更新 | 対象のステータスIDを挿入。`changed_by`は既知の場合は実行ユーザー、それ以外は`NULL`、システム/配送業者備考付き。 |

ステータス履歴行は通常の運用中に更新または削除されることはない。注文追跡APIは`order_status_history`を`order_statuses`に結合し、`created_at ASC`（同値の場合は`id ASC`）でソートし、各ステータス、タイムスタンプ、許可されている場合はアクター、および備考を返却する。サービスはいずれかのテーブルを更新する前に、無効または終端状態の遷移を拒否する。

| **トリガー** | 注文詳細の「注文追跡」ボタンクリック |
| **APIエンドポイント** | `GET /api/v1/orders/:id/tracking` |
| **リクエストヘッダー** | `Authorization: Bearer <accessToken>` |
| **送信前バリデーション** | ユーザー認証済み、注文が存在しユーザーに属する |
| **処理ステップ** | 1. JWTトークンを検証。 2. IDで注文を検索。 3. `buyer_id = user.id`を検証。 4. 注文履歴からステータスタイムラインを構築。 5. 推定配送日を計算。 6. 追跡データを返却。 |
| **成功レスポンス** | 200 OK（追跡タイムラインと推定配送日を含む） |

- **空状態**: 履歴に注文が存在しない場合に表示。

## 10. 権限・アクセス制御

### 10.1 認証要件

- すべてのチェックアウトおよび注文エンドポイントに対して、`Authorization`ヘッダー経由でJSON Web Token（JWT）ベアラートークンを渡す。
- セッション管理のためhttpOnlyクッキーにリフレッシュトークンを保存。

### 10.2 公開 vs 保護エンドポイント

| エンドポイント | アクセスレベル | 説明 |
|----------|-------------|-------------|
| `GET /checkout` | 保護（バイヤー） | チェックアウト画面データの読み込み |
| `GET /ads` | 公開（キャッシュ済み） | チェックアウト用スポンサー広告枠の読み込み |
| `POST /checkout/validate-coupon` | 保護（バイヤー） | クーポンの検証および適用 |
| `POST /orders` | 保護（バイヤー） | 新規注文の登録 |
| `GET /orders` | 保護（バイヤー） | 注文履歴の表示 |
| `GET /orders/:id` | 保護（バイヤー） | 注文詳細の表示 |
| `GET /orders/:id/tracking` | 保護（バイヤー） | 注文ステータスの追跡 |

### 10.3 ロールベースアクセス

| ロール | チェックアウトアクセス可 | 注文登録可 | 履歴表示可 |
|------|:-------------------:|:----------------:|:----------------:|
| `buyer` | ✓ | ✓ | ✓ |
| `merchant` | ✗ | ✗ | ✗ |
| `admin` | ✗ | ✗ | ✗ |

### 10.4 所有権ルール

| リソース | 所有権ルール | 適用方式 |
|----------|---------------|-------------|
| 注文 | ユーザーは自身の注文のみ表示/変更可能 | バックエンドでJWTの`buyer_id`によりフィルタリング |
| 注文商品 | 注文の所有権から継承 | バックエンドで注文結合によりフィルタリング |
| クーポン | クーポンは出品者が作成、バイヤーが適用 | バックエンドでクーポンの存在と条件を検証 |

|---------|------------|
| 不正アクセス | 全エンドポイントでのJWTベアラートークン検証 |
| 価格改ざん | クライアント提供値ではなく、注文作成時にDBから価格を取得 |
| 在庫改ざん | Prismaトランザクション内での原子的在庫減算 |
| IDOR攻撃 | 所有権検証（JWTからの`buyer_id`） |
| 在庫の競合状態 | Prismaを介した行レベルロックによる原子的操作 |
| クーポンの二重使用 | 注文トランザクション内でのクーポンused_count原子的インクリメント |
| 不正決済 | 決済ステータス追跡（MVPではスタブ、本番ゲートウェイ連携は将来） |
| 注文データ漏洩 | 認証済みユーザーのみに注文スコープを限定 |

### 13.4 レスポンシブデザイン要件

| ブレークポイント | チェックアウトレイアウト | 注文履歴レイアウト |
|------------|-----------------|---------------------|
| デスクトップ (≥ 1024px) | 2カラム：左サマリー、右フォーム。広告パネルは横型（画像左、テキスト右）、カラム上部に全幅表示。 | 全幅テーブル |
| タブレット (768px – 1023px) | 2カラム：左サマリー、右フォーム（幅狭）。広告パネルは横型（画像左、テキスト右）、カラム上部に全幅表示。 | 全幅テーブル（コンパクト） |
| モバイル (< 768px) | 1カラム：サマリー、次にフォーム。広告パネルは縦積み（画像上、コンテンツ下）、ヘッダーとフォームの間に全幅表示。 | カードベースのリスト |
