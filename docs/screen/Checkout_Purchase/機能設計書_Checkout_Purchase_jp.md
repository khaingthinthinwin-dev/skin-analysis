## 1. 機能概要

### 1.1 目的と範囲

本画面は、Cosmetics Finderプラットフォームのチェックアウトと注文管理の完全な機能を提供する。チェックアウトサブシステムは、注文確認から決済方法選択、注文確定に至るまでの購入ワークフローを処理する。注文サブシステムは、認証されたバイヤー向けに注文履歴、注文詳細、注文追跡を管理する。

これらのサブシステムは、eコマースワークフローの最終段階であり、カート内容を確認済み注文に変換する。在庫確認、クーポン割引適用、合計計算、商家履行およびバイヤー追跡のための注文記録永続化を行う。

### 1.2 機能 responsibilities

本画面は以下のコア機能領域を担当する：

1. **チェックアウトフロー** — 配送先住所入力、決済方法選択、クーポン適用、注文摘要確認を経て、最終確定までユーザーを案内する。
2. **クーポン検証** — チェックアウト時に割引コード（パーセンテージまたは固定額）を検証・適用し、有効期限、最低注文額、一回限りの制約を適用する。
3. **注文計算** — カート商品と適用クーポンに基づき、小計、割引額、最終合計を計算する。
4. **注文登録** — ステータス`placed`で注文記録を作成し、在庫を原子的に減算し、カートをクリアし、注文確認を返す。
5. **注文履歴** — 過去の全注文のページネーション付きリストを、ステータス、日付、合計、商品数とともに表示する。
6. **注文詳細** — 商品、配送先住所、決済ステータス、注文タイムラインを含む完全な注文情報を表示する。
7. **注文追跡** — タイムライン可視化と推定配送日のリアルタイム注文ステータス追跡を提供する。
8. **通知配信** — バイヤーおよび関連する商家に注文確認およびステータス変更通知を送信する。

### 1.3 対象ユーザー

| 属性 | 値 |
|------|-----|
| **プライマリアクター** | 認証済みバイヤー |

| **データスコープ** | 自分の注文、自分の配送先住所、自分の決済記録 |

## 3. 状態遷移仕様

### 3.1 注文ステータス状態

| 状態 | 説明 | バイヤーキャンセル可 | メルチャント更新可 | 履歴に表示 |
|------|------|:------------------:|:-----------------:|:----------:|
| `placed` | 注文作成済み、メルチャント確認待ち | ✓ | ✓（→`confirmed`） | ✓ |
| `confirmed` | メルチャントが注文を承認 | ✓ | ✓（→`packed`） | ✓ |
| `packed` | 注文梱包済み、出荷準備完了 | ✗ | ✓（→`shipped`） | ✓ |
| `shipped` | 注文が配送業者に発送済み | ✗ | ✓（→`out_for_delivery`） | ✓ |
| `out_for_delivery` | 注文がバイヤーへの配送中 | ✗ | ✗ | ✓ |
| `delivered` | バイヤーが注文を受領 | ✗ | ✗ | ✓ |

### 3.2 決済ステータス状態

| 状態 | 説明 | 返金可 |
|------|------|:------:|
| `pending` | 決済未処理 | いいえ |
| `completed` | 決済処理成功 | はい |
| `failed` | 決済処理失敗 | いいえ |
| `refunded` | バイヤーに返金済み | いいえ |

### 3.3 注文ステータス遷移

| 遷移ID | 元状態 | 目標状態 | トリガーアクション | ガード条件 |
|--------|--------|---------|-------------------|-----------|
| TR-ORDER-01 | `placed` | `confirmed` | メルチャントが注文を確認 | メルチャントが在庫、配送情報を検証 |
| TR-ORDER-02 | `confirmed` | `packed` | メルチャントが注文を梱包 | — |
| TR-ORDER-03 | `packed` | `shipped` | メルチャントが注文を発送 | 配送業者割り当て、追跡番号提供 |
| TR-ORDER-04 | `shipped` | `out_for_delivery` | 配送業者が配送を開始 | — |
| TR-ORDER-05 | `out_for_delivery` | `delivered` | バイヤーが注文を受領 | バイヤー確認または7日後自動確認 |

### 3.4 チェックアウトフォーム状態

| 状態 | 説明 | 送信可 |
|------|------|:------:|
| `IDLE` | フォーム読み込み済み、未操作 | いいえ |
| `EDITING` | ユーザーが配送先住所を入力中 | いいえ |

## 6. 機能操作仕様

### 6.1 操作：チェックアウト画面読み込み

| 属性 | 仕様 |
|------|------|
| **トリガー** | カートページから`/checkout`にナビゲーション |
| **APIエンドポイント** | `GET /api/v1/checkout` |

#### 6.3.1 チェックアウト永続化とトランザクション設計

以下の全書き込みステップは1つのデータベーストランザクション内で実行される。サービスは選択された商品行に対して行レベルロック（または同等の条件付き更新）を使用し、最新のコミット値に対して在庫を再検証する。いずれかのステップで失敗した場合、注文、注文商品、在庫変更、在庫記録、クーポン更新、カート変更をロールバックし、バイヤーまたはメルチャントに部分的な注文が公開されることはない。

##### A. カート統合ロジック（`carts`、`cart_items` → `orders`、`order_items`）

1. 認証済みバイヤーIDに一致する`carts.user_id`の単一カートを、`cart_items`と参照された`products`とともに読み込む。
2. カートが存在しないか、商品がない場合、`400 BAD_REQUEST`でリクエストを拒否。参照された商品が非アクティブ、利用不可、無効なメルチャントに属する、または在庫不足の場合、`409 CONFLICT`で拒否。
3. `products.merchant_id`でカート商品をグループ化。`orders`行には1つの`merchant_id`があるため、メルチャントグループごとに1つの注文を作成。全グループが作成可能な場合のみリクエスト成功。否则はトランザクション全体をロールバック。単一メルチャントのカートでは1つの注文が生成される。
4. 各グループについて、ロックされた商品レコードから価格と合計を計算。クライアント入力ではなく、`buyer_id`、グループ`メルチャントID`、配送/決済フィールド、計算された金額、`status = 'placed'`で`orders`を挿入。
5. ソース`cart_items`行ごとに1つの`order_items`行を挿入。`product_id`、`merchant_id`、要求された`quantity`、現在の商品価格を`unit_price`として、`quantity * unit_price`を`total_price`としてコピー。`cart_items`は変更可能な購入意図；`order_items`は不変の購入スナップショット。
6. 注文商品に変換された`cart_items`行のみを削除。全行が消費された後、買い手の空の`carts`行を後続使用のために保持。チェックアウト失敗時はカートを変更しない。

##### B. 在庫トランザクションロジック（`inventory_transactions`）

作成された各`order_items`行について、ロックされた`products.stock_quantity`を`before_quantity`として読み込み、`before_quantity >= order_items.quantity`を検証し、製品在庫を`after_quantity = before_quantity - order_items.quantity`に更新。同じトランザクション内で`inventory_transactions`行を以下で挿入：

| イベント | `transaction_type` | `quantity` | `before_quantity` / `after_quantity` | 参照および監査フィールド |
|---------|--------------------|------------|--------------------------------------|----------------------|
| 注文確認 | `order_created` | `-order_items.quantity` | 減算直前/直後の在庫 | `product_id`、`merchant_id`、`reference_type = 'order'`、`reference_id = orders.id`、`reason = 'Checkout order placed'`、`created_by = buyer_id` |

在庫トランザクションログは追加専用：`order_created`行は通常運用中に編集または削除されることはない。

##### C. 注文ステータス履歴追跡（`order_status_history`）

`orders.status`は現在の状態を保持し、`order_status_history`は正式な時系列監査証跡。各名前付きステータスを`order_statuses`マスタ行に解決し、`orders.status`が変更されるたびに同じデータベーストランザクションで正確に1つの履歴行を挿入。

| 遷移 | `orders.status`更新 | 履歴レコード |
|------|---------------------|-------------|
| チェックアウト成功 | `placed`として作成 | `order_id`、`placed`ステータスID、`changed_by = buyer_id`、注記`Order placed via checkout`を挿入 |
| メルチャント確認 | `placed` → `confirmed` | `confirmed`ステータスID、`changed_by = メルチャーユーザーID`、オプションの運用注記を挿入 |
| システム/配送業者履行遷移 | 許可された次の状態に更新 | 対象ステータスIDを挿入；`changed_by`は既知の場合アクティングユーザー、否则は`NULL`、システム/配送業者注記付き |

ステータス履歴行は通常運用中に更新または削除されることはない。注文追跡APIは`order_status_history`を`order_statuses`に結合し、`created_at ASC`（次に`id ASC`）でソートし、各ステータス、タイムスタンプ、許可された場合のアクター、注記を返す。サービスは either テーブルを更新する前に無効または終了状態の遷移を拒否する。

| `400` | `BAD_REQUEST` | クーポン使用回数制限到達 | トースト：「クーポンの使用回数上限に達しました」 |
| `401` | `UNAUTHORIZED` | JWTトークン不足または無効 | ログインにリダイレクト |
| `403` | `FORBIDDEN` | バイヤー以外のロール（メルチャント/管理者） | トースト：「買い物機能はバイヤーのみ利用可能です」 |
| `409` | `CONFLICT` | 送信時の在庫不足 | トースト：「一部の商品は現在利用できません。カートを確認してください。」 |
| `500` | `INTERNAL_SERVER_ERROR` | サーバーエラー | トースト：「エラーが発生しました。もう一度お試しください。」 |

### 9.3 エラー分類表 — 注文履歴・詳細

| HTTPステータス | エラーコード | シナリオ | ユーザー向け動作 |
|---------------|------------|---------|----------------|
| `401` | `UNAUTHORIZED` | JWTトークン不足または無効 | ログインにリダイレクト |
| `404` | `NOT_FOUND` | 注文が見つからない | トースト：「注文が見つかりません」 |
| `403` | `FORBIDDEN` | 別のユーザーの注文にアクセス | トースト：「注文が見つかりません」 |
| `500` | `INTERNAL_SERVER_ERROR` | サーバーエラー | トースト：「エラーが発生しました。もう一度お試しください。」 |

### 9.5 フロントエンドエラー表示動作

- **フィールドレベルバリデーション**：無効な入力の下に赤枠とインラインテキスト。
- **トースト通知**：APIエラーと成功アクション（注文登録）に使用。
- **ローディング状態**：「注文する」ボタンにスピナー；送信中にフルページオーバーレイ。
- **在庫警告**：チェックアウト中に在庫変更が検出された場合のアラートバナー。
- **空状態**：履歴に注文が存在しない場合に表示。

## 10. 権限・アクセス制御

### 10.1 認証要件

- 全チェックアウトおよび注文エンドポイントで`Authorization`ヘッダー経由でJSON Web Token（JWT）ベアラートークンを渡す。
- リフレッシュトークンはhttpOnlyクッキーに保存し、セッション管理に使用。

### 10.2 パブリック vs プロテクテッドエンドポイント

| エンドポイント | アクセスレベル | 説明 |
|--------------|---------------|------|
| `GET /checkout` | プロテクテッド（バイヤー） | チェックアウト画面データ読み込み |
| `POST /checkout/validate-coupon` | プロテクテッド（バイヤー） | クーポン検証・適用 |
| `POST /orders` | プロテクテッド（バイヤー） | 新規注文登録 |
| `GET /orders` | プロテクテッド（バイヤー） | 注文履歴表示 |
| `GET /orders/:id` | プロテクテッド（バイヤー） | 注文詳細表示 |
| `GET /orders/:id/tracking` | プロテクテッド（バイヤー） | 注文ステータス追跡 |

### 10.3 ロールベースアクセス

| ロール | チェックアウトアクセス可 | 注文登録可 | 履歴表示可 |
|--------|:----------------------:|:---------:|:---------:|
| `buyer` | ✓ | ✓ | ✓ |
| `merchant` | ✗ | ✗ | ✗ |
| `admin` | ✗ | ✗ | ✗ |

### 10.4 所有者ルール

| リソース | 所有者ルール | 適用 |
|---------|-------------|------|
| 注文 | ユーザーは自分の注文のみ表示/変更可能 | バックエンドがJWTの`buyer_id`でフィルタリング |
| 注文商品 | 注文の所有者から継承 | バックエンドが注文結合でフィルタリング |
| クーポン | クーポンはメルチャント作成、バイヤー適用 | バックエンドがクーポンの存在を検証 |

## 13. 非機能要件

### 13.1 パフォーマンス要件

| 指標 | 目標値 |
|------|--------|
| チェックアウト画面読み込み | ≤ 2秒 |
| 注文登録API | ≤ 2秒 |
| クーポン検証API | ≤ 500ミリ秒 |
| 注文履歴画面読み込み | ≤ 2秒 |
| 注文詳細画面読み込み | ≤ 1秒 |
| 在庫検証チェック | ≤ 100ミリ秒 |

### 13.2 キャッシュ戦略

| キャッシュ対象 | 戦略 | TTL |
|--------------|------|-----|
| 商品価格 | DBからリアルタイム | — |
| 在庫数量 | DBからリアルタイム | — |
| クーポン検証 | キャッシュなし（最新である必要あり） | — |
| 注文データ | キャッシュなし（ユーザー固有、リアルタイム） | — |

### 13.3 セキュリティ考慮事項

| 課題 | 対策 |
|------|------|
| 不正アクセス | 全エンドポイントでJWTベアラートークン検証 |
| 価格改ざん | 注文作成時にDBから価格を取得（クライアント提供ではない） |
| 在庫改ざん | Prismaトランザクション内で原子的な在庫減算 |
| IDOR攻撃 | 所有者検証（JWTのbuyer_id） |
| 在庫の競合状態 | Prisma経由の行レベルロックによる原子的操作 |
| クーポン二重使用 | 注文トランザクション内で原子的なクーポンused_countインクリメント |
| 決済不正 | 決済ステータス追跡（MVPではスタブ；実際のゲートウェイ統合は延期） |
| 注文データ漏洩 | 認証済みユーザーにのみ注文をスコープ |

### 13.4 レスポンシブデザイン要件

| ブレークポイント | チェックアウトレイアウト | 注文履歴レイアウト |
|----------------|----------------------|------------------|
| デスクトップ（≥ 1024px） | 2カラム：摘要左、フォーム右 | 全幅テーブル |
| タブレット（768px〜1023px） | 2カラム：摘要左、フォーム右（狭め） | 全幅テーブル（コンパクト） |
| モバイル（< 768px） | 1カラム：摘要、次にフォーム | カードベースリスト |
