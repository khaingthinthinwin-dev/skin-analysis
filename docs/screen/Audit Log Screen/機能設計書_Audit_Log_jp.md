## 1. 機能概要

### 1.1 目的と範囲

本画面サブシステムは、Cosmetics Finderプラットフォーム内で実行された重要なシステム操作を、プラットフォーム管理者が完全に可視化できるようにする。セキュリティ監視、コンプライアンス、運用上の説明責任における中心的な監査証跡として機能する。

監査ログには、ユーザー認証イベント、加盟店承認、商品変更、広告ライフサイクルイベント、注文ステータス遷移、コミッション率変更、支払処理、管理操作など、プラットフォーム全体の重要な操作を記録する。各ログエントリには、操作を実行した者、変更内容（変更前・変更後の値）、実行日時、実行元（IPアドレス、ユーザーエージェント）を記録する。

本書では、管理者が監査ログデータを表示、フィルタリング、検索、エクスポートするために利用するすべての画面、操作、ビジネスルール、APIエンドポイントを定義する。

### 1.2 機能責務

1. **監査証跡の表示** — タイムスタンプ、実行者、操作種別、エンティティ種別、概要、IPアドレスを含む、ソートおよびページング可能なテーブルで全監査ログを表示する。
2. **高度なフィルタリング** — 操作種別、エンティティ種別、日付範囲、IPアドレス、フリーテキスト検索で監査ログを絞り込み、特定イベントを速やかに特定する（`userId` と `entityId` はURLクエリパラメータとしてのみ受け付けるため、画面に対応する入力項目は存在しない）。
3. **ログ詳細確認** — 監査ログ個別エントリの変更前・変更後の値（人が読めるキーバリューリスト）、IPアドレス、解析済みクライアント情報（クライアント種別・ブラウザ・デバイス）を表示する。
4. **検索** — 操作名、エンティティ種別、ユーザー情報を対象に全文検索する。
5. **CSVエクスポート** — エクスポート用ダイアログで期間を選択したうえで、フィルタリング済みの監査ログデータを外部分析およびコンプライアンス報告用のCSV添付ファイルとしてダウンロードする。
6. **リアルタイム監視** — 最新のシステム活動をほぼリアルタイムで監視する自動更新機能を提供する（ブラウザタブが非表示の間は停止）。
7. **手動削除** — 権限を持つ管理者は、90日以上経過したDB監査ログレコードを、保持期間ベースまたは明示的に選択した行のみに限定して手動削除できる。システムによる自動削除は行わず、エクスポートファイル保存も存在しない（エクスポートは直接ストリーム配信される）。

## 3. 状態遷移仕様

### 3.1 監査ログ保持状態

| 状態 | 説明 | 管理者が利用可能なレコード | 許可される書込操作 |
|-------|-------------|:----------:|-------------------------|
| `ACTIVE` | 90日未満の追記専用監査ログレコード。誰も削除できない。 | はい | INSERTのみ |
| `DELETABLE` | 90日以上経過した監査ログレコード（`AUDIT_LOG_MIN_RETENTION_DAYS`）。管理者の手動削除対象にできる。 | はい | INSERTのみ |
| `DELETED` | 権限を持つ管理者の手動削除により除去されたレコード。 | いいえ | なし |

### 3.2 CSVエクスポート要求の状態

| 状態 | 説明 | 遷移トリガー |
|-------|-------------|-------------------|
| `IDLE` | エクスポート要求が進行中でない。エクスポートダイアログは開いているか閉じているかのいずれか。 | 管理者がエクスポートダイアログを開く |
| `VALIDATING` | 選択した日付範囲をクライアント側で検証する（両方の日付必須、終了日 >= 開始日、終端までの範囲 <= 365日）。サーバー側DTOでも検証する。 | 管理者がエクスポートダイアログを確定 |
| `STREAMING` | バックエンドが一致する行を読み取り、CSV添付ファイルをストリーム配信する。 | クライアント側・サーバー側の検証を通過 |
| `COMPLETED` | ブラウザがCSVファイルをダウンロードし、成功トーストを表示する。 | レスポンスの受領完了 |
| `FAILED` | 検証または生成に失敗し、エラートーストを表示する。ダイアログは開いたままとなる。 | エラーレスポンス |

CSVエクスポートの状態遷移では、`audit_logs`に対して読み取り専用クエリを実行する。エクスポートの状態遷移によって監査ログレコードを削除、アーカイブ、パージ、更新、その他の変更を行ってはならない。**エクスポートファイルの保存領域は存在しない** — 生成したCSVは管理者のブラウザへファイル添付として直接ストリーム配信され、恒久的には保存されないため、保持・期限切れ・削除の対象となるファイルは存在しない。

### 3.3 自動更新状態

| 状態 | 説明 | 遷移トリガー |
|-------|-------------|-------------------|
| `DISABLED` | 監査ログ一覧を自動更新しない。 | 管理者が自動更新を無効化 |
| `ENABLED` | `AUDIT_LOG_AUTO_REFRESH_INTERVAL`ミリ秒ごとに一覧を更新する。 | 管理者が自動更新を有効化 |
| `REFRESHING` | 読み取り専用の一覧要求を処理中である。 | 更新間隔の経過、または管理者による更新要求 |
| `PAUSED` | ページが非表示、または要求処理中のため自動更新を一時停止している。 | ページ表示状態の変更、または要求の重複 |
| `ERROR` | 最新の更新要求が失敗した。既存の一覧データは変更しない。 | 更新要求がエラーを返す |

### 3.4 状態遷移マトリクス

## 6. 機能操作仕様

### 6.1 操作：監査ログ一覧取得

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | `/admin/audit-logs`へ移動 |
| **APIエンドポイント** | `GET /api/v1/admin/audit-logs` |
| **クエリパラメータ** | `userId`（任意）、`action`（任意）、`entityType`（任意）、`entityId`（任意）、`dateFrom`（任意）、`dateTo`（任意）、`ipAddress`（任意）、`search`（任意）、`page`（デフォルト1）、`limit`（サーバー既定50，画面は10を送信）、`sortBy`（デフォルト`created_at`）、`sortOrder`（デフォルト`desc`） |
| **処理手順** | 1. JWTトークンと管理者ロールを検証する。2. フィルタ（userId、action、entityType、entityId、日付範囲、ipAddress）でクエリを構築する。日付のみの値はミャンマー時間の日境界（00:00:00.000／23:59:59.999 +06:30）に展開する。3. `search`が指定された場合、`action`、`entity_type`、結合した`users.name`／`users.email`にLIKE条件を追加する。4. `ipAddress`が指定された場合、アドレスとその表現に`contains`条件を追加する。5. `action`に`AUDIT_LOG_DELETE`を含む場合、旧`audit.admin.delete`のレコードも対象にする。6. ソートを適用する（デフォルト：`created_at DESC`、`id`をタイブレーカーとする）。7. ページングする。8. 各エントリについて`users`テーブルを結合し、実行者名・メールアドレス・ロールを取得する。9. **`entityId`を含まない**ページング済み監査ログ一覧を返す。 |
| **成功レスポンス** | ページング済み監査ログ一覧を含む200 OK |

### 6.2 操作：監査ログ詳細取得

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | 監査ログ行の「詳細を表示」アイコンボタンをクリック |
| **APIエンドポイント** | `GET /api/v1/admin/audit-logs/:id` |
| **処理手順** | 1. JWTトークンと管理者ロールを検証する。2. IDで監査ログエントリを検索する。3. `users`テーブルを結合して実行者情報を取得する。4. `old_value`／`new_value`の機密フィールドをマスクする。5. `old_value`、`new_value`、`ip_address`、`user_agent`を含む監査ログDTOを返す — **`entityId`は含まない**。 |
| **成功レスポンス** | 監査ログ詳細を含む200 OK |

### 6.3 操作：監査ログのエクスポート（CSV）

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | 「CSVエクスポート」ボタンをクリックし、ダイアログで期間を指定して確定（一覧が空の場合は情報トーストで停止） |
| **APIエンドポイント** | `POST /api/v1/admin/audit-logs/export` |
| **リクエストボディ** | `{ userId?: string, action?: string[], entityType?: string[], entityId?: string, dateFrom?: string, dateTo?: string, ipAddress?: string, search?: string, format: 'csv' }` |
| **処理手順** | 1. JWTトークンと管理者ロールを検証する。2. 入力を検証する（日付範囲は必須、最大365日）。3. 一覧エンドポイントと同じフィルタで読み取り専用クエリを構築する。4. 行数を確認する。10,000行を超える場合は警告付き400を返し、監査ログを変更しない。5. Timestamp、Actor Name、Actor Email、Actor Role、Action、Entity Type、Old Value、New Value、IP Address、User Agentの列を持つCSV内容を生成する（Entity ID列は含まない）。タイムスタンプはミャンマー時間で表記し、変更前・変更後の値は機密フィールドをマスクしたJSON文字列とする。6. 先頭にUTF-8 BOMを付け、行はCRLFで結合する。7. ファイル名は`audit-logs-{startDate}-{endDate}({today}).csv`（ミャンマー日付。期間がない場合は`audit-logs-{today}.csv`）。8. 適用フィルタと行数を記録する`AUDIT_EXPORT`自己監査イベントを追記する。9. ファイルを添付としてクライアントへストリーム配信する — **サーバー側には何も保存しない**。 |
| **成功レスポンス** | `Content-Type: text/csv; charset=utf-8`、`Content-Disposition: attachment; filename="..."`とCSV本文を含む200 OK（ダウンロードURLは返さない） |

### 6.4 操作：監査ログの手動削除

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | 管理者が「監査ログ削除」ボタンをクリックし、任意でテーブル内の行を選択して保持期間を確認し、削除を確定 |
| **APIエンドポイント** | `DELETE /api/v1/admin/audit-logs/files` |
| **リクエストボディ** | `{ olderThanDays?: number, recordIds?: string[], fileIds?: string[] }`（`fileIds`はAPI契約の互換性のために受け付けられるが、サービスは無視する — エクスポートはストリーム配信され、エクスポートファイルのテーブルは存在しない） |
| **処理手順** | 1. JWTトークンと管理者ロールを検証する。2. `olderThanDays`が指定されている場合、`AUDIT_LOG_MIN_RETENTION_DAYS`（90）以上であることを検証する。3. `recordIds`が指定された場合、対象行を取得し、存在しない行、または保持期間未満の行があればリクエスト全体を拒否する（atomic — 何も削除しない）うえで、指定された行のみを削除する。4. 指定がない場合、しきい値より古い行を数え、対象がなければ拒否し、制御されたバッチで削除する。5. `deletedRecords`（常に0の`deletedFiles`を含む）、`olderThanDays`、選択された`recordIds`を記録する`AUDIT_LOG_DELETE`自己監査イベントを追記する。6. 削除したレコード数とファイル数を返す。 |
| **成功レスポンス** | `{ deletedRecords: number, deletedFiles: number }`を含む200 OK（`deletedFiles`は常に`0`） |
| **エラーレスポンス** | `olderThanDays`が90未満の場合は400、非管理者の場合は403、削除対象がない場合および指定レコードが存在しない／若すぎる場合は400 |

### 6.5 操作：利用可能なフィルタ選択肢の取得

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | 管理者がフィルタドロップダウンを開く |
| **APIエンドポイント** | `GET /api/v1/admin/audit-logs/filters` |
| **処理手順** | 1. JWTトークンと管理者ロールを検証する。2. `audit_logs`から重複しない`action`値を取得する。3. `audit_logs`から重複しない`entity_type`値を取得する。4. 監査カタログ（システムが記録できるすべての操作／エンティティ種別）と突合し、結果をソート・重複排除したうえで、旧`audit.admin.delete`の表示を操作リストから隠す。5. 利用可能なフィルタ選択肢の配列を返す。 |
| **成功レスポンス** | `{ actions: string[], entityTypes: string[] }`を含む200 OK |

| 経過期間チェック | 対象レコードが90日以上経過していること。`recordIds`指定時は参照されたすべてのレコードが存在し適格である必要があり、1件でも不適格ならリクエスト全体が拒否される | "Records younger than 90 days cannot be deleted" / "One or more specified records do not exist." | 「90日未満のレコードは削除できません」／「指定されたレコードの一部が存在しません。」 |

## 9. エラーハンドリング仕様

### 9.1 エラーレスポンス構造

```json
{
  "statusCode": 400,
  "message": ["dateTo must be greater than or equal to dateFrom"],
  "error": "Bad Request",
  "timestamp": "2026-08-25T12:00:00.000Z",
  "path": "/api/v1/admin/audit-logs"
}
```

### 9.2 エラー分類表 — 監査ログ表示

| HTTPステータス | エラーコード | 発生条件 | ユーザー向け動作 |
|-------------|-------------|----------|---------------------|
| `400` | `BAD_REQUEST` | フィルタパラメータが不正 | 「フィルタパラメータが不正です。入力を確認してください。」 |
| `400` | `BAD_REQUEST` | dateToがdateFromより前 | 「終了日は開始日より後である必要があります」 |
| `400` | `BAD_REQUEST` | ソート項目が不正 | 「無効なソート項目です」 |
| `403` | `FORBIDDEN` | 非管理者がアクセスを試みた | 「アクセスが拒否されました」 |
| `404` | `NOT_FOUND` | 監査ログエントリが見つからない | 「監査ログエントリが見つかりません」 |
| `500` | `INTERNAL_SERVER_ERROR` | サーバーエラー | 「問題が発生しました。もう一度お試しください」 |

### 9.3 エラー分類表 — エクスポート

| HTTPステータス | エラーコード | 発生条件 | ユーザー向け動作 |
|-------------|-------------|----------|---------------------|
| `400` | `BAD_REQUEST` | エクスポート形式が不正 | 「エクスポート形式はCSVである必要があります」 |
| `400` | `BAD_REQUEST` | 日付範囲が365日を超える | 「日付範囲は365日を超えることはできません」 |
| `400` | `BAD_REQUEST` | エクスポートが行数上限を超える | 「エクスポートが最大行制限（10,000）を超えています。フィルターを絞り込んでください。」 |
| `400` | `BAD_REQUEST` | エクスポートで書込またはパージを実行しようとした | 「CSVエクスポートは読み取り専用です。」 |
| `500` | `INTERNAL_SERVER_ERROR` | エクスポート生成に失敗 | 「レポート生成に失敗しました。もう一度お試しください。」 |

### 9.4 エラー分類表 — 手動削除

| HTTPステータス | エラーコード | 発生条件 | ユーザー向け動作 |
|-------------|-------------|----------|---------------------|
| `400` | `BAD_REQUEST` | `olderThanDays`が90未満 | 「最小保持期間は90日です。90日未満のレコードとファイルは削除できません。」 |
| `400` | `BAD_REQUEST` | 削除対象となるレコードがない | 「削除対象となるレコードまたはファイルがありません（90日以上経過している必要があります）。」 |
| `400` | `BAD_REQUEST` | 指定した`recordIds`が存在しない、または経過期間を満たさない | 「指定されたレコードの一部が存在しません。」／「90日未満のレコードは削除できません。」 |
| `403` | `FORBIDDEN` | 非管理者が削除を試みた | 「アクセスが拒否されました」 |
| `500` | `INTERNAL_SERVER_ERROR` | 削除に失敗 | 「削除に失敗しました。もう一度お試しください。」 |

### 9.5 フロントエンドのエラー表示動作

- **フィールド単位のバリデーション**：不正な入力欄の直下にインラインテキスト（日付範囲、保持日数、エクスポート期間）。
- **フォーム単位のサマリー**：一覧の読み込み／更新失敗時は一覧上部のエラーバナー（`role="alert"`）、削除ダイアログとエクスポートダイアログではインラインメッセージ。
- **トースト通知**：APIエラーおよび操作成功の通知に使用する（エクスポート成功、削除成功、空一覧でのエクスポート通知）。
- **ローディング状態**：API呼び出し中はボタンを無効化しラベルを変更する。読み込み中はテーブルにスケルトンを表示する。

## 11. リアルタイム通知動作

### 11.1 自動更新動作

管理者監査ログ画面では、WebSocketプッシュではなく認証済みポーリングを使用する。有効時、クライアントは`AUDIT_LOG_AUTO_REFRESH_INTERVAL`ミリ秒ごとに、現在のフィルタ条件に一致する一覧を要求する（デフォルト30秒）。

| イベント | トリガー | クライアント動作 | データ操作 |
|-------|---------|---------------|----------------|
| `autoRefreshEnabled` | 管理者がトグルを有効化 | 設定済みポーリング間隔を開始 | 読み取り専用`GET`要求 |
| `auditLogRefresh` | ポーリング間隔が経過 | 現在のページとフィルタを再読み込み | 読み取り専用`SELECT` |
| `newActivityDetected` | レスポンスに新しいレコードが含まれる | 一覧を更新し、ブロッキングしない通知を表示 | 監査ログの変更なし |
| `autoRefreshDisabled` | 管理者がトグルを無効化 | ポーリングを停止し、現在の一覧を保持 | なし |
| `refreshError` | 更新要求が失敗 | 既存データを保持し、エラー通知を表示 | 監査ログの変更なし |

### 11.2 更新・整合性ルール

- 自動更新では、管理者が現在表示しているフィルタ、ソート順、ページング状態をそのまま使用する。
- 更新要求は読み取り専用とし、監査ログレコードを削除、アーカイブ、パージ、更新してはならない。
- クライアントは、ブラウザタブが非表示のときにポーリングを停止し、バックグラウンド更新も行わない（`refetchIntervalInBackground: false`）。
- 更新に失敗しても既存の結果を消去せず、直前の行を保持して次のスケジュール間隔で再試行できる。
- エクスポート操作は管理者が明示的に開始し、自動更新とは独立して実行する。
- 監査ログの手動削除は管理者が明示的に開始し、自動更新およびエクスポート操作とは独立して実行する。

| CSVエクスポート生成（10,000行以下） | 5秒以内 |

### 13.2 セキュリティ考慮事項

| 懸念事項 | 対策 |
|------------|------------|
| 管理者権限の迂回 | すべてのエンドポイントでJwtAuthGuard + RolesGuardによりRBACを適用 |
| データ完全性 | 監査ログは追記のみ（DB上UPDATEなし）。DELETEは90日以上経過したレコードに対する管理者手動削除に限定 |
| 機密データの漏えい | パスワード、トークン、秘密情報を`old_value`／`new_value`に記録しない |
| エクスポートデータの漏えい | エクスポートから機密フィールドを除外し、監査ログに記録 |
| SQLインジェクション | Prisma ORMによるパラメータ化クエリ |
| 大規模データセットの性能 | user_id、action、entity_type、entity_id、created_atにDBインデックスを設定 |
| 誤削除 | 最低90日経過要件を適用し、管理者の確認を必須とする。削除操作を監査イベントとして記録 |

### 13.3 レスポンシブデザイン要件

| ブレークポイント | レイアウト |
|--------|--------|
| デスクトップ（1024px以上） | 完全なテーブルレイアウト、4列フィルタカード、中央配置の詳細モーダル（最大40rem） |
| タブレット（768px〜1023px） | 2列フィルタグリッド、水平スクロール付きレスポンシブテーブル、中央配置のダイアログ |
| モバイル（768px未満） | 1列フィルタ、スクロール可能なテーブル、全画面モーダル・ダイアログ |

### 13.4 アクセシビリティ要件

### 13.5 バックグラウンドジョブと保持

監査ログレコードをシステムがバックグラウンドで自動削除するジョブは存在しない。DB監査ログレコードの削除は、権限を持つ管理者が手動で実行する場合に限る。CSVエクスポートはブラウザへストリーム配信され保存されないため、保持・パージ対象となるエクスポートファイルは存在しない。

| 属性 | 仕様 |
|-------------|---------------|
| **自動パージ** | 完全に廃止。保持期間を処理するスケジュール済みバックグラウンドジョブは存在しない。 |
| **管理者手動削除** | `admin`ロールを持つ権限ある管理者は、`DELETE /api/v1/admin/audit-logs/files`により90日以上経過したDB監査ログレコードを手動削除できる（保持期間ベース、または明示的に選択した行に限定）。 |
| **最小経過期間** | 90日未満（`< AUDIT_LOG_MIN_RETENTION_DAYS`）のレコードは、管理者を含む誰も削除できない。 |
| **エクスポートファイルの保持** | 該当なし — エクスポートは添付ファイルとしてストリーム配信され、エクスポートファイルのメタデータテーブルは存在しない（`deletedFiles`は常に0）。 |
| **監査可能性** | 追跡可能性のため、管理者による削除を`AUDIT_LOG_DELETE`イベントとして記録する。 |

管理者監査ログUIには、権限を持つ管理者向けの手動削除操作を公開する。エクスポートファイルの期限切れ・削除のパスは存在しない。

| 要件 | 実装 |
|-------------|----------------|
| キーボード操作 | すべてのインタラクティブ要素をTabキーでフォーカス可能にする |
| スクリーンリーダー | ボタン、フィルタ、モーダルにARIAラベルを付与 |
| 色のコントラスト | タイムスタンプと操作バッジをWCAG 2.1 AAに準拠させる |
| フォーカス管理 | モーダルのフォーカストラップ、および閉じた際のフォーカス復帰 |
