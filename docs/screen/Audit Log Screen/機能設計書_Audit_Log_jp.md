## 1. 機能概要

### 1.1 目的と範囲

本画面サブシステムは、Cosmetics Finderプラットフォーム内で実行された重要なシステム操作を、プラットフォーム管理者が完全に可視化できるようにする。セキュリティ監視、コンプライアンス、運用上の説明責任における中心的な監査証跡として機能する。

監査ログには、ユーザー認証イベント、加盟店承認、商品変更、広告ライフサイクルイベント、注文ステータス遷移、コミッション率変更、支払処理、管理操作など、プラットフォーム全体の重要な操作を記録する。各ログエントリには、操作を実行した者、変更内容（変更前・変更後の値）、実行日時、実行元（IPアドレス、ユーザーエージェント）を記録する。

本書では、管理者が監査ログデータを表示、フィルタリング、検索、エクスポートするために利用するすべての画面、操作、ビジネスルール、APIエンドポイントを定義する。

### 1.2 機能責務

1. **監査証跡の表示** — タイムスタンプ、実行者、操作種別、対象エンティティ、概要を含む、ソートおよびページング可能なテーブルで全監査ログを表示する。
2. **高度なフィルタリング** — ユーザー、操作種別、エンティティ種別、日付範囲、IPアドレスで監査ログを絞り込み、特定イベントを速やかに特定する。
3. **ログ詳細確認** — 監査ログ個別エントリの変更前・変更後の値（JSON差分）、ユーザーエージェント、IPアドレスを含む詳細を表示する。
4. **検索** — 操作名、エンティティ種別、ユーザー情報を対象に全文検索する。
5. **CSVエクスポート** — フィルタリング済みの監査ログデータを、外部分析およびコンプライアンス報告用のCSV形式でエクスポートする。
6. **リアルタイム監視** — 最新のシステム活動をほぼリアルタイムで監視する自動更新機能を提供する。
7. **手動削除** — 権限を持つ管理者は、90日以上経過したDB監査ログレコードおよびCSVエクスポートファイルを手動削除できる。システムによる自動削除は行わない。

## 3. 状態遷移仕様

### 3.1 監査ログ保持状態

| 状態 | 説明 | 管理者が利用可能なレコード | 許可される書込操作 |
|-------|-------------|:----------:|-------------------------|
| `ACTIVE` | 90日未満の追記専用監査ログレコード。誰も削除できない。 | はい | INSERTのみ |
| `DELETABLE` | 90日以上経過した監査ログレコード（`AUDIT_LOG_MIN_RETENTION_DAYS`）。管理者の手動削除対象にできる。 | はい | INSERTのみ |
| `DELETED` | 権限を持つ管理者の手動削除により除去されたレコード。 | いいえ | なし |

### 3.2 CSVエクスポートファイル状態

| 状態 | 説明 | 遷移トリガー |
|-------|-------------|-------------------|
| `NOT_STARTED` | 対象リクエストのエクスポートジョブが作成されていない。 | 管理者が有効なCSVエクスポート要求を送信 |
| `QUEUED` | エクスポート要求が受理され、処理待ちである。 | エクスポート要求のバリデーション成功 |
| `PROCESSING` | 一致する監査ログを読み取り、CSVファイルを生成中である。 | エクスポートワーカーの開始 |
| `COMPLETED` | CSVファイルをダウンロードできる。管理者が手動削除するまで保持する。 | ファイル生成成功 |
| `FAILED` | CSV生成に失敗した、または要求が設定済み上限を超えた。 | 処理またはバリデーションエラー |
| `DELETED` | 権限を持つ管理者の手動削除により生成済みエクスポートファイルが除去された。 | 管理者がCSVファイルを削除 |

CSVエクスポートの状態遷移では、`audit_logs`に対して読み取り専用クエリを実行する。エクスポートの状態遷移によって監査ログレコードを削除、アーカイブ、パージ、更新、その他の変更を行ってはならない。エクスポートファイルは、権限を持つ管理者が手動削除するまで無期限に保持する。

### 3.3 自動更新状態

| 状態 | 説明 | 遷移トリガー |
|-------|-------------|-------------------|
| `DISABLED` | 監査ログ一覧を自動更新しない。 | 管理者が自動更新を無効化 |
| `ENABLED` | `AUDIT_LOG_AUTO_REFRESH_INTERVAL`ミリ秒ごとに一覧を更新する。 | 管理者が自動更新を有効化 |
| `REFRESHING` | 読み取り専用の一覧要求を処理中である。 | 更新間隔の経過、または管理者による更新要求 |
| `PAUSED` | ページが非表示、または要求処理中のため自動更新を一時停止している。 | ページ表示状態の変更、または要求の重複 |
| `ERROR` | 最新の更新要求が失敗した。既存の一覧データは変更しない。 | 更新要求がエラーを返す |

### 3.4 状態遷移マトリクス

| 遷移ID | 遷移元 | 遷移先 | トリガー／ガード条件 |
|---------------|------------|----------|---------------------------|
| TR-AUDIT-001 | `ACTIVE` | `DELETABLE` | レコードが90日以上経過（`>= AUDIT_LOG_MIN_RETENTION_DAYS`）。自動処理は行わない。 |
| TR-AUDIT-002 | `DELETABLE` | `DELETED` | 権限を持つ管理者が `DELETE /api/v1/admin/audit-logs/files` で手動削除。 |
| TR-AUDIT-003 | `NOT_STARTED` | `QUEUED` | 管理者が有効なCSVエクスポート要求を送信。 |
| TR-AUDIT-004 | `QUEUED` | `PROCESSING` | エクスポートワーカーが読み取り専用クエリを開始。 |
| TR-AUDIT-005 | `PROCESSING` | `COMPLETED` | CSVファイルの生成成功。任意で `audit.export` イベントを追記。 |
| TR-AUDIT-006 | `PROCESSING` | `FAILED` | クエリ、バリデーション、ストレージ、または生成に失敗。 |
| TR-AUDIT-007 | `COMPLETED` | `DELETED` | 権限を持つ管理者が `DELETE /api/v1/admin/audit-logs/files` でCSVファイルを手動削除。 |
| TR-AUDIT-008 | `DISABLED` | `ENABLED` | 管理者が自動更新を有効化。 |
| TR-AUDIT-009 | `ENABLED` | `REFRESHING` | 更新間隔が経過。 |
| TR-AUDIT-010 | `REFRESHING` | `ENABLED` | 読み取り専用一覧クエリが成功。 |
| TR-AUDIT-011 | `REFRESHING` | `ERROR` | 読み取り専用一覧クエリが失敗。 |

## 4. ビジネスルール

### 4.1 監査ログデータルール

| ルールID | ルール名 | 説明 | 適用レイヤー |
|---------|-----------|-------------|-------------------|
| BR-AUDIT-001 | 追記のみ、管理者による手動削除 | 監査ログは追記のみ（UPDATEなし）とする。DELETEは、`admin`ロールを持つ権限ある管理者が、90日以上経過したレコード（`>= AUDIT_LOG_MIN_RETENTION_DAYS`）を手動削除する場合に限り許可する。90日未満のレコードは誰も削除できない。 | バックエンド（DB制約＋サービス） |
| BR-AUDIT-007 | システム自動パージなし | DB監査ログレコードおよびCSVエクスポートファイルに対するシステムのバックグラウンド自動削除を完全に廃止する。保持期間の定期パージジョブは存在しない。削除はすべて手動かつ管理者起点で行う。 | バックエンド（スケジュールジョブなし） |

## 6. 機能操作仕様

### 6.1 操作：監査ログ一覧取得

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | `/admin/audit-logs`へ移動 |
| **APIエンドポイント** | `GET /api/v1/admin/audit-logs` |
| **クエリパラメータ** | `userId`（任意）、`action`（任意）、`entityType`（任意）、`entityId`（任意）、`dateFrom`（任意）、`dateTo`（任意）、`ipAddress`（任意）、`search`（任意）、`page`（デフォルト1）、`limit`（デフォルト50）、`sortBy`（デフォルト`created_at`）、`sortOrder`（デフォルト`desc`） |
| **処理手順** | 1. JWTトークンと管理者ロールを検証する。2. フィルタ（userId、action、entityType、entityId、日付範囲、ipAddress）でクエリを構築する。3. `search`が指定された場合、`action`、`entity_type`、結合した`users.name`／`users.email`にLIKE条件を追加する。4. ソートを適用する（デフォルト：`created_at DESC`）。5. ページングする。6. 各エントリについて`users`テーブルを結合し、実行者名・メールアドレスを取得する。7. ページング済み監査ログ一覧を返す。 |
| **成功レスポンス** | ページング済み監査ログ一覧を含む200 OK |

### 6.2 操作：監査ログ詳細取得

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | 監査ログ行の「詳細を表示」をクリック |
| **APIエンドポイント** | `GET /api/v1/admin/audit-logs/:id` |
| **処理手順** | 1. JWTトークンと管理者ロールを検証する。2. IDで監査ログエントリを検索する。3. `users`テーブルを結合して実行者情報を取得する。4. `old_value`、`new_value`、`ip_address`、`user_agent`を含む完全な監査ログDTOを返す。 |
| **成功レスポンス** | 監査ログ詳細を含む200 OK |

### 6.3 操作：監査ログのエクスポート（CSV）

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | 「CSVエクスポート」ボタンをクリック |
| **APIエンドポイント** | `POST /api/v1/admin/audit-logs/export` |
| **リクエストボディ** | `{ userId?: string, action?: string, entityType?: string, entityId?: string, dateFrom?: string, dateTo?: string, ipAddress?: string, search?: string, format: 'csv' }` |
| **処理手順** | 1. JWTトークンと管理者ロールを検証する。2. 入力を検証する（日付範囲は最大365日）。3. 一覧エンドポイントと同じフィルタで読み取り専用クエリを構築する。4. 行数を確認する。10,000行を超える場合は警告付き400を返し、監査ログを変更しない。5. Timestamp、Actor Name、Actor Email、Actor Role、Action、Entity Type、Entity ID、Old Value、New Value、IP Address、User Agentの列を持つCSVファイルを生成する。6. 自動TTL期限なしのエクスポートストレージに保存する（管理者が手動削除するまで保持）。7. 任意で`audit.export`イベントを`audit_logs`に追記する。このイベントはエクスポート対象レコードとは独立しており、対象レコードを削除、アーカイブ、パージ、更新しない。8. ダウンロードURLを返す。 |
| **成功レスポンス** | `{ downloadUrl: string }`を含む200 OK |

### 6.4 操作：監査ログとCSVエクスポートファイルの手動削除

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | 管理者が「監査ログとCSVファイルを削除」ボタンをクリックし、確認する |
| **APIエンドポイント** | `DELETE /api/v1/admin/audit-logs/files` |
| **リクエストボディ** | `{ olderThanDays?: number, recordIds?: string[], fileIds?: string[] }` |
| **処理手順** | 1. JWTトークンと管理者ロールを検証する。2. `olderThanDays`が指定されている場合、`AUDIT_LOG_MIN_RETENTION_DAYS`（90）以上であることを検証する。3. 指定された閾値より古い`created_at`を持つDB監査ログレコードを選択する（デフォルト90日）。4. 指定された閾値より古い生成済みCSVエクスポートファイルを選択する。5. 選択したレコードとファイルを制御されたバッチで削除する。6. 任意で削除内容を記録する`audit.admin.delete`イベントを追記する。7. 削除した件数を返す。 |
| **成功レスポンス** | `{ deletedRecords: number, deletedFiles: number }`を含む200 OK |
| **エラーレスポンス** | `olderThanDays`が90未満の場合は400、非管理者の場合は403、削除対象がない場合は400 |

### 6.5 操作：利用可能なフィルタ選択肢の取得

| 属性 | 仕様 |
|-----------|---------------|
| **トリガー** | 管理者がフィルタドロップダウンを開く |
| **APIエンドポイント** | `GET /api/v1/admin/audit-logs/filters` |
| **処理手順** | 1. JWTトークンと管理者ロールを検証する。2. `audit_logs`から重複しない`action`値を取得する。3. `audit_logs`から重複しない`entity_type`値を取得する。4. 利用可能なフィルタ選択肢の配列を返す。 |
| **成功レスポンス** | `{ actions: string[], entityTypes: string[] }`を含む200 OK |

## 11. リアルタイム通知動作

### 11.1 自動更新動作

管理者監査ログ画面では、WebSocketプッシュではなく認証済みポーリングを使用する。有効時、クライアントは`AUDIT_LOG_AUTO_REFRESH_INTERVAL`ミリ秒ごとに、現在のフィルタ条件に一致する一覧を要求する（デフォルト30秒）。

| イベント | トリガー | クライアント動作 | データ操作 |
|-------|---------|---------------|----------------|
| `autoRefreshEnabled` | 管理者がトグルを有効化 | 設定済みポーリング間隔を開始 | 読み取り専用`GET`要求 |
| `auditLogRefresh` | ポーリング間隔が経過 | 現在のページとフィルタを再読み込み | 読み取り専用`SELECT` |
| `newActivityDetected` | レスポンスに新しいレコードが含まれる | 一覧を更新し、ブロッキングしない通知を表示 | 監査ログの変更なし |
| `autoRefreshDisabled` | 管理者がトグルを無効化 | ポーリングを停止し、現在の一覧を保持 | なし |
| `refreshError` | 更新要求が失敗 | 既存データを保持し、エラー通知を表示 | 監査ログの変更なし |

### 11.2 更新・整合性ルール

- 自動更新では、管理者が現在表示しているフィルタ、ソート順、ページング状態をそのまま使用する。
- 更新要求は読み取り専用とし、監査ログレコードを削除、アーカイブ、パージ、更新してはならない。
- クライアントは、ページが非表示のとき、または別の更新要求が処理中のときにポーリングを一時停止する。
- 更新に失敗しても既存の結果を消去しない。次のスケジュール間隔で再試行できる。
- エクスポート操作は管理者が明示的に開始し、自動更新とは独立して実行する。
- 監査ログとCSVエクスポートファイルの手動削除は管理者が明示的に開始し、自動更新およびエクスポート操作とは独立して実行する。

### 13.2 セキュリティ考慮事項

| 懸念事項 | 対策 |
|------------|------------|
| 管理者権限の迂回 | すべてのエンドポイントでJwtAuthGuard + RolesGuardによりRBACを適用 |
| データ完全性 | 監査ログは追記のみ（DB上UPDATEなし）。DELETEは90日以上経過したレコードに対する管理者手動削除に限定 |
| 機密データの漏えい | パスワード、トークン、秘密情報を`old_value`／`new_value`に記録しない |
| エクスポートデータの漏えい | エクスポートから機密フィールドを除外し、監査ログに記録 |
| SQLインジェクション | Prisma ORMによるパラメータ化クエリ |
| 大規模データセットの性能 | user_id、action、entity_type、entity_id、created_atにDBインデックスを設定 |
| 誤削除 | 最低90日経過要件を適用し、管理者の確認を必須とする。削除操作を監査イベントとして記録 |

### 13.3 レスポンシブデザイン要件

| ブレークポイント | レイアウト |
|--------|--------|
| デスクトップ（1024px以上） | 完全なテーブルレイアウト、サイドバーフィルタ |
| タブレット（768px〜1023px） | フィルタを縦積み、レスポンシブテーブル |
| モバイル（768px未満） | カード形式のログ一覧、全幅モーダル |

### 13.5 バックグラウンドジョブと保持

監査ログレコードまたはCSVエクスポートファイルをシステムがバックグラウンドで自動削除するジョブは存在しない。DB監査ログレコードおよび生成済みCSVエクスポートファイルの削除は、権限を持つ管理者が手動で実行する場合に限る。

| 属性 | 仕様 |
|-------------|---------------|
| **自動パージ** | 完全に廃止。保持期間を処理するスケジュール済みバックグラウンドジョブは存在しない。 |
| **管理者手動削除** | `admin`ロールを持つ権限ある管理者は、`DELETE /api/v1/admin/audit-logs/files`により90日以上経過したDB監査ログレコードとCSVエクスポートファイルを手動削除できる。 |
| **最小経過期間** | 90日未満（`< AUDIT_LOG_MIN_RETENTION_DAYS`）のレコードとCSVファイルは、管理者を含む誰も削除できない。 |
| **エクスポートファイルの保持** | 生成されたCSVエクスポートファイルは、権限を持つ管理者が手動削除するまで無期限に保持する。自動TTL期限は存在しない。 |
| **監査可能性** | 追跡可能性のため、管理者による削除を`audit.admin.delete`イベントとして任意で記録する。 |

管理者監査ログUIには、権限を持つ管理者向けの手動削除操作を公開する。エクスポートファイルの期限切れによる削除は廃止し、管理者起点の手動削除のみをサポートする。

| 要件 | 実装 |
|-------------|----------------|
| キーボード操作 | すべてのインタラクティブ要素をTabキーでフォーカス可能にする |
| スクリーンリーダー | ボタン、フィルタ、モーダルにARIAラベルを付与 |
| 色のコントラスト | タイムスタンプと操作バッジをWCAG 2.1 AAに準拠させる |
| フォーカス管理 | モーダルのフォーカストラップ、および閉じた際のフォーカス復帰 |
