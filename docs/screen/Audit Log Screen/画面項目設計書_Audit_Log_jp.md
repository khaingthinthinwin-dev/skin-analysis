## 2. 画面概要・目的

### 2.1 目的
管理者監査ログ画面は、Cosmetics Finderプラットフォーム内で実行されたすべての重要なシステムアクションについて、プラットフォーム管理者に完全な可視性を提供します。セキュリティ監視、コンプライアンス、運用責任のための中央監査トレイルとして機能します。この画面では、監査ログデータの表示、フィルタリング、検索、エクスポート、および90日以上経過したレコードの手動削除が可能です。

### 2.2 対象ユーザーと権限

| 属性 | 値 |
| :--- | :--- |
| **主要アクター** | プラットフォーム管理者（管理者ロール） |
| **認証要件** | JWT Bearer Token（`admin`ロール） |
| **データ範囲** | プラットフォーム全体の監査ログエントリ（追記のみ、90日以上経過したレコードは管理者による手動削除可能） |
| **アクセス制御** | 管理者のみルート — `JwtAuthGuard` + `RolesGuard`強制適用 |

### 2.3 主要機能・基本設計方針
1. **監査トレイル表示** — すべての監査ログエントリをソート可能、ページネーション付きテーブルで表示。
2. **高度なフィルタリング** — アクションタイプ、エンティティタイプ、日付範囲、IPアドレス、フリーテキスト検索によるフィルタリング。（`userId` / `entityId`はURLクエリパラメータとしてのみ利用可能であり、対応する入力項目は画面に表示されません。）
3. **ログ詳細検査** — 人が読める旧値・新値リストと解析済みクライアント情報（クライアント種別、ブラウザ、デバイス）の表示。
4. **検索** — アクション名、エンティティタイプ、ユーザー情報に対する全文検索（300msデバウンス）。
5. **CSVエクスポート** — エクスポート用ダイアログで期間を選択してから、フィルタリングされた監査ログデータをCSVファイルとしてダウンロード。
6. **リアルタイム監視** — 30秒ごとの自動更新機能（ブラウザタブが非表示の間は停止）。
7. **手動削除** — 90日以上経過したDB監査ログレコードを、保持期間ベースまたは明示的に選択した行のみに限定して削除。
8. **国際化** — 英語、日本語、マレー語の完全なi18nサポート。
9. **レスポンシブデザイン** — デスクトップテーブルレイアウト、モバイルカードベースレイアウト。

## 5. 各項目における挙動・イベント仕様

### 5.1 ページ読み込み（`/admin/audit-logs`）
- **トリガー:** 管理者が`/admin/audit-logs`にナビゲート。
- **処理ロジック:**
  1. **認証チェック:** JWTトークンと`admin`ロールを検証。
  2. **初期データ読み込み:** デフォルトパラメータ（`page=1`, `limit=10`, `sortBy=created_at`, `sortOrder=desc`）およびURLに含まれる`userId` / `entityId`で`GET /api/v1/admin/audit-logs`を実行。
  3. **フィルターオプション読み込み:** アクションフィルターとエンティティタイプフィルタードロップダウンを入力するために`GET /api/v1/admin/audit-logs/filters`を実行（5分間キャッシュ）。
  4. **レンダリング:** 結果を含む監査ログテーブルを表示（読み込み中はスケルトン表示）。
- **例外処理:**
  - `403`（FORBIDDEN）: `/unauthorized`へリダイレクト（遷移後はページはアンマウント）。
  - 読み込み失敗（キャッシュデータなし）: サーバーメッセージまたは「監査ログの読み込みに失敗しました」（`audit.loadFailed`）をインラインのエラーバナー（`role="alert"`）で表示。
  - ネットワークエラー: Axiosのエラーメッセージ、またはフォールバックテキストをバナーで表示。

### 5.2 自動更新トグル（`tglAutoRefresh` onChange）
- **トリガー:** 管理者が自動更新スイッチをトグル。
- **処理ロジック:**
  1. **有効な場合:** ポーリング間隔（30秒）を開始。各間隔で、現在のフィルターを使用して監査ログリストを再取得。
  2. **無効な場合:** ポーリングを停止（`refetchInterval: false`）。現在のリストデータを保持。
  3. **一時停止動作:** ブラウザタブが非表示（`document.visibilityState !== 'visible'`）の間は自動的にポーリングを停止し、バックグラウンド実行も行わない（`refetchIntervalInBackground: false`）。
- **例外処理:**
  - リフレッシュエラー（以前に取得成功したデータがある場合）: 既存行を保持し、ブロックしないエラーバナー（`refreshError`）を表示。次の間隔で自動リトライ。

### 5.3 CSVエクスポート（`btnExportCsv` onClick → ダイアログ確定）
- **トリガー:** 管理者が「CSVエクスポート」ボタンをクリック。
- **処理ロジック:**
  1. **空リストの事前チェック:** `meta.total === 0`の場合は情報トースト（`audit.exportEmpty`）を表示し、ダイアログを**開かない**。
  2. **ダイアログを開く:** 現在のリストの`dateFrom`/`dateTo`を初期値として、CSVエクスポート日付範囲ダイアログ（第4.7項）を表示。
  3. **クライアント側バリデーション:** 両方の日付が必須、終了日 >= 開始日、終了日終端までの範囲 <= 365日（`AUDIT_LOG_EXPORT_MAX_RANGE_DAYS`）。エラーは入力欄の下に表示。
  4. **バックエンドディスパッチ:** 現在のリストフィルター + `{ dateFrom, dateTo, format: 'csv' }`で`POST /api/v1/admin/audit-logs/export`を実行（レスポンス種別 `blob`）。
  5. **バックエンド実行:** 範囲（最大365日、最大10,000行）を検証し、UTF-8のCSV添付ファイル（BOM付き、CRLF改行、MMTタイムスタンプ）をストリーミング返却。ファイル名は`audit-logs-{startDate}-{endDate}({today}).csv`。
  6. **実行後UI:** Blob URLを生成し、`Content-Disposition`のファイル名（フォールバック名はクライアント側で構築）でダウンロードをトリガー。ダイアログを閉じ、成功トースト（`audit.exportSuccess`）を表示。
- **例外処理:**
  - `400`その他のAPIエラー: エラーのBlobをJSONへ展開し、`message`を表示。フォールバックは`audit.exportFailed`。
  - エクスポートボタンは処理中は無効（ラベルは"エクスポート中..."）。

### 5.4 監査ログ削除ボタン（`btnDeleteLogs` onClick）
- **トリガー:** 管理者が「監査ログ削除」ボタンをクリック。
- **処理ロジック:**
  1. **認可チェック:** 管理者ロールを検証。非管理者ユーザーにはボタンを非表示。
  2. **ダイアログを開く:** 前回のエラーをクリアし、手動削除確認ダイアログを表示（第4.6項）。
- **例外処理:**
  - なし（権限がない場合はボタンを非表示）。

### 5.5 保持期間入力（`txtRetentionDays` onChange / onBlur）
- **トリガー:** 管理者が保持期間の値を変更しフォーカスを外す（または送信を試行）。
- **処理ロジック:**
  1. **バリデーション:** Zodの`deleteAuditLogsSchema` — 整数へ変換し、90以上であること。
  2. **サマリーの更新:** 削除範囲サマリーテキストに入力値で即時反映（行が選択されている場合は表示形式も切替）。
  3. **確認ボタンの有効/無効:** 値が無効な間は確認ボタンを無効に。
- **例外処理:**
  - 無効な入力: インラインエラー（`audit.retentionMin`）、`aria-invalid` + `role="alert"`。

### 5.6 削除確認（`btnConfirmDelete` onClick）
- **トリガー:** 管理者が「削除を確認」ボタンをクリック。
- **処理ロジック:**
  1. **クライアント側事前チェック:** 保持期間 >= 90を検証。
  2. **バックエンドディスパッチ:** `{ olderThanDays: <値> }`で`DELETE /api/v1/admin/audit-logs/files`を実行。行が選択されている場合は`{ recordIds: [...] }`も追加（成功時に選択はクリア）。
  3. **バックエンド実行:** JWTトークンと管理者ロールを検証。`recordIds`が指定された場合は全IDが適格（経過日数チェック）であることをatomicに検証し、該当行のみを削除。指定がない場合は`created_at`がしきい値より古いDBレコードを制御されたバッチで削除。`{ deletedRecords, deletedFiles }`を返却（`deletedFiles`は常に0 — エクスポートファイルの保存領域は存在しない）。
  4. **実行後UI:** ダイアログを閉じ、選択をクリアし、`deletedRecords`件数の成功トーストを表示し、一覧とフィルターキャッシュを破棄。
- **例外処理:**
  - `400`（BAD_REQUEST）: インラインエラーメッセージ（例: 「最小保持期間は90日です」「削除対象のレコードがありません」）。
  - `403`（FORBIDDEN）: インラインエラーメッセージ。
  - その他のエラー: インラインエラー（フォールバックは`audit.deleteFailed`）。ダイアログはリトライ用に開いたまま。
  - 処理中: 確認ボタンが無効化され"削除中..."表示。入力項目も無効。

### 5.7 詳細表示（`btnViewDetail` onClick）
- **トリガー:** 管理者がログ行の「詳細表示」アイコンボタンをクリック。
- **処理ロジック:**
  1. **状態設定:** 行IDを保持し、モーダルを開いて`GET /api/v1/admin/audit-logs/:id`を取得。
  2. **バックエンド実行:** IDで監査ログエントリを検索。実行者詳細のためにusersテーブルと結合。完全な監査ログDTO（`entityId`は含まない）を返却。
  3. **実行後UI:** 監査ログ詳細モーダル（第4.4項）を表示。読み込み中はスケルトン表示。
- **例外処理:**
  - 取得失敗: モーダル内に「監査ログエントリが見つかりません」（`audit.detailNotFound`）を表示。

### 5.8 行選択（`chkSelectRow` / `chkSelectAll` onChange）
- **トリガー:** 管理者が行のチェックボックス、またはヘッダーの全選択チェックボックスを切り替え。
- **処理ロジック:**
  1. **状態更新:** 行IDを`selectedIds`セットに追加/削除。全選択は現在のページに表示されている全IDを追加/削除（ページに1件以上ある場合のみ）。
  2. **視覚的フィードバック:** 選択された行に`data-selected`を付与。削除ダイアログの範囲サマリーが「選択したレコード」形式に切り替わる。
  3. **削除との連携:** 削除確定時に選択IDを`recordIds`として送信。削除成功時に選択をクリア。
- **例外処理:** 該当なし（選択はクライアント側のみ）。

### 5.9 フィルタークリア（`btnClearFilters` onClick）
- **トリガー:** 管理者が「フィルターをクリア」ボタンをクリック（`activeCount > 0`のときのみ表示）。
- **処理ロジック:**
  1. **状態リセット:** すべてのフィルター値（検索欄・日付入力を含む）をデフォルトに戻し、ページ1にリセット。
  2. **再取得:** デフォルトパラメータで`GET /api/v1/admin/audit-logs`を実行。
  3. **UI更新:** フィルタークリアボタンとアクティブフィルターバッジを非表示。
- **例外処理:** 該当なし。

### 5.10 ページネーション（`btnPrevPage` / `btnNextPage` / `btnPageNumbers` / `selPageSize` onClick/onChange）
- **トリガー:** 管理者がページナビゲーションをクリック、またはページサイズを変更。
- **処理ロジック:**
  1. **状態更新:** `page`（ページ変更）または`limit` + `page=1`リセット（ページサイズ変更）を更新。
  2. **再取得:** 更新されたパラメータで`GET /api/v1/admin/audit-logs`を実行。
  3. **UI更新:** テーブル、ページネーションコントロール、ページ情報テキストを更新。
- **例外処理:**
  - `400`（BAD_REQUEST）: サーバーメッセージをエラーバナーで表示。

### 5.11 カラムソート（`colTimestamp` / `colAction` / `colEntityType` ヘッダークリック）
- **トリガー:** 管理者がソート可能なカラムヘッダーをクリック。
- **処理ロジック:**
  1. **切り替え/リセット:** 同一列なら`asc`/`desc`を切り替え、別の列ならその列 + `desc`で設定。
  2. **再取得:** `sortBy` / `sortOrder`付きで`GET /api/v1/admin/audit-logs`を実行。ページはリセットしない。
  3. **UI更新:** ソートアイコンが`ArrowUp` / `ArrowDown`（非対象列は減光された`ArrowUpDown`）に切替。
- **例外処理:** 該当なし。

### 6.6 バリデーション強制レイヤー

1. **フロント側（クライアント）:** Zodスキーマ（`auditLogQuerySchema`、`deleteAuditLogsSchema`）によるリアルタイムフィードバック。本画面でReact Hook Formは**使用しません** — ダイアログはローカルの`useState`と`safeParse`で状態を管理します。
2. **バックエンド（サーバー）:** NestJS ValidationPipe + class-validator DTOsをすべてのエンドポイントで適用。
3. **データベース（制約）:** DBインデックスをパフォーマンスの安全策として活用。

## 7. レスポンシブレイアウト動作

### 7.1 デスクトップ（≥1024px）
- すべてのカラムが表示されるフルテーブルレイアウト（横方向スクロール可能なコンテナ）
- フィルターカード4列グリッド（`lg:grid-cols-4`）、日付範囲は全幅行

- 水平スクロール付きレスポンシブテーブル
- 2列フィルターグリッド
- センタードモーダル／ダイアログ（`md:`のブレークポイントで中央配置・枠線付きのスタイルを適用）

- カードコンテナ内のスクロール可能テーブル（フィルターは1列）
- 詳細モーダル、エクスポートダイアログ、削除ダイアログは全画面（`h-dvh`、角丸なし）で内部スクロール
