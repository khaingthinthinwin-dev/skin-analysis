## 1. 機能概要

### 1.1 目的と範囲

本サブシステムは、ダッシュボードと分析画面を通じて、マーチャントとプラットフォーム管理者にビジネスパフォーマンスの統合ビューを提供します。マーチャントは自店舗の売上、注文、商品パフォーマンス、顧客デモグラフィクスを監視でき、管理者はプラットフォーム全体のKPI、収益、ユーザー成長、マーチャント・カテゴリ別パフォーマンスを監視できます。

本サブシステムは、分析に対して**完全に読み取り専用**です。KPIやグラフデータは、トランザクションデータ（`orders`・`order_items`）とマスタデータ（`products`・`users`・`shops`・`reviews`）をクエリ時に集計して導出します。本バージョンでは導出KPIテーブルは永続化しません。

**スコープ境界:** 注文ステータス更新（`PATCH /orders/:id/status`、M-DASH-003）は本サブシステムの**対象外**です。これは**注文管理・フルフィルメントモジュール**が所有・実装します。Sales & Analyticsはデータ依存関係として `orders.status` を**読み取るのみ**です（KPI認識 BR-SA-006、注文一覧表示、キャッシュ無効化 §11.2）。本サブシステムは `orders.status` を一切書き込みません。

### 1.2 機能責務

本サブシステムは以下のコア機能領域を担当します。

1. **販売ダッシュボードKPI** — 主要指標（総売上、注文数、平均注文金額、平均評価）の表示（M-DASH-005）。
2. **日次・月次売上概要** — 日別・月別の売上サマリー表示（M-DASH-001）。
3. **注文一覧（読み取り専用）** — 自店舗の注文をステータス・金額付きで表示（M-DASH-002）。`orders.status` は読み取り専用で表示し、更新は注文管理・フルフィルメントモジュールで行う（対象外）。
4. **注文ステータス更新（対象外）** — 注文ステータスの前進（M-DASH-003）は注文管理・フルフィルメントモジュールが所有。本仕様ではデータ依存関係のトレーサビリティのため §3・§4.4・§6.4 に記載するのみで、ここでは実装しない。
5. **ベストセラー商品ランキング** — 上位商品の表示（M-DASH-004）。
6. **売上トレンドグラフ** — 選択可能な期間（7d/30d/90d/1y）で売上トレンドを可視化（M-ANAL-001）。
7. **商品パフォーマンス** — 商品ごとの閲覧数・売上パフォーマンス表示（M-ANAL-002）。
8. **顧客デモグラフィクス** — 配送先住所データから匿名化した顧客属性の内訳表示（M-ANAL-003）。
9. **プラットフォーム全体ダッシュボード（管理者）** — プラットフォームKPI（ユーザー、マーチャント、注文、収益）と保留アクション表示（A-ANAL-001）。
10. **ユーザー成長分析（管理者）** — 時間経過に伴うユーザー成長表示（A-ANAL-002）。
11. **売上レポート（管理者）** — 月次・年次の売上レポートとエクスポート（A-ANAL-003）。
12. **カテゴリ別パフォーマンス（管理者）** — カテゴリ別の売上・収益内訳（A-ANAL-004）。
13. **マーチャント別パフォーマンス（管理者）** — マーチャント別収益ランキング（A-ANAL-005）。

### 1.3 対象ユーザー

| 属性 | 値 |
|------|-----|
| **主要アクター（マーチャント）** | 自店舗の売上・注文・分析を閲覧する認証済みマーチャント |
| **主要アクター（管理者）** | プラットフォーム全体のダッシュボード・分析を閲覧する認証済み管理者 |

| **データスコープ** | マーチャント：自店舗の注文商品と自社商品のみ。管理者：プラットフォーム全体。 |

### 2.4 データ依存関係 — 注文ステータス更新（M-DASH-003）

注文ステータス更新のワークフローは**すべて注文管理・フルフィルメントモジュール**が実行します（本サブシステムの対象外）。Sales & Analyticsはその結果を消費するのみです。

| 手順 | 操作 | 担当モジュール |
|:----:|------|---------------|
| 1 | マーチャントが注文管理画面でステータスを前進させる | 注文管理・フルフィルメント |
| 2 | `PATCH /orders/:id/status` が前進のみの遷移を検証し保存する | 注文管理・フルフィルメント |
| 3 | 注文管理が `cache:sa:merchant:{id}:kpis` を無効化する（モジュール間契約、§11.2） | 注文管理・フルフィルメント |
| 4 | Sales & Analyticsが次回リクエスト時に更新された `orders.status` からKPIを再集計する | Sales & Analytics（読み取り専用） |

状態機械自体（状態と前進のみの遷移）は §3 に定義され、§6.4 に従い注文管理モジュールが強制します。

## 3. 状態遷移仕様

> 下記の注文ステータス状態機械（§3.1–§3.2）は**注文管理・フルフィルメントモジュール**が所有・強制します（対象外）。Sales & Analyticsは、`orders.status` の読み取り方法（KPI認識 BR-SA-006、注文一覧表示、キャッシュ無効化 §11.2）を定義するためにのみここに記載します。本サブシステムは遷移を一切実行しません。

### 3.1 注文ステータス状態（M-DASH-003）

| 状態 | DB値 | 説明 | 終端状態 |
|------|------|------|:--------:|
| `PENDING` | `'pending'` | 注文作成・マーチャント確認待ち | ✗ |
| `CONFIRMED` | `'confirmed'` | マーチャントが注文を確認 | ✗ |
| `PROCESSING` | `'processing'` | 出荷準備中 | ✗ |
| `DELIVERED` | `'delivered'` | 顧客へ配達済み | ✗ |
| `DONE` | `'done'` | 注文完了・顧客確認済み | ✓ |

### 3.2 注文ステータス遷移表

| 遷移ID | 起点状態 | 目標状態 | トリガー操作 | ガード条件 |
|--------|----------|----------|--------------|------------|
| TR-SA-01 | `PENDING` | `CONFIRMED` | マーチャントが注文を確認 | 注文に自店舗の商品が1件以上含まれる |
| TR-SA-02 | `CONFIRMED` | `PROCESSING` | マーチャントが出荷準備を開始 | 前状態が `confirmed` |
| TR-SA-03 | `PROCESSING` | `DELIVERED` | マーチャントが配達済みに変更 | 前状態が `processing` |
| TR-SA-04 | `DELIVERED` | `DONE` | 注文完了 | 前状態が `delivered` |

> 規則: **前進方向のみ**の遷移を許可（TR-SA-01→02→03→04）。後退・スキップは不可。`done` は終端。遷移は**注文管理・フルフィルメントモジュール**が強制します（§6.4、対象外）。

### 3.3 クエリ状態仕様（期間）

| 状態 | 説明 | 動作 |
|------|------|------|
| `RANGE_PRESET` | ユーザーが7d/30d/90d/1yを選択 | クエリ時に `now()` から期間を算出 |
| `RANGE_CUSTOM` | 明示的な `from`/`to` を指定 | `range` とは排他。両方指定で `400 BAD_REQUEST` |
| `RANGE_EMPTY` | 期間指定なし | デフォルト `30d` |

### 3.4 データ鮮度 / キャッシュ状態

| 状態 | 説明 | TTL | 動作 |
|------|------|:---:|------|
| `CACHE_COLD` | ダッシュボードKPI未キャッシュ | — | DBクエリ、Redisキャッシュをシード |
| `CACHE_WARM` | ダッシュボードKPIキャッシュ済み | 5分 | キャッシュレスポンスを返却 |
| `CACHE_INVALIDATED` | 注文ステータス更新 *（注文管理・フルフィルメントモジュールによる）* | — | `DEL cache:sa:merchant:{id}:kpis`、次回リクエストで再クエリ |

## 9. エラー処理仕様

### 9.1 エラーレスポンス構造

```json
{
  "statusCode": 409,
  "message": ["Invalid status transition"],
  "error": "Conflict",
  "timestamp": "2026-08-14T12:00:00.000Z",
  "path": "/api/v1/orders/clx1234567890/status"
}
```

### 9.2 エラー分類テーブル — 販売・分析

| HTTPステータス | エラーコード | シナリオ | ユーザー向け動作 |
|----------------|--------------|----------|------------------|
| `400` | `BAD_REQUEST` | 期間・日付・期間形式・クエリパラメータ不正 | フィールド別インラインエラー + 上部バナー |
| `401` | `UNAUTHORIZED` | JWT欠落・無効 | ログインへリダイレクト |
| `403` | `FORBIDDEN` | 非マーチャント・非管理者ロール、または他店舗のデータへのアクセス | "You don't have permission to view this data" |
| `404` | `NOT_FOUND` | 注文 `:id` が見つからない *（注文管理・フルフィルメントモジュールが送出 — 分析画面からは発生しない）* | "Order not found" + 更新オプション |
| `409` | `INVALID_STATUS_TRANSITION` | 非前進の注文ステータス変更 *（注文管理・フルフィルメントモジュールが送出 — 分析画面からは発生しない）* | "Invalid status transition" + ステータスバッジは変化なし |
| `422` | `UNPROCESSABLE_ENTITY` | レポート期間の組み合わせ不正 | "Invalid report parameters" |
| `429` | `TOO_MANY_REQUESTS` | レート制限超過 | "Too many requests. Please wait {seconds} seconds" |
| `500` | `INTERNAL_SERVER_ERROR` | 集計・DB障害 | "Something went wrong. Please try again" |

### 9.3 フロントエンドのエラー表示動作

- **グラフ・ローディング**: フェッチ中のスケルトン表示。エラー時は再試行ボタン付きエラー状態。
- **空データ**: ゼロ埋めグラフと `0`/`—` KPIプレースホルダ（BR-SA-025）。エラーにしない。
- **注文ステータスエラー**: 分析画面からは発生しない（ステータスは読み取り専用）。更新の再取得時に古い `409` が返った場合、バッジはサーバーレスポンスで再描画。
- **トースト通知**: APIエラーと出力成功に使用。
- **出力失敗**: CSV出力エラーはトーストで通知。出力はクライアント側のため、常に現在のビューを出力。

### 10.4 所有権とデータスコープ

```typescript
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles('merchant', 'admin')
@Controller('analytics/merchant')
export class MerchantAnalyticsController {
  // GET /dashboard, GET /sales, GET /products, GET /demographics
  //   merchant  -> order_items.merchant_id = 現在のユーザー でスコープ（BR-SA-001）
  //   admin     -> マーチャントスコープなし（BR-SA-002）。管理者は店舗を持たないため、
  //                マーチャントフィルタで明示しない限りデータなし
}

@UseGuards(JwtAuthGuard, RolesGuard)
@Roles('admin')
@Controller('analytics/admin')
export class AdminAnalyticsController {
  // GET /dashboard, GET /revenue, GET /users（管理者のみ）
}

@UseGuards(JwtAuthGuard, RolesGuard)
@Roles('merchant', 'admin')
@Controller('orders')
export class MerchantOrdersController {
  // GET /         -> 読み取り専用の注文一覧: merchant: 自店舗商品を含む注文。admin: 全注文
  // PATCH /:id/status -> 対象外: 注文管理・フルフィルメントモジュールが所有（§6.4）
  //   merchant  -> 注文に呼び出し元が所有する商品が含まれない場合 403（BR-SA-017）
  //   admin     -> 許可。マーチャント所有権をバイパス（管理者はマーチャント機能を継承、
  //                要件定義書 §2）。前進のみの遷移ルール（BR-SA-016）は引き続き適用
}
```

## 11. リアルタイム通知動作

### 11.1 現在の実装

販売・分析画面はWebSocket接続を必要としません。ダッシュボード・分析データは、ナビゲーション時と期間変更時に標準のクエリ無効化（TanStack Query）で取得します。ステータス更新（およびそれによるキャッシュ無効化）は注文管理・フルフィルメントモジュールが開始します。

### 11.2 更新トリガー

| イベント | トリガー | 効果 |
|----------|----------|------|
| 注文ステータス更新 | `PATCH /orders/:id/status` 成功 *（注文管理・フルフィルメントモジュールが開始）* | KPIキャッシュ無効化。注文一覧とKPIを再取得 |
| 期間変更 | ユーザーが7d/30d/90d/1yを切り替え | 新しいウィンドウでグラフとKPIを再取得 |
| 手動更新 | 更新ボタンクリック | アクティブビューを完全再取得 |
| ルートフォーカス | ダッシュボードルートに復帰 | スケールタイムを超えたクエリを再取得（デフォルト5分） |

### 11.3 保留アクション（管理者ダッシュボード）

保留アクション件数（マーチャント承認、レビュー審査、コンテンツ通報）は、管理者ダッシュボードとともに取得される読み取り専用の集計です。ダッシュボード読み込み時に更新されます。本バージョンではプッシュ通知は実装しません。

## 16. 共有スキーマと画面間の考慮事項

本セクションは、他サブシステムと共有するスキーマと動作を文書化します。他機能仕様書（例: SKM-FDS-AD-001 BR-AD-042）で提起されたスキーマギャップのクロスリファレンス先です。

### 16.1 共有テーブル

| テーブル | 消費元 | 販売・分析での用途 |
|----------|--------|--------------------|
| `orders` | 販売ダッシュボード、チェックアウト、注文履歴 | 収益KPI、注文一覧、レポート |
| `order_items` | 販売ダッシュボード、チェックアウト | マーチャントスコープの売上集計 |
| `products` | 商品管理、商品詳細 | 商品パフォーマンス、評価KPI |
| `shops` | 店舗プロフィール、広告管理 | マーチャント識別、管理者の保留アクション |
| `reviews` | レビュー審査、商品詳細 | 保留レビュー数 |
| `users` | サインアップ/ログイン、管理者管理 | ユーザー成長、マーチャント識別 |

### 16.2 注文ステータス列挙の共有

`order_statuses`（pending, confirmed, processing, delivered, done）は、チェックアウト（`pending` を作成）、注文履歴（表示）、注文管理・フルフィルメント（ステータス前進）で共有されます。Sales & AnalyticsはKPI認識（BR-SA-006）と注文一覧表示のために**読み取り専用**で消費します。列挙値の変更はこれらのサブシステム全体で調整する必要があります。

### 16.3 決済ステータス列挙の共有

`orders.payment_status`（pending, completed, failed）は、チェックアウトが書き込み、管理者売上レポートが読み取ります（BR-SA-019 は `completed` のみをカウント）。決済意味論の変更は報告収益に影響します。

### 16.4 products.avg_rating / review_count の共有

`avg_rating`/`review_count` はレビューサブシステムが `products` に非正規化します。販売・分析は読み取り専用で利用します（BR-SA-009、§7.6）。再計算はレビューサブシステムの責務とします。

### 16.5 shop.is_approved の共有

`shops.is_approved` は広告管理画面（SKM-FDS-AD-001 BR-AD-040~043）をゲートし、本仕様の管理者保留アクション件数（§5.3 EL-SA-45）でも使用します。管理者ダッシュボードは `is_approved = false` のショップを「承認待ちマーチャント」としてカウントしますが、これは保留と却下を区別できないヒューリスティックです（§16.7 参照）。

### 16.6 集計の真実の源

本仕様のKPI・レポート数値は、`orders`/`order_items` からクエリ時に計算します。非正規化された収益・KPIテーブルは存在しません。将来のバージョンで分析マテリアライゼーション（例: 日次ロールアップテーブル）を導入する場合は、ここに明記し、BR-SA-005/006/019 の定義と整合させる必要があります。

### 16.7 shops.is_approved ブール制限（保留 vs 却下）

**状態:** 文書化された制限。本バージョンではスキーマ変更なし。

`shops.is_approved` はブール値（データベース設計書 §3.9）のため、審査待ち（保留）と審査後の却下を**区別できません**。また `shops` には `rejection_reason` フィールドがありません（`advertisements.rejection_reason` とは異なります）。

現状の影響:
1. **広告管理**（SKM-FDS-AD-001 BR-AD-041/042）: ショップが未承認のマーチャントはホームページへリダイレクトされます。保留も却下も `is_approved = false` に集約され、同一の扱いを受けます。
2. **管理者ダッシュボードの保留アクション**（本仕様、§5.3 EL-SA-45）: 「承認待ちマーチャント」はすべての `is_approved = false` のショップをカウントするため、却下済みショップを含めて実際の保留作業を過大に計上します。

将来のスキーマバージョンへの推奨:
- ブールを `shops` 上の列挙型 `approval_status`（`pending`/`approved`/`rejected`）に置き換え、`advertisements.approval_status` と同様にする。
- 却下ショップ用に `shops.rejection_reason`（VARCHAR、NULL許容）を追加する。
- BR-AD-040~043、管理者の保留アクションクエリ（§6.6 手順3）、およびマーチャント向けリダイレクトロジック（SKM-FDS-AD-001 §12）をそれに応じて更新する。

影響ドキュメント: SKM-FDS-AD-001（BR-AD-042）、本ドキュメント（§5.3、§6.6、§16.5）。

### 16.8 変更調整

`order_statuses`、`orders.payment_status`、`products.avg_rating`、`shops.is_approved` への変更は、SKM-FDS-AD-001（広告管理）、チェックアウト・注文履歴の機能仕様書、レビュー機能仕様書、本ドキュメントに対してレビューする必要があります。
