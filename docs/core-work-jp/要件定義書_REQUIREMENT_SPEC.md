## 1. プロジェクト概要と背景

### 1.1 プロジェクト名
**Cosmetics Finder**

### 1.2 目的と目標
本システムは、パーソナライズされたスキンケアソリューションを求める購入者と、スキンケア商品を販売する出品者をつなぐAI搭載のスキンケアマーケットプレイスプラットフォームを提供します。プラットフォームの特徴として、AI肌分析、スマートな商品レコメンド、閲覧からチェックアウトまでの完全なeコマースワークフローを備えています。

### 1.3 ビジネス背景
- **課題:** 消費者は個人の肌タイプや肌悩みに合ったスキンケア商品を見つけるのが困難です。従来のeコマースにはパーソナライゼーションが欠如しており、不適切な商品選択や無駄な支出につながっています。
- **解決策:** ユーザーの肌状態を分析し、パーソナライズされた商品をレコメンドするAI搭載のマーケットプレイスを実装し、購入者と適切な出品者をつなぎます。
- **期待される成果:**
  - AI分析に基づくパーソナライズされたスキンケア商品レコメンド
  - ターゲット商品マッチングによるコンバージョン率の向上
  - 出品者向けの商品管理・売上分析ツール
  - マルチベンダーマーケットプレイスモデルによるプラットフォーム成長

### 1.4 プロジェクト範囲
- **含まれるもの:** ユーザー認証/認可、AI肌分析、商品管理、ショッピングカート、チェックアウト、注文管理、出品者ダッシュボード、管理者パネル、多言語対応（EN/MY/JA）
- **含まれないもの:** 物理的な商品配送ロジスティクス、ペイメントゲートウェイ統合（スタブ化）、モバイルネイティブアプリ、高度なMLモデルトレーニング

### 1.5 技術スタック

**バックエンド:**
- ランタイム: Node.js v22+ (LTS)
- フレームワーク: NestJS v11
- 言語: TypeScript v5.7+
- ORM: Prisma v6
- データベース: PostgreSQL v16
- キャッシュ: Redis v7 (ioredis v6)
- 認証: JWT (access + refresh tokens), Argon2パスワードハッシュ
- APIドキュメント: Swagger/OpenAPI v11

**フロントエンド:**
- UIライブラリ: React v19
- バンドラ: Vite v6
- 言語: TypeScript v5.7+ (strict)
- ルーティング: React Router v7
- 状態管理: TanStack Query v5
- フォーム: React Hook Form + Zod
- UIコンポーネント: shadcn/ui (Radix UI)
- スタイリング: Tailwind CSS v4
- i18n: i18next (English, Myanmar, Japanese)
- テスト: Vitest, Testing Library, MSW v2

## 3. 機能要件

### 3.1 コアエンティティとデータモデル

#### 3.1.1 ユーザーエンティティ
ロール割り当てを持つシステムユーザーを表現します。

**属性:**
- UserID (主キー, CUID)
- Email (ユニーク)
- FullName
- PasswordHash (Argon2)
- Role (buyer, merchant, admin)
- AvatarUrl (オプション)
- Phone (オプション)
- IsActive (デフォルト: true)
- EmailVerified (デフォルト: false)
- CreatedDate
- ModifiedDate

#### 3.1.2 商品エンティティ
出品者によって出品されたスキンケア商品を表現します。

**属性:**
- ProductID (主キー, CUID)
- MerchantID (Userへの外部キー)
- CategoryID (Categoryへの外部キー)
- Name
- Slug (ユニーク)
- Description
- ShortDescription
- Price (Decimal 10,2)
- CompareAtPrice (オプション)
- SKU (ユニーク, オプション)
- StockQuantity (デフォルト: 0)
- LowStockThreshold (デフォルト: 10)
- Images (文字列配列)
- Tags (文字列配列)
- SkinTypes (文字列配列)
- Ingredients (文字列配列)
- IsActive (デフォルト: true)
- IsFeatured (デフォルト: false)
- AvgRating (Decimal 3,2, デフォルト: 0)
- ReviewCount (デフォルト: 0)
- CreatedDate
- ModifiedDate

#### 3.1.3 カテゴリエンティティ
ツリー構造を持つ商品カテゴリを表現します。

**属性:**
- CategoryID (主キー, CUID)
- Name
- Slug (ユニーク)
- ParentID (Categoryへの外部キー, オプション)
- IconUrl (オプション)
- SortOrder (デフォルト: 0)
- CreatedDate

#### 3.1.4 注文エンティティ
顧客注文を表現します。

**属性:**
- OrderID (主キー, CUID)
- UserID (Userへの外部キー)
- Status (pending, confirmed, processing, delivered, done)
- Subtotal (Decimal 10,2)

- Tax (Decimal 10,2, デフォルト: 0)

- IsVerifiedPurchase (デフォルト: false)

- CreatedDate
- ModifiedDate
- ユニーク制約: [UserID, ProductID]

#### 3.1.6 お気に入りエンティティ

- WishlistID (主キー, CUID)

## 4. 特別ビジネスルール

### 4.1 認証ルール

#### ルール 4.1.1: デュアルトークンアーキテクチャ
- アクセストークン: 15分の有効期限、`JWT_ACCESS_SECRET`で署名
- リフレッシュトークン: 7日間の有効期限、`JWT_REFRESH_SECRET`（異なるシークレット）で署名
- リフレッシュトークンはDB保存前にArgon2でハッシュ化
- トークンローテーション: 使用のたびに新しいリフレッシュトークンを発行
- 絶対時間制限: 90日間のハードセッション上限（ローテーションに関係なく）
- トークンファミリー追跡による侵入検出（リユーズ検出）
- 無効化されたトークンのリユーズ検出時: そのユーザーのすべてのトークンを無効化

#### ルール 4.1.2: Redisブラックリスト化
- ログアウト時、残りTTLの間アクセストークンをRedisでブラックリスト化
- JwtAuthGuardは各リクエスト時にRedisブラックリストをチェック（サブミリ秒）
- ログアウト後に盗まれたトークンの使用を防止

#### ルール 4.1.3: パスワードセキュリティ
- パスワードは8文字以上であること
- パスワードはArgon2でハッシュ化（メモリハード、GPU耐性）
- プレーンテキストパスワードは保存しない

### 4.2 商品ルール

#### ルール 4.2.1: 商品ステータス
- 商品は有効または無効にできる
- 有効な商品のみ検索結果に表示される
- 無効な商品は購入者には非表示だが出品者には表示される

#### ルール 4.2.2: 在庫管理
- 在庫数量は0以下にはならない
- 低在庫閾値で警告を発する（デフォルト: 10単位）
- 注文作成時に在庫がアトミックに減らされる
- 在庫切れの商品はカートに追加できない

#### ルール 4.2.3: 商品画像
- 商品ごとに最大10枚の画像
- 対応形式: JPG, PNG, WebP
- 最大ファイルサイズ: 画像ごとに5MB
- 最初の画像がメイン/カバー画像

### 4.3 注文ルール

#### ルール 4.3.1: 注文ステータスフロー
```
pending → confirmed → processing → delivered → done
```

#### ルール 4.3.2: 注文完了
- doneステータスはシステムによって自動確認または購入者によって確認される

#### ルール 4.3.3: 価格計算
- 小計 = すべてのアイテムの（単価 × 数量）の合計
- 税金は配送先住所の場所に基づいて計算される
- 合計 = 小計 + 送料 + 税金
- 価格は注文作成時にロックされ（後の価格変更の影響を受けない）

### 4.4 レビュールール

#### ルール 4.4.1: レビュー対象資格
- 商品を購入したユーザーのみレビュー可能（認証済み購入）
- ユーザーごとに商品ごとに1件のレビュー
- レビューはデフォルトで承認されるが、管理者によってモデレーション可能

#### ルール 4.4.2: レビュー評価
- 評価は1〜5の間であること（両端含む）
- 平均評価はすべての承認されたレビューから自動計算される
- レビュー数は自動更新される

### 4.5 プロモーションルール

#### ルール 4.5.1: クーポンバリデーション
- クーポンコードはユニークであること
- クーポンは有効で有効期限内であること
- 注文金額が最低要件を満たすこと（設定されている場合）
- 総使用数が最大使用数を超えないこと（設定されている場合）
- 注文ごとに1つのクーポンのみ適用可能

#### ルール 4.5.2: 割引計算
- パーセンテージ割引: 小計に適用
- 固定割引: 小計から差し引かれる（小計を超えない）
- 割引後の金額は0以下にならない

### 4.6 広告ルール

#### ルール 4.6.1: 広告承認
- すべての広告は表示前に管理者承認が必要
- 支払い後、広告は「承認待ち」ステータスになる
- 管理者は承認または却下（理由付き）できる
- 却下された広告は編集して再送信可能

#### ルール 4.6.2: 広告支払い
- 出品者は広告送信前に広告料金を支払う必要がある
- 検証後、広告は「承認待ち」に遷移
- 支払い取引は金額、ステータス、参照で記録
- 却下時は自動返金

#### ルール 4.6.3: 週間広告制限
- すべての出品者で週あたり最大5件の有効な広告
- 週は月曜00:00から日曜23:59（UTC）
- 表示前に制限を検証

#### ルール 4.6.4: 広告表示
- 広告はバナー/画像と告知メッセージで表示
- スケジュール内の承認済み広告のみ購入者に表示
- アクティブ広告は5分間TTLでRedisにキャッシュ

### 4.7 出品者ルール

#### ルール 4.6.1: 店舗承認
- 新しい出品者店舗には管理者承認が必要
- 承認されるまで店舗は無効
- 管理者は理由を付けて店舗を却下できる

#### ルール 4.6.2: 商品所有権
- 出品者は自分の商品のみ編集/削除可能
- 商品は出品者のユーザーアカウントにリンクされている

### 4.7 AI肌分析ルール

#### ルール 4.7.1: 画像要件
- 画像には顔が含まれていること
- 画像は明るくクリアであること
- 最大画像サイズ: 10MB
- 対応形式: JPG, PNG, WebP

#### ルール 4.7.2: 分析結果
- 分析結果は24時間キャッシュされる
- ユーザーはいつでも再分析可能
- 分析履歴は無期限に保持される

### 6.4 開発制約・前提条件

- **シングルテナント:** 単一組織向けに設計
- **多言語対応:** UIは最初からEnglish, Myanmar, Japaneseをサポート
- **ローカル開発:** Node.js, PostgreSQL, Redisをローカルマシンに
- **適切な負荷:** 一般的なeコマースワークロード向けに設計
- **AIサービス:** AI肌分析は外部APIを使用するか、初期実装ではスタブ化
- **ペイメントゲートウェイ:** 決済処理はスタブ化（実際の決済統合なし）

### 6.5 将来の拡張ポイント

1. **AI強化:** 肌分析の高度なMLモデル
2. **ペイメントゲートウェイ:** 実際の決済処理（Stripe, PayPal）
3. **モバイルアプリ:** React Nativeモバイルアプリケーション
4. **プッシュ通知:** Firebase Cloud Messaging
5. **メールサービス:** トランザクショナルメール（SendGrid, AWS SES）
6. **クラウドストレージ:** AWS S3, Azure Blob for file storage
7. **マイクロサービス移行:** サービスの独立スケーリング
8. **高度な分析:** ビジネスインテリジェンスダッシュボード

## 7. 受入基準と成功指標

### 7.1 機能的受入基準

- [ ] すべての3つのユーザーロールがログインし、それぞれのダッシュボードにアクセスできる
- [ ] ユーザー登録と認証がエンドツーエンドで機能する
- [ ] AI肌分析が画像を処理し、結果を返す
- [ ] 商品閲覧、検索、フィルタが正しく機能する
- [ ] ショッピングカート操作（追加、更新、削除）が適切に機能する
- [ ] チェックアウトフローが注文を作成し、在庫を更新する
- [ ] 出品者は商品を管理できる（CRUD操作）
- [ ] 出品者ダッシュボードに売上データが表示される
- [ ] 管理者はレビューとコンテンツをモデレーションできる
- [ ] すべてのAPIエンドポイントでロールベースアクセス制御が実行される
- [ ] 多言語対応がEN, MY, JAで機能する

### 7.2 非機能的受入基準

- [ ] ダッシュボードページのロード時間が≤ 2秒
- [ ] APIレスポンス時間が≤ 500ms（p95）
- [ ] すべてのロールベースアクセス制御が実行される
- [ ] SQLインジェクションとXSS脆弱性が軽減される
- [ ] データベーススキーマがPrismaマイグレーションで作成される
- [ ] テストカバレッジ ≥ 80%

### 7.3 成功指標

- **ユーザー登録:** 最初の月以内に100人以上のユーザー
- **AI分析利用:** 1日50件以上の分析
- **コンバージョン率:** 閲覧から購入まで5%以上
- **出品者導入:** 最初の四半期以内に10人以上の出品者
- **システム稼働率:** 99%以上の可用性
- **ユーザー満足度:** 平均評価4.0以上
